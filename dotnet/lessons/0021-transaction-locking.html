Transaction, isolation level, locking, dan deadlock

ACID, transaction yang benar di T-SQL dan EF Core, lima isolation level beserta anomalinya, dan blocking serta deadlock yang Anda buat sendiri di dua jendela query

Target lesson ini: Anda bisa menjawab pertanyaan interview "Jelaskan isolation level di SQL Server. Apa itu deadlock dan bagaimana mencegahnya?" tanpa melihat catatan, dan sudah melihat sendiri blocking, dirty read, phantom, dan deadlock antara dua sesi di ProductCatalogLab.

Lanjutan lesson 0020: pola SET XACT_ABORT ON + TRY/CATCH + THROW di usp_UpdatePrice kini dijelaskan alasannya. Padanan Node: prisma.$transaction(...) atau BEGIN/COMMIT lewat pg. Konsep isolation level dan deadlock sama di semua database relasional; yang khas SQL Server adalah default-nya (READ COMMITTED berbasis lock) dan nama fiturnya.

Catatan versi: dokumentasi Microsoft terbaru banyak menyebut optimized locking. Fitur itu hanya ada di Azure SQL dan SQL Server 2025 [11]. Container sql2022 memakai perilaku "without optimized locking", dan itulah yang diajarkan di sini.

1. ACID dan dasar transaction

"A transaction is a sequence of operations performed as a single logical unit of work." Empat properti yang wajib dimilikinya: [1]

PropertiArti (kutipan Microsoft Learn)Contoh Product Catalog
Atomicity"either all of its data modifications are performed, or none of them are performed"Transfer Stock: kurangi Product A dan tambah Product B, tidak boleh salah satu saja
Consistency"all rules must be applied to the transaction's modifications to maintain all data integrity"CHECK Stock >= 0, FK ke Category tetap terpenuhi
Isolation"Modifications made by concurrent transactions must be isolated from the modifications made by any other concurrent transactions"Dua request mengubah Product yang sama tidak saling melihat data setengah jadi
Durability"its effects are permanently in place in the system. The modifications persist even in the event of a system failure"Setelah COMMIT, server mati pun perubahan tetap ada
  • Mesinnya: "Locking facilities that preserve transaction isolation" dan "Logging facilities to ensure transaction durability" (transaction log). [1]
  • Autocommit adalah default: "Every Transact-SQL statement is committed or rolled back when it completes." Satu UPDATE yang mengubah 2.495 baris sudah atomik. Explicit transaction (BEGIN TRANSACTION … COMMIT/ROLLBACK) dibutuhkan saat beberapa statement harus berhasil atau gagal bersama. [1]
  • Jebakan interview: "If a run-time statement error (such as a constraint violation) occurs in a batch, the default behavior in the Database Engine is to roll back only the statement that generated the error." Jadi BEGIN TRAN; UPDATE (ok); UPDATE (gagal); COMMIT; tanpa pengaman menyimpan setengah transaction. Lab Langkah 3a memperlihatkannya. [1]

2. Transaction yang benar di T-SQL

SET XACT_ABORT ON;                         -- error run-time apa pun me-rollback SELURUH transaction
BEGIN TRY
    BEGIN TRANSACTION;
        UPDATE dbo.Product SET Stock = Stock - 5 WHERE Id = 1;
        UPDATE dbo.Product SET Stock = Stock + 5 WHERE Id = 2;
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;   -- 1 (masih aktif) atau -1 (uncommittable)
    THROW;                                     -- lempar ulang ke aplikasi (lesson 0020)
END CATCH;
  • SET XACT_ABORT ON: "if a Transact-SQL statement raises a run-time error, the entire transaction is terminated and rolled back." Default-nya OFF ("OFF is the default setting in a T-SQL statement, while ON is the default setting in a trigger"). Compile error (syntax) tidak terpengaruh. [3]
  • XACT_STATE(): 1 = ada transaction aktif yang bisa di-commit; 0 = tidak ada transaction; -1 = transaction "uncommittable": "it can only request a full rollback of the transaction." Bedanya dengan @@TRANCOUNT: "@@TRANCOUNT can't be used to determine whether that transaction is classified as an uncommittable transaction." [4] IF @@TRANCOUNT > 0 ROLLBACK seperti di lesson 0020 juga benar untuk pola ini, karena keduanya hanya me-rollback.
  • Nested transaction itu ilusi: "BEGIN TRANSACTION increments @@TRANCOUNT by 1." "A commit of an inner transaction decrements @@TRANCOUNT but has no other effects. A rollback of an inner transaction always rolls back the outer transaction". Yang menentukan hanya COMMIT terluar (lab Langkah 3c). [2]

Padanan Node: await prisma.$transaction(async tx => { ... }) otomatis rollback bila callback melempar error. Di T-SQL, perilaku "semua atau tidak sama sekali" itu harus Anda minta sendiri lewat XACT_ABORT dan TRY/CATCH.

3. Transaction di EF Core

  • Default sudah aman untuk satu SaveChanges: "all changes in a single call to SaveChanges are applied in a transaction. If any of the changes fail, then the transaction is rolled back and none of the changes are applied to the database." Microsoft menambahkan: "You should only manually control transactions if your application requirements deem it necessary." [5]
  • Manual, bila beberapa SaveChanges (atau SaveChanges + raw SQL) harus atomik: "You can use the DbContext.Database API to begin, commit, and rollback transactions." [5] Isolation level dipilih lewat overload BeginTransaction(IsolationLevel). [6]
// Pola dari dokumentasi EF Core. StockMovement hanya contoh tabel riwayat (tidak ada di mini project).
await using var tx = await context.Database.BeginTransactionAsync();   // opsional: (IsolationLevel.Serializable)
try
{
    from.Stock -= qty;
    await context.SaveChangesAsync();

    context.StockMovements.Add(new StockMovement { ProductId = from.Id, Delta = -qty });
    await context.SaveChangesAsync();

    await tx.CommitAsync();       // tanpa Commit, transaction di-rollback saat tx di-dispose
}
catch (Exception)
{
    // log; transaction otomatis di-rollback saat dispose
    throw;
}
  • Bila EnableRetryOnFailure aktif, transaction manual tidak bisa langsung dipakai: "Manually controlling transactions in this way is incompatible with implicitly invoked retrying execution strategies." [5] Tanpa itu, EF Core melempar InvalidOperationException: "The configured execution strategy 'SqlServerRetryingExecutionStrategy' does not support user-initiated transactions." Solusinya: "manually invoke the execution strategy with a delegate representing everything that needs to be executed. If a transient failure occurs, the execution strategy will invoke the delegate again." Jadi bungkus seluruh unit kerja (begin, SaveChangesAsync, commit) dengan context.Database.CreateExecutionStrategy().ExecuteAsync(...). [12]
  • Lost update tanpa lock panjang: EF Core mendukung optimistic concurrency: kolom [Timestamp] byte[] Version (rowversion) ikut di WHERE saat UPDATE; kalau baris sudah diubah orang lain, SaveChanges melempar DbUpdateConcurrencyException. Kata dokumentasinya: "optimistic concurrency takes no locks, but arranges for the data modification to fail on save if the data has changed since it was queried." SQL yang dikirim: UPDATE [People] SET [FirstName] = @p0 WHERE [PersonId] = @p1 AND [Version] = @p2;, dan bila ada update bersamaan "the UPDATE fails to find any matching rows and reports that zero were affected", sehingga SaveChanges() "throws a DbUpdateConcurrencyException". [Timestamp] memetakan properti ke kolom rowversion SQL Server yang "automatically changes when the row is updated". [13] Microsoft menyebut dua pendekatan: pessimistic ("A system of locks prevents transactions from modifying data in a way that affects other transactions") dan optimistic ("transactions don't lock data when they read it"). [1]

4. Isolation level dan anomalinya

Tiga anomali yang menjadi dasar semua pertanyaan isolation level [1]:

  • Dirty read: "a second transaction reads a row that's being updated by another transaction. The second transaction is reading data that hasn't been committed yet". Kalau penulisnya ROLLBACK, data yang dibaca tidak pernah ada.
  • Non-repeatable read: "a second transaction accesses the same row several times and reads different data each time."
  • Phantom: "two identical queries are executed and the set of rows returned by the second query is different." Penyebabnya INSERT/DELETE baris yang cocok dengan WHERE.
  • Bonus: lost update, dua transaction membaca baris yang sama lalu meng-UPDATE berdasarkan nilai lama: "The last update overwrites updates made by the other transactions". Obatnya UPDATE bersyarat dalam satu statement (seperti usp_AdjustStock di 0020), UPDLOCK, atau optimistic concurrency.
Isolation levelDirty readNon-repeatable readPhantomCara kerja (tanpa optimized locking)
READ UNCOMMITTEDbisabisabisatidak meminta S lock; setara hint NOLOCK
READ COMMITTED (default)tidakbisabisaS lock dilepas begitu baris selesai dibaca
REPEATABLE READtidaktidakbisaS lock ditahan sampai akhir transaction, tanpa range lock
SNAPSHOTtidaktidaktidakrow versioning: membaca versi saat transaction dimulai
SERIALIZABLEtidaktidaktidakkey-range lock atas rentang WHERE

Tabel diringkas dari [1] dan [7]. Dipasang per sesi dengan SET TRANSACTION ISOLATION LEVEL ...; di dalam SP, level kembali ke semula saat SP selesai.

  • READ COMMITTED: "statements can't read data that was modified but not committed by other transactions. ... This option is the SQL Server default." [7]
  • REPEATABLE READ "keeps read and write locks that are acquired on selected data until the end of the transaction. However, because range-locks aren't managed, phantom reads can occur." SERIALIZABLE: "Range-locks are acquired when a SELECT operation uses a range WHERE clause to avoid phantom reads", "the most restrictive of the isolation levels." [1]
  • Isolation level tidak mengubah lock untuk menulis: "A transaction always holds an exclusive lock to perform data modification, and holds that lock until the transaction completes, regardless of the isolation level". Isolation level hanya mengatur perilaku membaca. [1]
  • Trade-off: level rendah = lebih banyak akses bersamaan tapi lebih banyak anomali; level tinggi "requires more system resources and increases the chances that one transaction blocks another." [1]

  • Dengan row versioning, "read operations don't acquire shared (S) locks on the data being read, and therefore don't block transactions that are modifying data." Biayanya version store (tempdb). [1]
  • Default berbeda per platform: di SQL Server (termasuk 2022) READ_COMMITTED_SNAPSHOT OFF ("the default setting in SQL Server") dan ALLOW_SNAPSHOT_ISOLATION OFF; di Azure SQL Database RCSI ON. Jadi di sql2022, pembaca menunggu penulis. [1]
  • Rekomendasi Microsoft: "Microsoft recommends the row versioning-based READ COMMITTED isolation level for all applications, unless an application relies upon the blocking behavior of the lock-based READ COMMITTED isolation level." [8]

5. Lock dan blocking

"Locking is a mechanism used by the Database Engine to synchronize access by multiple users to the same piece of data at the same time." "All locks held by a transaction are released when the transaction completes (either commits or rolls back)." [1]

ModeDipakai untuk
Shared (S)membaca; di READ COMMITTED dilepas "as soon as the read operation completes"
Update (U)tahap "cari baris" sebelum mengubah; "Prevents a common form of deadlock"
Exclusive (X)INSERT/UPDATE/DELETE; ditahan sampai transaction selesai
Intent (IS, IX)tanda di level page/tabel bahwa ada lock di bawahnya ("lock hierarchy")
Key-rangedipakai SERIALIZABLE untuk mencegah phantom
Diminta ↓ / sudah dipegang →SUX
Sbolehbolehmenunggu
Ubolehmenunggumenunggu
Xmenunggumenunggumenunggu
  • Granularitas: KEY/RID (baris), PAGE, OBJECT (tabel). "Locking at a smaller granularity, such as rows, increases concurrency but has a higher overhead". Lock escalation ke tabel terjadi bila "A single Transact-SQL statement acquires at least 5,000 locks on a single nonpartitioned table or index." [1]
  • Blocking itu normal: "When a transaction requests a lock on a resource locked by another transaction, the requesting transaction waits until the lock is released. By default, transactions in the Database Engine don't time out, unless LOCK_TIMEOUT is set." [8] SET LOCK_TIMEOUT menentukan "the number of milliseconds a statement waits for a lock to be released"; "A value of -1 (default) indicates no time-out period (that is, wait forever)." [14] Jadi SET LOCK_TIMEOUT 3000 membuat statement menyerah setelah 3 detik dengan error 1222 "Lock request time out period exceeded." [15] Di aplikasi .NET, yang biasanya terlihat adalah command timeout dari sisi client.
  • Melihat blocking: sys.dm_exec_requests kolom blocking_session_id ("If this column is NULL or 0, the request isn't blocked"), wait_type, wait_time; sys.dm_tran_locks menampilkan setiap lock beserta request_mode dan request_status (GRANTED/WAIT). Di SQL Server 2022 keduanya butuh izin VIEW SERVER PERFORMANCE STATE (sa di lab sudah punya). [10] [9]
  • Pedoman transaction: "Don't require input from users during a transaction.", "Keep the transaction as short as possible.", "Access the least amount of data possible while in a transaction.", "Few transactions require the SERIALIZABLE transaction isolation level." [1] Di .NET artinya: jangan memanggil HTTP API eksternal atau menunggu user di antara BeginTransaction dan Commit.

Latihan 5 — Lock dan blocking

6. Deadlock

A: X lock Product 1→ mintaProduct 2 (milik B) · B: X lock Product 2→ mintaProduct 1 (milik A)
  • Definisi: "A deadlock occurs when two or more tasks permanently block each other by each task having a lock on a resource that the other tasks are trying to lock." Beda dengan blocking: blocking selesai sendiri saat lock dilepas; deadlock adalah siklus yang tidak akan pernah selesai sendiri. [8]
  • Deteksi dan victim: deadlock monitor memeriksa secara berkala ("The default interval is 5 seconds"). Engine "rolls back the transaction of the deadlock victim, and returns error 1205 to the application." Victim default adalah transaction "least expensive to roll back"; bisa diatur dengan SET DEADLOCK_PRIORITY. [8]
  • Pencegahan (judul-judul dari bagian "Minimize deadlocks"): "Access objects in the same order.", "Avoid user interaction in transactions.", "Keep transactions short and in one batch.", "Avoid higher isolation levels such as REPEATABLE READ and SERIALIZABLE when not required.", "Use a row versioning-based isolation level." Tetapi "deadlocks can't be completely avoided", jadi aplikasi tetap harus siap. [8]
  • Pola baca-lalu-ubah: dua transaction sama-sama memegang S lock lalu sama-sama minta X adalah deadlock klasik. Solusi resmi: "select a row with UPDLOCK hint, then update the row". [1] Lebih sederhana lagi: satu UPDATE bersyarat (WHERE Id = @Id AND Stock + @Delta >= 0) seperti usp_AdjustStock.
  • Investigasi: "The system_health event session captures xml_deadlock_report events by default", jadi deadlock graph sudah tersedia tanpa setup (lab Langkah 30). [8]
-- T-SQL: kunci baris untuk diubah sejak dibaca (U lock ditahan sampai COMMIT)
BEGIN TRANSACTION;
SELECT @stock = Stock FROM dbo.Product WITH (UPDLOCK) WHERE Id = @Id;
IF @stock >= @Qty
    UPDATE dbo.Product SET Stock = Stock - @Qty WHERE Id = @Id;
COMMIT TRANSACTION;
// C#: tangani 1205 dengan mengulang SELURUH unit kerja setelah jeda acak.
for (var attempt = 1; ; attempt++)
{
    try
    {
        await using var tx = await context.Database.BeginTransactionAsync();
        // ... baca dan ubah Product ...
        await context.SaveChangesAsync();
        await tx.CommitAsync();
        break;
    }
    catch (Exception ex) when (ex.GetBaseException() is SqlException { Number: 1205 } && attempt < 3)
    {
        context.ChangeTracker.Clear();                       // buang state yang sudah di-rollback
        await Task.Delay(Random.Shared.Next(50, 250));       // jeda acak
    }
}

Dasar pola retry: "applications should have an error handler that can handle error 1205", dan "The application should pause briefly before resubmitting its query ... Randomizing the duration of the pause minimizes the likelihood of the deadlock reoccurring". [8] Error 1205 juga bisa ditangkap di blok CATCH T-SQL.

-- ============ Bagian 1 · Atomicity, XACT_ABORT, TRY/CATCH (Sesi A saja) ======================

-- Langkah 3 (Sesi A) -----------------------------------------------------------------------
-- 3a) JEBAKAN: XACT_ABORT OFF (default) tanpa TRY/CATCH. Error 547 hanya membatalkan
--     STATEMENT yang gagal; batch lanjut, COMMIT tetap jalan, UPDATE pertama tersimpan.
SET XACT_ABORT OFF;
BEGIN TRANSACTION;
    UPDATE dbo.Product SET Stock = Stock + 5 WHERE Id = 1;   -- berhasil
    UPDATE dbo.Product SET Stock = -1 WHERE Id = 2;          -- gagal: CK_Product_Stock (547)
COMMIT TRANSACTION;
SELECT Id, Stock FROM dbo.Product WHERE Id IN (1, 2);        -- Id 1 = 36: setengah transaction tersimpan
UPDATE dbo.Product SET Stock = 31 WHERE Id = 1;              -- kembalikan

-- 3b) POLA BENAR: XACT_ABORT ON + TRY/CATCH. Error apa pun membatalkan SELURUH transaction.
SET XACT_ABORT ON;
BEGIN TRY
    BEGIN TRANSACTION;
        UPDATE dbo.Product SET Stock = Stock + 5 WHERE Id = 1;
        UPDATE dbo.Product SET Stock = -1 WHERE Id = 2;
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    -- XACT_STATE: 1 = masih bisa di-commit, -1 = uncommittable (hanya boleh ROLLBACK), 0 = tidak ada.
    SELECT XACT_STATE() AS XactState, ERROR_NUMBER() AS ErrorNumber;   -- -1 dan 547
    IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
    -- Di Stored Procedure, akhiri CATCH dengan THROW; (lesson 0020). Di sini tidak, supaya demo lanjut.
END CATCH;
SELECT Id, Stock FROM dbo.Product WHERE Id IN (1, 2);        -- 31 dan 62: tidak ada yang berubah
SET XACT_ABORT OFF;

-- 3c) Nested transaction bukan transaction sungguhan: COMMIT dalam hanya mengurangi @@TRANCOUNT.
BEGIN TRANSACTION;
    BEGIN TRANSACTION;
        SELECT @@TRANCOUNT AS TranCount;                     -- 2
        UPDATE dbo.Product SET Stock = 999 WHERE Id = 1;
    COMMIT TRANSACTION;                                      -- tidak menyimpan apa pun
    SELECT @@TRANCOUNT AS TranCount;                         -- 1
ROLLBACK TRANSACTION;                                        -- membatalkan SEMUANYA, termasuk yang "di-commit"
SELECT @@TRANCOUNT AS TranCount, Stock FROM dbo.Product WHERE Id = 1;   -- 0 dan 31
-- >>> lanjut: Langkah 4 (masih Sesi A)

UPDATE dbo.Product SET Price = 99999.99 WHERE Id = 1;

-- >>> lanjut: Sesi B, Langkah 5

-- Langkah 6 (Sesi A) -----------------------------------------------------------------------
-- Sesi B sedang menunggu. Siapa yang mem-block siapa?
SELECT session_id, status, blocking_session_id, wait_type, wait_time, wait_resource
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;        -- session Sesi B, diblok oleh Sesi A, wait_type LCK_M_S

-- Lock apa saja yang dipegang dan diminta di database ini?
SELECT request_session_id, resource_type, request_mode, request_status, resource_description
FROM sys.dm_tran_locks
WHERE resource_database_id = DB_ID(N'ProductCatalogLab')
  AND resource_type <> 'DATABASE'
ORDER BY request_session_id, resource_type;
-- Sesi A: X pada KEY (GRANTED), IX pada PAGE dan OBJECT (intent lock).
-- Sesi B: S pada KEY yang sama (WAIT), IS pada PAGE dan OBJECT.

ROLLBACK TRANSACTION;          -- lock dilepas, SELECT di Sesi B langsung selesai: 80.19

8. Latihan tulis query

Tulis sendiri di editor SQL, jalankan di lab, baru buka jawaban. Tidak dinilai otomatis; bandingkan hasil dan bentuk kodenya.

A. Tulis Stored Procedure dbo.usp_TransferStock dengan parameter @FromId int, @ToId int, @Qty int. SP memindahkan @Qty Stock dari satu Product ke Product lain secara atomik, menolak bila Stock asal tidak cukup (THROW 50003), dan tidak bisa deadlock walau dua request memanggil (1, 2) dan (2, 1) bersamaan. Uji: pindahkan 5 dari Id 1 ke Id 2, lalu coba pindahkan 100000, lalu kembalikan 5 dari Id 2 ke Id 1.

Lihat jawaban 
CREATE OR ALTER PROCEDURE dbo.usp_TransferStock
    @FromId int,
    @ToId   int,
    @Qty    int
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    DECLARE @FirstId  int = IIF(@FromId < @ToId, @FromId, @ToId),
            @SecondId int = IIF(@FromId < @ToId, @ToId, @FromId),
            @FirstStock int, @SecondStock int;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Kunci kedua baris dalam urutan Id naik, sama untuk SEMUA pemanggil: tidak ada siklus.
        -- UPDLOCK: lock ditahan sampai COMMIT, dan dua pembaca UPDLOCK tidak bisa sama-sama lolos.
        SELECT @FirstStock  = Stock FROM dbo.Product WITH (UPDLOCK) WHERE Id = @FirstId;
        SELECT @SecondStock = Stock FROM dbo.Product WITH (UPDLOCK) WHERE Id = @SecondId;

        IF @FirstStock IS NULL OR @SecondStock IS NULL
            THROW 50001, N'Product tidak ditemukan.', 1;
        IF IIF(@FromId = @FirstId, @FirstStock, @SecondStock) < @Qty
            THROW 50003, N'Stock asal tidak cukup.', 1;

        UPDATE dbo.Product SET Stock = Stock - @Qty WHERE Id = @FromId;
        UPDATE dbo.Product SET Stock = Stock + @Qty WHERE Id = @ToId;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;
GO

EXEC dbo.usp_TransferStock @FromId = 1, @ToId = 2, @Qty = 5;
SELECT Id, Stock FROM dbo.Product WHERE Id IN (1, 2);           -- 26 dan 67

BEGIN TRY
    EXEC dbo.usp_TransferStock @FromId = 1, @ToId = 2, @Qty = 100000;
END TRY
BEGIN CATCH
    SELECT ERROR_NUMBER() AS ErrorNumber, ERROR_MESSAGE() AS Message;   -- 50003
END CATCH;

EXEC dbo.usp_TransferStock @FromId = 2, @ToId = 1, @Qty = 5;   -- kembali 31 dan 62
SELECT Id, Stock FROM dbo.Product WHERE Id IN (1, 2);
GO

Poin yang dinilai interviewer: XACT_ABORT ON + TRY/CATCH + THROW; (atomicity dan error sampai ke aplikasi); urutan akses yang sama (Id kecil dulu) sebagai pencegah deadlock; UPDLOCK supaya pola baca-lalu-ubah tidak berubah menjadi deadlock S→X atau lost update. Uji deadlock-nya sendiri: jalankan EXEC dbo.usp_TransferStock 1, 2, 1 dan 2, 1, 1 bersamaan di dua jendela, dibungkus BEGIN TRAN tanpa COMMIT: yang kedua hanya menunggu, tidak ada 1205 (lalu ROLLBACK di kedua jendela). Kalau ditanya "kenapa tidak cukup CHECK constraint?": constraint tetap penjaga terakhir (547), tapi 50003 lebih jelas untuk dipetakan ke response 409.

B. Tulis query "siapa mem-block siapa" untuk dipakai saat aplikasi terasa macet: tampilkan session_id yang menunggu, blocking_session_id, wait_type, lama menunggu dalam detik, nama isolation level sesi yang menunggu (bukan angkanya), dan teks SQL yang sedang menunggu. Jalankan di jendela ketiga saat lab sedang di Langkah 5 (Sesi B menunggu Sesi A).

Lihat jawaban 
SELECT r.session_id,
       r.blocking_session_id,
       r.wait_type,
       r.wait_time / 1000.0 AS WaitSeconds,
       CASE r.transaction_isolation_level
           WHEN 1 THEN 'READ UNCOMMITTED'
           WHEN 2 THEN 'READ COMMITTED'
           WHEN 3 THEN 'REPEATABLE READ'
           WHEN 4 THEN 'SERIALIZABLE'
           WHEN 5 THEN 'SNAPSHOT'
           ELSE 'UNSPECIFIED'
       END AS IsolationLevel,
       t.text AS WaitingSql
FROM sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id <> 0
ORDER BY r.wait_time DESC;

blocking_session_id bukan 0 berarti request itu diblok; angka isolation level (1–5) dipetakan sesuai dokumentasi sys.dm_exec_requests. CROSS APPLY memanggil function per baris (mirip JOIN ke table-valued function di lesson 0020). Langkah berikutnya di dunia nyata: lihat apa yang dikerjakan sesi pemblokir (biasanya transaction yang lupa di-commit atau terlalu panjang), bukan langsung KILL.

Latihan 7 — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Jelaskan isolation level di SQL Server: anomali apa yang dicegah masing-masing, apa default-nya, dan level mana yang Anda pilih." (60–90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Isolation level menentukan seberapa jauh transaction terlindung dari perubahan transaction lain yang berjalan bersamaan. Ada tiga anomali: dirty read, yaitu membaca data yang belum di-commit; non-repeatable read, membaca baris yang sama dua kali dengan hasil berbeda; dan phantom, query yang sama mengembalikan himpunan baris berbeda karena ada INSERT. READ UNCOMMITTED membolehkan ketiganya, sama dengan NOLOCK. READ COMMITTED, default SQL Server, mencegah dirty read. REPEATABLE READ menahan shared lock sampai akhir transaction sehingga mencegah non-repeatable read, tapi phantom masih bisa. SERIALIZABLE menambah range lock sehingga phantom pun tercegah, dengan biaya blocking paling besar. SNAPSHOT mencegah ketiganya lewat row versioning, pembaca tidak memblok penulis, tapi harus diaktifkan dengan ALLOW_SNAPSHOT_ISOLATION dan bisa gagal dengan update conflict 3960. Di SQL Server 2022 READ_COMMITTED_SNAPSHOT default OFF, jadi pembaca menunggu penulis; Microsoft menyarankan RCSI untuk kebanyakan aplikasi. Apa pun levelnya, UPDATE tetap memegang X lock sampai commit. Pilihan saya: default READ COMMITTED, idealnya dengan RCSI, dan level lebih tinggi hanya untuk transaction tertentu yang memang butuh."

Checklist: apakah Anda menyebut…

  • tiga anomali dengan definisi: dirty read, non-repeatable read, phantom?
  • READ UNCOMMITTED (= NOLOCK) membolehkan dirty read; READ COMMITTED adalah default dan mencegahnya?
  • REPEATABLE READ menahan shared lock sampai akhir transaction, phantom masih bisa; SERIALIZABLE memakai range lock?
  • SNAPSHOT memakai row versioning: pembaca tidak memblok penulis, perlu ALLOW_SNAPSHOT_ISOLATION, bisa update conflict?
  • trade-off: level lebih tinggi berarti lebih banyak blocking dan risiko deadlock; RCSI default OFF di SQL Server 2022?
  • pilihan yang dibela: READ COMMITTED (idealnya RCSI), level tinggi hanya bila perlu; UPDATE tetap memegang X lock?

"Apa itu deadlock, apa bedanya dengan blocking, dan bagaimana Anda mencegah serta menanganinya di aplikasi .NET?" (60–90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Blocking itu normal: transaction B menunggu lock yang dipegang transaction A, dan begitu A commit atau rollback, B lanjut. Deadlock adalah siklus: A memegang baris 1 dan menunggu baris 2, sementara B memegang baris 2 dan menunggu baris 1, jadi tidak ada yang bisa lanjut. SQL Server punya deadlock monitor yang memeriksa secara berkala, default tiap 5 detik; ia memilih satu victim, biasanya yang paling murah di-rollback, me-rollback transaction-nya, dan mengirim error 1205. Pencegahannya: akses tabel dan baris dalam urutan yang sama di semua kode, transaction sependek mungkin tanpa menunggu input user, jangan pakai REPEATABLE READ atau SERIALIZABLE kalau tidak perlu, pertimbangkan RCSI supaya pembaca tidak memblok penulis, dan untuk pola baca-lalu-ubah pakai UPDLOCK saat membaca. Karena deadlock tidak bisa dihilangkan seratus persen, aplikasi harus menangkap SqlException nomor 1205 lalu mengulang seluruh transaction setelah jeda singkat yang diacak. Untuk investigasi, deadlock graph sudah dicatat otomatis oleh extended event system_health."

Checklist: apakah Anda menyebut…

  • blocking = menunggu lock lalu lanjut setelah dilepas; deadlock = siklus saling menunggu?
  • contoh konkret dua transaction yang mengunci dua baris dengan urutan terbalik?
  • deadlock monitor memilih victim (paling murah di-rollback), me-rollback, error 1205?
  • pencegahan: urutan akses sama, transaction pendek, tanpa input user di tengah transaction?
  • hindari isolation level tinggi bila tidak perlu, RCSI, atau UPDLOCK untuk pola baca-lalu-ubah?
  • aplikasi menangkap 1205 dan retry seluruh transaction dengan jeda acak; deadlock graph di system_health?

Lulus kalau minimal 4 dari 6.

"Apa itu ACID? Tunjukkan cara menulis transaction yang benar di T-SQL dan di EF Core." (60–90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"ACID adalah empat jaminan transaction: Atomicity, semua perubahan tersimpan atau tidak sama sekali; Consistency, data selalu memenuhi aturan seperti constraint; Isolation, transaction yang berjalan bersamaan tidak saling mengganggu, diatur lewat isolation level dan lock; Durability, yang sudah di-commit tetap ada walau server crash, dijamin transaction log. Di T-SQL tiap statement sudah autocommit, tapi kalau beberapa statement harus atomik saya tulis SET XACT_ABORT ON, lalu BEGIN TRY, BEGIN TRANSACTION, statement-statementnya, COMMIT. Di BEGIN CATCH: IF XACT_STATE() <> 0 ROLLBACK, lalu THROW supaya error sampai ke aplikasi. XACT_ABORT penting karena default-nya hanya statement yang gagal yang di-rollback, sehingga tanpa itu COMMIT bisa menyimpan setengah transaction. Saya juga tahu nested BEGIN TRAN tidak independen: COMMIT dalam hanya mengurangi @@TRANCOUNT. Di EF Core, satu SaveChanges sudah otomatis satu transaction. Kalau beberapa SaveChanges harus atomik, saya pakai await using var tx = await context.Database.BeginTransactionAsync(), bisa dengan IsolationLevel, lalu CommitAsync; kalau exception, transaction di-rollback saat dispose. Kalau retry on failure aktif, bungkus dengan execution strategy."

Checklist: apakah Anda menyebut…

  • keempat huruf ACID dengan arti yang benar?
  • autocommit: tiap statement sudah transaction; explicit transaction untuk beberapa statement?
  • SET XACT_ABORT ON + BEGIN TRY/BEGIN TRANSACTION/COMMIT?
  • CATCH: IF XACT_STATE() <> 0 (atau @@TRANCOUNT > 0) ROLLBACK lalu THROW;?
  • EF Core: satu SaveChanges = satu transaction; BeginTransactionAsync untuk beberapa SaveChanges, lalu CommitAsync?
  • jebakan: tanpa XACT_ABORT hanya statement gagal yang di-rollback, atau nested COMMIT hanya mengurangi @@TRANCOUNT?
