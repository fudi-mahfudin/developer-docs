Optimasi query: execution plan, SARGable, parameter sniffing, pagination, dan SQL dari EF Core

Jawaban terstruktur untuk "query ini lambat", dengan bukti dari plan dan logical reads di lab sendiri

Target lesson ini: Anda bisa menjawab "Endpoint ini lambat dan query-nya dari EF Core. Bagaimana Anda menganalisis dan memperbaikinya?" tanpa catatan: mengambil SQL dari EF Core, membaca execution plan (scan vs seek, key lookup, estimated vs actual), mengenali predikat yang tidak SARGable, menjelaskan parameter sniffing, dan memilih keyset pagination untuk halaman jauh, dengan angka yang sudah Anda lihat sendiri pada 100.000 Product.

1. Alur analisis, lalu membaca execution plan

Pewawancara ingin mendengar urutan kerja, bukan daftar trik. Urutan dari dokumentasi EF Core: temukan perintah yang lambat di log, jalankan SQL-nya di tool SQL, lalu baca execution plan-nya. [1]

  1. Ambil SQL yang sebenarnya: log EF Core atau ToQueryString (bagian 5). Sekalian cek N+1 dan tracking (0006).
  2. Jalankan dengan actual plan + SET STATISTICS IO ON di Azure Data Studio, VS Code mssql, atau SSMS.
  3. Baca plan: operator mana yang mahal, scan atau seek, Key Lookup berulang, estimated vs actual rows, warning.
  4. Perbaiki sesuai temuan: tulis ulang agar SARGable (bagian 2), index (0022), parameter sniffing (bagian 3), keyset pagination (bagian 4).
  5. Ukur lagi dengan angka yang sama: logical reads dan plan.

Execution plan menjelaskan "the sequence in which the source tables are accessed" dan "the methods used to extract data from each table". [2] Ada dua bentuk:

Estimated planActual plan
Query dijalankan?Tidak: "the T-SQL queries or batches do not execute" [3]Ya
Isiplan hasil kompilasi optimizer, tanpa angka runtime"the compiled plan plus its execution context": jumlah baris aktual, warning, waktu [4]
T-SQLSET SHOWPLAN_XML ON [5]SET STATISTICS XML ON [6]
Kapanquery yang terlalu lama/berbahaya untuk dijalankan (mis. UPDATE besar)analisis normal: lihat apa yang benar-benar terjadi

Yang dibaca di plan untuk interview:

  • Operator dan biayanya. "It's particularly important to note the costs associated with each node of the plan, and to identify how indexes are used (or not)." [1] Clustered Index Scan pada tabel besar untuk sedikit baris, atau Key Lookup yang dieksekusi ribuan kali, adalah tersangka utama (operator: 0022).
  • Estimated vs actual rows. Optimizer memilih plan dari perkiraan. Kalau perkiraannya 16.667 baris dan aktualnya 20, plan yang dipilih untuk 16.667 baris itu salah untuk 20 baris. Penyebab umum: statistik, local variable, dan parameter sniffing (bagian 3).
  • Scan tidak selalu buruk. Scan bisa paling efisien bila "the result set of the query is a high percentage of rows from the table." [7] Dan analisis plan di database kecil menyesatkan: "always make sure it contains data that is similar to your production system" [1], itu alasan lab memakai 100.000 baris.

2. SARGable: jangan bungkus kolom dengan fungsi

"The term SARGable in relational databases refers to a Search ARGumentable predicate that can use an index to speed up the execution of the query." [8] Aturannya satu: "Applying any function or computation on the column(s) in the search predicate generally makes the query non-sargable". [9] Index menyimpan nilai kolom, bukan nilai YEAR(kolom), jadi engine harus menghitung fungsinya untuk setiap baris: scan.

Non-SARGable (scan)SARGable (bisa seek)
WHERE YEAR(CreatedAt) = 2025 AND MONTH(CreatedAt) = 6WHERE CreatedAt >= '2025-06-01' AND CreatedAt < '2025-07-01'
WHERE LEFT(Name, 12) = N'Product 0001'WHERE Name LIKE N'Product 0001%' (prefix)
WHERE Price * 1.1 > 1000WHERE Price > 1000 / 1.1: "the computation is moved to the other side of the predicate" [9]
WHERE Name LIKE N'%0001' (wildcard di depan)tidak ada versi seek; butuh desain lain (mis. full-text search)
  • Bukan hanya WHERE: "SARGability applies not only to WHERE clauses, but also to JOINs, HAVING, GROUP BY and ORDER BY clauses." Penyebab yang paling sering: CONVERT(), CAST(), ISNULL(), COALESCE() pada kolom. [9] Microsoft juga menulis di best practice stored procedure: "Avoid wrapping functions around columns specified in the WHERE and JOIN clauses." [10]
  • Kalau fungsi tidak bisa dihindari: buat computed column dengan ekspresi yang sama lalu index kolom itu. [9]
  • Konversi tersembunyi: parameter nvarchar terhadap kolom varchar membuat SQL Server mengonversi kolomnya (CONVERT_IMPLICIT, terlihat sebagai warning di plan), efeknya sama dengan fungsi. Dapper: "On SQL Server it is crucial to use the unicode when querying unicode and ANSI when querying non unicode." [11] Kolom lab bertipe nvarchar, jadi lab tidak mendemokannya.
  • Rentang tanggal: pakai half-open >= awal AND < awal-berikutnya. BETWEEN '2025-06-01' AND '2025-06-30' melewatkan baris tanggal 30 Juni yang punya jam.

Padanan Node: aturan ini sama di PostgreSQL/MySQL. Prisma where: { createdAt: { gte, lt } } menghasilkan rentang yang SARGable; masalahnya muncul saat Anda menulis raw SQL dengan fungsi pada kolom.

3. Parameter sniffing (versi ringkas)

"Parameter sensitivity, also known as parameter sniffing, refers to a process where the Database Engine sniffs the current parameter values during compilation or recompilation, and passes them to the Query Optimizer". Berlaku untuk stored procedure, query lewat sp_executesql, dan prepared query. [4] Query berparameter dari EF Core dan Dapper dikirim lewat sp_executesql, jadi ikut kena.

Biasanya ini bagus: plan dibuat sekali lalu dipakai ulang. Masalahnya muncul pada data tidak merata: "a single cached plan for a parameterized query isn't optimal for all possible incoming parameter values. This is the case with non-uniform data distributions." [12] Lab sengaja timpang: Category 1 punya 90.000 Product, Category 6 hanya 20.

Dipanggil pertamaPlan yang disimpanAkibat untuk nilai lain
@CategoryId = 6 (20 baris)Index Seek + Key LookupCategory 1: 90.000 Key Lookup, logical reads ratusan ribu
@CategoryId = 1 (90.000 baris)Clustered Index ScanCategory 6: scan seluruh tabel untuk 20 baris

Gejala khas di produksi: "kemarin cepat, hari ini lambat, padahal kodenya tidak berubah", atau lambat hanya untuk nilai tertentu. Di actual plan, properti operator SELECT memperlihatkan nilai parameter saat kompilasi dan saat eksekusi; kalau berbeda jauh, curigai sniffing.

Penanganan, masing-masing punya harga ("Each method has associated tradeoffs and drawbacks"): [9]

CaraEfekHarga
OPTION (RECOMPILE)"generate a new, temporary plan for the query and immediately discard that plan" [13]CPU kompilasi di setiap eksekusi; cocok untuk query yang tidak dipanggil ribuan kali per detik
OPTION (OPTIMIZE FOR (@p = nilai))plan dibuat untuk nilai "khas" pilihan Anda"requires a full understanding of optimal parameter values" [9]
OPTIMIZE FOR UNKNOWN / local variablememakai rata-rata selektivitas, bukan nilai yang dikirim [4]plan "rata-rata": stabil, tapi tidak terbaik untuk nilai ekstrem
Index yang lebih baik (mis. covering)tanpa Key Lookup, satu plan bagus untuk semua nilaibiaya tulis dan storage index (0022)

SQL Server 2022: Parameter Sensitive Plan (PSP) optimization "automatically enables multiple, active cached plans for a single parameterized statement", aktif di compatibility level 160 (default database baru), saat ini hanya untuk predikat equality. Fitur ini bisa menyembunyikan demo klasik, jadi skrip lab mematikannya sementara dengan ALTER DATABASE SCOPED CONFIGURATION SET PARAMETER_SENSITIVE_PLAN_OPTIMIZATION = OFF lalu menyalakannya lagi. [12] Untuk interview, cukup sebut bahwa fitur ini ada; jawaban utamanya tetap mekanisme dan cara penanganan di atas.

4. Pagination: OFFSET/FETCH vs keyset

-- OFFSET/FETCH (EF Core: .Skip(90000).Take(20))
SELECT Id, Name, Price FROM dbo.Product
ORDER BY Id
OFFSET 90000 ROWS FETCH NEXT 20 ROWS ONLY;

-- Keyset / seek (EF Core: .Where(p => p.Id > lastId).Take(20))
SELECT TOP (20) Id, Name, Price FROM dbo.Product
WHERE Id > @lastId
ORDER BY Id;
  • OFFSET "Specifies the number of rows to skip before the query starts to return rows" [14], tapi melewati bukan berarti gratis: "The database must still process the first 20 entries, even if they aren't returned to the application; this creates possibly significant computation load that increases with the number of rows being skipped." Kalau data berubah di antara dua halaman, baris bisa terlewat atau tampil dua kali. [15]
  • Keyset: "simply use a WHERE clause to skip rows, instead of an offset." Dengan index pada kolom urutannya, query ini "very efficient" dan tidak terpengaruh perubahan di baris sebelumnya. Batasannya: tidak bisa lompat ke halaman tertentu ("does not support random access"), hanya maju/mundur. [15]
  • Urutan harus unik, apa pun metodenya: "relational databases do not apply any ordering by default, even on the primary key." Urut menurut kolom yang bisa kembar (Price, CreatedAt)? Tambahkan Id sebagai pemecah seri, dan buat composite index yang cocok. [15]
  • Keyset dua kolom ditulis dengan OR, karena perbandingan (A, B) > (x, y) tidak didukung EF Core LINQ (dan tidak ada di T-SQL): WHERE A > @x OR (A = @x AND B > @y). [15]
// EF Core, sampel resmi: urut Date lalu PostId, keyset dua kunci
var nextPage = await context.Posts
    .OrderBy(b => b.Date).ThenBy(b => b.PostId)
    .Where(b => b.Date > lastDate || (b.Date == lastDate && b.PostId > lastId))
    .Take(10)
    .ToListAsync();

Kapan OFFSET tetap wajar: tabel kecil, admin panel dengan nomor halaman, halaman awal saja. Kapan keyset: infinite scroll, API "next cursor", export besar. Padanan Node: Prisma skip/take (offset) vs cursor + take (keyset).

5. Melihat SQL yang dihasilkan EF Core

protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    => optionsBuilder
        .UseSqlServer(connectionString)
        .LogTo(Console.WriteLine, LogLevel.Information)   // setiap perintah SQL + durasinya
        .EnableSensitiveDataLogging();                    // nilai parameter ikut tampil: HANYA development

var query = db.Products
    .Where(p => p.CategoryId == categoryId)
    .OrderBy(p => p.Price)
    .TagWith("Products by category");                    // komentar di SQL, mudah dicari di log

Console.WriteLine(query.ToQueryString());               // SQL-nya, TANPA mengeksekusi query
var products = await query.ToListAsync();
  • Simple logging (LogTo) "requires minimal configuration and no additional NuGet packages"; di level Information log berisi akses database. [16] Setiap perintah dicatat dengan durasinya, mis. Executed DbCommand (4ms) [Parameters=[...]] lalu SQL-nya, jadi query lambat langsung terlihat. Tapi: "Leaving command execution logging enabled in your production environment is usually a bad idea." [1] (Di ASP.NET Core, log yang sama keluar lewat ILogger dengan kategori Microsoft.EntityFrameworkCore.Database.Command.)
  • Nilai parameter tidak ikut tampil di log maupun pesan exception secara default (di log muncul sebagai @p0='?'). EnableSensitiveDataLogging "Enables application data to be included in exception messages, logging, etc. This can include ... parameter values for commands being sent to the database"; aktifkan "only ... if you have the appropriate security measures in place". [17]
  • ToQueryString() (EF Core 5+): "Generates a string representation of the query used. This string may not be suitable for direct execution and is intended only for use in debugging." [18] Hasilnya berupa DECLARE parameter diikuti SELECT ... WHERE [p].[CategoryId] = @__categoryId_0 (nama parameter tergantung versi). Salin ke Azure Data Studio, jalankan dengan actual plan: kembali ke langkah 2 di bagian 1.
  • TagWith "allows you to inject a small, identifying comment into the SQL query", supaya SQL di log atau di monitoring server bisa dikaitkan ke kode LINQ-nya. [1]

Hubungkan ke bagian sebelumnya: Skip/Take diterjemahkan menjadi OFFSET/FETCH; Where(p => p.CreatedAt.Year == 2025) menjadi DATEPART(year, ...) pada kolom (non-SARGable, bandingkan dengan rentang tanggal); query berparameter EF Core kena parameter sniffing. N+1 dan AsNoTracking: lesson 0006. Padanan Node: LogTo ≈ Prisma log: ['query'] atau knex debug; ToQueryString ≈ knex .toString() / .toSQL().

DECLARE @c int = 6;

-- 2. SARGable vs non-SARGable ---------------------------------------------------------------
-- 2a. UQ_Product_Name (dari setup) berisi Name + Id, jadi kedua query ini dijawab dari index itu saja.
-- Fungsi pada kolom: engine harus menghitung LEFT() untuk setiap baris -> Index Scan seluruh index.
SELECT Id, Name FROM dbo.Product WHERE LEFT(Name, 12) = N'Product 0001';

-- Hasil sama (100 baris: Product 000100..000199), tapi LIKE dengan prefix tetap bisa dicari di index -> Index Seek, reads jauh lebih kecil.
SELECT Id, Name FROM dbo.Product WHERE Name LIKE N'Product 0001%';

-- Wildcard di depan tidak punya titik awal di index -> kembali scan (10 baris, tetap membaca seluruh index).
SELECT Id, Name FROM dbo.Product WHERE Name LIKE N'%0001';
GO

-- 2b. Tanggal. Index pada CreatedAt; Id ikut otomatis, jadi SELECT Id, CreatedAt tetap covering.
CREATE INDEX IX_Product_CreatedAt ON dbo.Product (CreatedAt);
GO

-- Non-SARGable: YEAR() dan MONTH() membungkus kolom -> Index Scan seluruh IX_Product_CreatedAt.
SELECT Id, CreatedAt FROM dbo.Product WHERE YEAR(CreatedAt) = 2025 AND MONTH(CreatedAt) = 6;

-- SARGable: kolom dibiarkan polos, rentang half-open [1 Juni, 1 Juli) -> Index Seek, hasil sama (3.323 baris menurut rumus seed).
SELECT Id, CreatedAt FROM dbo.Product WHERE CreatedAt >= '2025-06-01' AND CreatedAt < '2025-07-01';
GO

-- Category 1 = 90.000 Product, Category 6 = 20 Product (setup). Satu plan tidak cocok untuk keduanya.
CREATE OR ALTER PROCEDURE dbo.usp_ProductsByCategory @CategoryId int
AS

GO

EXEC dbo.usp_ProductsByCategory @CategoryId = 1;

EXEC dbo.usp_ProductsByCategory @CategoryId = 1;   -- scan: wajar untuk 90% tabel

-- 3c. Dua perbaikan.
-- Perbaikan 1: OPTION (RECOMPILE) -> plan baru setiap eksekusi, dibuang setelahnya. Bayarannya CPU kompilasi tiap panggilan.
CREATE OR ALTER PROCEDURE dbo.usp_ProductsByCategory_Recompile @CategoryId int
AS
    SELECT Id, Name, Price FROM dbo.Product WHERE CategoryId = @CategoryId
    OPTION (RECOMPILE);
GO
EXEC dbo.usp_ProductsByCategory_Recompile @CategoryId = 6;   -- Index Seek + Key Lookup
EXEC dbo.usp_ProductsByCategory_Recompile @CategoryId = 1;   -- Clustered Index Scan
GO
-- Alternatif lain (tidak dijalankan): OPTION (OPTIMIZE FOR (@CategoryId = 1)) memakai nilai "khas" yang Anda pilih;
-- OPTION (OPTIMIZE FOR UNKNOWN) memakai rata-rata, sama seperti local variable di 1c.

-- Perbaikan 2 (akar masalah): covering index. Tidak ada Key Lookup, jadi Index Seek bagus untuk 20 MAUPUN 90.000 baris
-- dan plan yang disimpan aman untuk semua nilai.
DROP INDEX IF EXISTS IX_Product_CategoryId ON dbo.Product;
CREATE INDEX IX_Product_CategoryId_Covering ON dbo.Product (CategoryId) INCLUDE (Name, Price);
GO
EXEC sp_recompile N'dbo.usp_ProductsByCategory';
GO
EXEC dbo.usp_ProductsByCategory @CategoryId = 6;   -- Index Seek, beberapa reads
EXEC dbo.usp_ProductsByCategory @CategoryId = 1;   -- Index Seek yang sama, reads sebanding scan, tanpa lookup
GO

DROP INDEX IF EXISTS IX_Product_CategoryId_Covering ON dbo.Product;
CREATE INDEX IX_Product_CategoryId ON dbo.Product (CategoryId);
ALTER DATABASE SCOPED CONFIGURATION SET PARAMETER_SENSITIVE_PLAN_OPTIMIZATION = ON;

GO

EXEC dbo.usp_ProductsByCategory @CategoryId = 6;

GO

-- 4. Pagination: OFFSET/FETCH vs keyset -----------------------------------------------------
-- 4a. Urut Id. Halaman ke-4.501 (20 per halaman): OFFSET harus membaca dan membuang 90.000 baris dulu.
SELECT Id, Name, Price FROM dbo.Product
ORDER BY Id
OFFSET 90000 ROWS FETCH NEXT 20 ROWS ONLY;     -- logical reads: ratusan (hampir seluruh tabel)

-- Keyset: aplikasi mengingat Id terakhir halaman sebelumnya, lalu Index Seek langsung ke sana.
DECLARE @lastId int = 90000;
SELECT TOP (20) Id, Name, Price FROM dbo.Product
WHERE Id > @lastId
ORDER BY Id;                                   -- logical reads: hitungan jari, hasil sama persis
GO

-- 4b. Urutan yang lebih realistis: Product terbaru dulu (CreatedAt DESC), Id sebagai pemecah seri supaya urutan unik.
-- IX_Product_CreatedAt (dari bagian 2) secara efektif berisi (CreatedAt, Id), cocok dengan urutan ini.
SELECT Id, Name, CreatedAt FROM dbo.Product
ORDER BY CreatedAt DESC, Id DESC
OFFSET 90000 ROWS FETCH NEXT 20 ROWS ONLY;     -- scan + sort, atau 90.000 lookup: mahal
GO

-- Nilai kunci baris terakhir halaman sebelumnya. Di aplikasi nilainya datang dari halaman yang baru ditampilkan;
-- di sini diambil dengan OFFSET supaya hasilnya bisa dibandingkan, jadi STATISTICS IO dimatikan sebentar.
SET STATISTICS IO OFF;
DECLARE @lastCreatedAt datetime2(0), @lastId int;
SELECT @lastCreatedAt = CreatedAt, @lastId = Id FROM dbo.Product
ORDER BY CreatedAt DESC, Id DESC
OFFSET 89999 ROWS FETCH NEXT 1 ROWS ONLY;
SET STATISTICS IO ON;

-- Keyset dua kunci. T-SQL tidak punya (CreatedAt, Id) < (@a, @b), jadi ditulis dengan OR.
-- Syarat pertama (CreatedAt <= ...) memberi rentang seek; sisanya membuang baris seri yang sudah tampil.
-- Hasilnya harus sama dengan query OFFSET di atas, dengan Index Seek + 20 Key Lookup saja.
SELECT TOP (20) Id, Name, CreatedAt FROM dbo.Product
WHERE CreatedAt <= @lastCreatedAt
  AND (CreatedAt < @lastCreatedAt OR Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
GO

SET STATISTICS IO OFF;
GO

DROP PROCEDURE IF EXISTS dbo.usp_ProductsByCategory;
DROP PROCEDURE IF EXISTS dbo.usp_ProductsByCategory_Recompile;

7. Latihan tulis query

Tulis sendiri di editor SQL, jalankan di lab, baru buka jawaban. Tidak dinilai otomatis; bandingkan hasil, plan, dan logical reads.

A. Laporan "Product baru per bulan" menjalankan SELECT Id, CreatedAt FROM dbo.Product WHERE CONVERT(char(7), CreatedAt, 120) = '2025-03'; Buat IX_Product_CreatedAt (CreatedAt), tulis ulang query ini supaya SARGable, buktikan jumlah barisnya sama dan plan-nya berubah dari Index Scan menjadi Index Seek, lalu hapus index-nya.

Lihat jawaban 
CREATE INDEX IX_Product_CreatedAt ON dbo.Product (CreatedAt);
SET STATISTICS IO ON;

-- Sebelum: CONVERT membungkus kolom -> Index Scan seluruh IX_Product_CreatedAt
SELECT Id, CreatedAt FROM dbo.Product WHERE CONVERT(char(7), CreatedAt, 120) = '2025-03';

-- Sesudah: kolom polos, rentang half-open -> Index Seek
SELECT Id, CreatedAt FROM dbo.Product
WHERE CreatedAt >= '2025-03-01' AND CreatedAt < '2025-04-01';

-- Bukti jumlah sama
SELECT
    (SELECT COUNT(*) FROM dbo.Product WHERE CONVERT(char(7), CreatedAt, 120) = '2025-03') AS Lama,
    (SELECT COUNT(*) FROM dbo.Product WHERE CreatedAt >= '2025-03-01' AND CreatedAt < '2025-04-01') AS Baru;

SET STATISTICS IO OFF;
DROP INDEX IF EXISTS IX_Product_CreatedAt ON dbo.Product;

Kedua versi menghasilkan 3.434 baris (menurut rumus seed). Kenapa tidak BETWEEN '2025-03-01' AND '2025-03-31'? '2025-03-31' berarti 31 Maret pukul 00:00:00, jadi Product yang dibuat siang hari tanggal 31 terlewat. Rentang half-open < '2025-04-01' benar untuk tipe tanggal apa pun. Di EF Core bentuk yang sama: .Where(p => p.CreatedAt >= from && p.CreatedAt < to), bukan p.CreatedAt.Month == 3.

B. Halaman katalog diurutkan menurut harga termurah (ORDER BY Price, Id), 20 per halaman, dan sekarang memakai OFFSET. Tulis (1) index yang mendukung urutan ini dan (2) query keyset untuk "halaman berikutnya" jika baris terakhir halaman sebelumnya punya Price = @lastPrice dan Id = @lastId. Uji dengan nilai baris ke-20 halaman pertama, lalu bandingkan hasilnya dengan OFFSET 20 ROWS FETCH NEXT 20 ROWS ONLY. Hapus index setelahnya.

Lihat jawaban 
-- (1) Price di key; Id otomatis ikut sebagai key terakhir (clustered key), Name di INCLUDE -> covering
CREATE INDEX IX_Product_Price ON dbo.Product (Price) INCLUDE (Name);
GO

-- Nilai baris terakhir halaman pertama (di aplikasi: dari halaman yang baru ditampilkan)
DECLARE @lastPrice decimal(18, 2), @lastId int;
SELECT @lastPrice = Price, @lastId = Id FROM dbo.Product
ORDER BY Price, Id
OFFSET 19 ROWS FETCH NEXT 1 ROWS ONLY;

-- (2) Keyset: halaman berikutnya
SELECT TOP (20) Id, Name, Price FROM dbo.Product
WHERE Price > @lastPrice OR (Price = @lastPrice AND Id > @lastId)
ORDER BY Price, Id;

-- Pembanding: harus 20 baris yang sama
SELECT Id, Name, Price FROM dbo.Product
ORDER BY Price, Id
OFFSET 20 ROWS FETCH NEXT 20 ROWS ONLY;
GO

DROP INDEX IF EXISTS IX_Product_Price ON dbo.Product;

Id wajib ada di ORDER BY dan di kondisi keyset supaya urutan unik: tanpa itu, dua Product berharga sama bisa terlewat atau tampil dua kali antar halaman. Index (Price) pada tabel ber-clustered key Id sudah diurutkan (Price, Id), jadi keyset menjadi Index Seek + Top tanpa Sort. Kalau optimizer tidak memakai seek untuk bentuk OR, tulis setara: WHERE Price >= @lastPrice AND (Price > @lastPrice OR Id > @lastId) (bentuk yang dipakai bagian 4b skrip). EF Core: .OrderBy(p => p.Price).ThenBy(p => p.Id).Where(p => p.Price > lastPrice || (p.Price == lastPrice && p.Id > lastId)).Take(20).

Latihan 6 — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Endpoint daftar Product tiba-tiba lambat. Query-nya dari EF Core. Bagaimana Anda menganalisis dan memperbaikinya?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Pertama saya ambil SQL-nya: log EF Core di level Information menampilkan setiap perintah beserta durasinya, atau ToQueryString untuk satu query. Sekalian saya cek sisi aplikasi: N+1, tracking yang tidak perlu, kolom berlebih. Lalu SQL itu saya jalankan di Azure Data Studio dengan actual execution plan dan SET STATISTICS IO ON. Di plan saya cari Clustered Index Scan pada tabel besar, Key Lookup yang dieksekusi ribuan kali, dan selisih besar estimated vs actual rows. Kalau ada fungsi di kolom WHERE, misalnya YEAR(CreatedAt), saya tulis ulang jadi rentang supaya SARGable. Kalau index-nya kurang, saya buat composite atau covering index. Kalau lambatnya hanya untuk nilai parameter tertentu, saya curigai parameter sniffing. Kalau halaman jauh yang lambat, saya ganti OFFSET dengan keyset pagination. Terakhir saya ukur lagi: logical reads harus turun dan plan berubah."

Checklist: apakah Anda menyebut…

  • ambil SQL yang sebenarnya: logging EF Core (durasi per perintah) atau ToQueryString?
  • cek sisi aplikasi dulu: N+1, AsNoTracking, projection (lesson 0006)?
  • jalankan dengan actual execution plan + SET STATISTICS IO (logical reads)?
  • baca plan: scan vs seek, Key Lookup berulang, estimated vs actual rows?
  • perbaikan sesuai temuan: SARGable, index covering/composite, parameter sniffing, keyset pagination?
  • ukur lagi sesudah perbaikan dan bandingkan dengan angka sebelumnya?

Lulus kalau minimal 4 dari 6.

"Apa itu parameter sniffing, kapan jadi masalah, dan bagaimana menanganinya?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Saat query berparameter atau stored procedure pertama kali dikompilasi, SQL Server mengintip nilai parameter saat itu dan membuat plan untuk nilai tersebut, lalu plan itu disimpan dan dipakai ulang. Itu biasanya bagus. Masalahnya muncul kalau datanya tidak merata: di lab saya, Category 6 punya 20 Product dan Category 1 punya 90.000. Kalau 6 dipanggil duluan, plan Index Seek + Key Lookup disimpan, lalu Category 1 menjalankan 90.000 key lookup. EF Core dan Dapper juga kena karena mengirim query berparameter lewat sp_executesql. Penanganannya: OPTION (RECOMPILE) dengan harga CPU kompilasi, OPTIMIZE FOR nilai yang khas, atau memperbaiki akarnya dengan covering index supaya satu plan bagus untuk semua nilai. Di SQL Server 2022 ada PSP optimization yang bisa menyimpan beberapa plan per query."

Checklist: apakah Anda menyebut…

  • plan dikompilasi untuk nilai parameter pertama, lalu disimpan dan dipakai ulang?
  • jadi masalah kalau distribusi data tidak merata (contoh 20 vs 90.000 baris)?
  • berlaku untuk stored procedure dan query berparameter (sp_executesql dari EF Core/Dapper)?
  • OPTION (RECOMPILE): plan per eksekusi, bayar CPU kompilasi?
  • OPTIMIZE FOR / OPTIMIZE FOR UNKNOWN, atau perbaiki akar dengan covering index?
  • SQL Server 2022: PSP optimization menyimpan beberapa plan per query?

Lulus kalau minimal 4 dari 6. Review 0024 akan menanyakan salah satunya lagi.
