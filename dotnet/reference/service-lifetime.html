Kenapa DbContext Scoped [4]

  • DbContext = satu unit of work yang pendek. Di web app: satu request = satu unit of work.
  • AddDbContext mendaftarkannya Scoped secara default.
  • Satu request: Service dan Repository berbagi DbContext dan change tracker yang sama.
  • Antar request: instance terpisah, karena DbContext tidak thread-safe.

Captive dependency [2]

builder.Services.AddDbContext<AppDbContext>(...);   // Scoped
builder.Services.AddSingleton<PriceCache>();
public class PriceCache(AppDbContext db) { }        // ✗ DbContext ikut hidup selamanya
// Development: InvalidOperationException
//   "Cannot consume scoped service 'AppDbContext' from singleton 'PriceCache'."

Deteksi dan perbaikan [3]

  • Scope validation aktif default di Development: Scoped tidak boleh di-resolve dari root provider atau di-inject ke Singleton.
  • Selalu aktif: builder.Host.UseDefaultServiceProvider(o => o.ValidateScopes = true);
  • Perbaikan 1: turunkan lifetime konsumen (Singleton → Scoped).
  • Perbaikan 2: inject IServiceScopeFactory, lalu using var scope = f.CreateScope(); dan ambil service dari scope.ServiceProvider (juga untuk BackgroundService).
  • Beda NestJS: request scope "bubbles up" otomatis. .NET tidak; ia melempar exception.

Jawaban 60–90 detik

Transient: baru setiap diminta. Scoped: satu per request, di-dispose di akhir request; contoh DbContext karena satu request satu unit of work. Singleton: satu seumur aplikasi, harus thread-safe. Captive dependency: service berumur panjang memegang dependensi berumur lebih pendek (Singleton + DbContext), sehingga state bocor antar request dan DbContext dipakai paralel. Scope validation di Development melempar exception; perbaiki dengan menurunkan lifetime atau IServiceScopeFactory.
