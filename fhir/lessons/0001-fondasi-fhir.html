Fondasi FHIR: dari HL7 v2 ke Resource, R4, dan Profile

Pertanyaan pembuka yang hampir pasti muncul, dijelaskan dengan bahasa developer JavaScript

Target lesson ini: Anda bisa menjawab "Apa itu FHIR, dan apa bedanya dengan HL7 v2? Kenapa kami memakai R4, dan apa itu profile?" tanpa catatan, dalam kurang dari satu menit per bagian: Resource sebagai unit modular ber-URL, REST + JSON di atas standar web, arti label Normative dan FMM, serta kenapa FHIR "dasar" selalu disesuaikan lewat Profile, Extension, dan Implementation Guide.

Semua fakta di bawah diambil dari spesifikasi FHIR R4 (v4.0.1) dan dikutip [n]. Contoh JSON dan TypeScript hanya untuk dibaca, tidak perlu dijalankan. REST, HTTP status, JSON, dan OAuth sudah Anda kuasai; lesson ini hanya mengajarkan yang khas FHIR.

1. Dari HL7 v2 ke FHIR

FHIR (Fast Healthcare Interoperability Resources) adalah "a next generation standards framework created by HL7" yang menggabungkan "the best features of HL7's" v2, v3, dan CDA. [1] Untuk interview, pembandingnya hampir selalu HL7 v2: standar pesan lama yang masih banyak berjalan di rumah sakit. 

MSH|^~\&|LAB|RSUD|EHR|RSUD|202410261030||ORU^R01|MSG0001|P|2.5
PID|1||RM-00123^^^RSUD^MR||Santoso^Budi||19800512|M
OBX|1|NM|2339-0^Glucose^LN||95|mg/dL|70-99|N|||F

Ilustrasi pesan v2 yang disederhanakan (bukan dikutip dari spesifikasi): satu pesan, baris = segment, field dipisah |, komponen dipisah ^, seperti contoh |^Smith^John| di halaman perbandingan v2. [3]

HL7 v2FHIR
Unitpesan dari "re-usable segments"; "segments can't be independently manipulated"Resource: "All exchangeable content is defined as a resource" [2], masing-masing punya URL sendiri
Variasi"One of the biggest challenges with HL7 v2 interoperability is the variation of implementation"core kecil, variasi dikelola eksplisit lewat profile (bagian 5)
Data lokalZ-segment: maknanya "opaque without prior manual explanation by the sender"extension: "can appear at any level (including within data types)", punya URL definisi
Updatebisa kirim sebagian + kode penghapusan"requiring all data to be present as a snapshot"
Teks manusiatidak wajib"FHIR requires human readable content to be provided for each resource"

Kutipan kolom HL7 v2 dan baris extension/update/teks: [3]. Keduanya tidak saling meniadakan: FHIR menyebut "Evolutionary development path from HL7 Version 2 and CDA: standards can co-exist and leverage each other". [1] Di interview, sebut bahwa integrasi nyata sering memetakan pesan v2 lama ke resource FHIR (dibahas di lesson 0006).

2. Kenapa REST + JSON: fondasi yang sudah Anda kuasai

FHIR berdiri di atas "Web standards: XML, JSON, HTTP, OAuth, etc." dan mendukung "RESTful architectures". [1] Halaman REST API-nya berstatus Normative dan menyebut FHIR "a 'RESTful' specification based on common industry level use of the term REST", dengan pola URL VERB [base]/[type]/[id]. [4] Jadi bagi developer Node, membaca satu pasien adalah fetch biasa: 

// base = "https://fhir.contoh-rs.id/fhir" (contoh fiktif)
const res = await fetch(`${base}/Patient/123`, {
  headers: { Accept: "application/fhir+json" },
});
const patient = await res.json(); // { resourceType: "Patient", id: "123", ... }
  • MIME type JSON-nya: "The MIME-type for this format is application/fhir+json." [5]
  • Setiap resource adalah objek JSON "with a property resourceType which informs the parser which resource type this is". [5]
  • REST bukan satu-satunya jalan: "you do not have to use REST to make use of resources" (ada juga dokumen dan messaging). [2] Detail interaksi REST, search, dan Bundle ada di lesson 0003.

Padanan TypeScript yang paling membantu: resourceType adalah discriminant dari union type, persis seperti field type di reducer Redux. 

type Meta = { versionId?: string; lastUpdated?: string; profile?: string[] };
interface Resource { resourceType: string; id?: string; meta?: Meta }
interface Patient extends Resource { resourceType: "Patient"; birthDate?: string }
interface Observation extends Resource { resourceType: "Observation"; status: string }

function label(r: Patient | Observation): string {
  switch (r.resourceType) {            // TypeScript mempersempit tipe di tiap case
    case "Patient": return `Pasien, lahir ${r.birthDate ?? "?"}`;
    case "Observation": return `Observasi (${r.status})`;
  }
}

Tipe di atas sengaja diringkas. Kardinalitas aslinya: Patient.birthDate 0..1 [16], Observation.status 1..1 [17].

Latihan 2 — REST + JSON

3. Resource: definisi, kategori, dan bedanya dengan datatype

"The basic building block in FHIR is a Resource." [2] Menurut spesifikasi, sebuah resource adalah entitas yang: [6]

  • "has a known identity (a URL) by which it can be addressed" → [base]/Patient/123;
  • "identifies itself as one of the types of resource defined in this specification" → resourceType;
  • "has an identified version that changes if the contents of the resource change" → meta.versionId.
{
  "resourceType": "Patient",
  "id": "123",
  "meta": { "versionId": "2", "lastUpdated": "2024-10-26T10:30:00Z" },
  "identifier": [{ "system": "https://rs.contoh.id/no-rm", "value": "RM-00123" }],
  "name": [{ "family": "Santoso", "given": ["Budi"] }],
  "gender": "male",
  "birthDate": "1980-05-12"
}

Semua resource boleh punya id ("the 'logical id' of the resource"), meta, implicitRules, dan language. meta.versionId "Changes each time the content of the resource changes", dan meta.profile adalah "An assertion that the content conforms to a resource profile". [6] "Most resources are derived from DomainResource", sehingga juga bisa memuat text, resource contained, dan extension. [6] Bedakan id (alamat di server ini) dari identifier (nomor bisnis seperti nomor rekam medis); detailnya di lesson 0002.

Kategori

Resource vs datatype

Datatype adalah tipe untuk elemen di dalam resource: tipe primitif ("single elements with a primitive value", mis. string, boolean, decimal, dateTime) dan tipe kompleks ("re-usable clusters of elements", mis. Identifier, HumanName, CodeableConcept, Quantity, Period). [8] Berbeda dengan resource, datatype tidak punya identitas URL atau versi sendiri: ia selalu hidup di dalam sebuah resource. Kalau satu resource butuh resource lain, ia memakai datatype Reference: "resources are identified and addressed by their URL". [9] Padanan TypeScript: resource ≈ entity/aggregate dengan endpoint sendiri; datatype ≈ value object (type Address = {...}) yang di-embed.

Latihan 3 — Resource

4. R4 vs R5, Normative, dan maturity (FMM)

Versi FHIR ditulis "publication.major.minor.revision"; yang dipakai track ini adalah "FHIR Release 4 (Technical Correction #1) (v4.0.1)". [10] Setiap artefak (resource, halaman, profile) punya status:

StatusArtinya
Normative (tanda N)"The content is considered to be stable and has been 'locked', subjecting it to FHIR Inter-version Compatibility Rules." Forward compatibility: "content that is conformant in an old release will remain conformant with future versions."
Trial Use"considered by the authors to be ready for use in production systems", tetapi "Future versions of FHIR may make significant changes to Trial Use content".
FMM 0–5tingkat kematangan konten Trial Use. FMM 0: baru di build. FMM 2: diuji interoperabilitasnya oleh "at least three independently developed systems". FMM 5: "implemented in at least 5 independent production systems in more than one country".

Semua kutipan tabel: [10]. Backward compatibility (instance versi baru dibaca sistem lama) "is not guaranteed by FHIR".

  • R4 (4.0.0, 27 Des 2018): "First Normative content". [11] Normative di R4 antara lain REST API [4], format JSON [5], Patient [16], Observation [17], Bundle, dan StructureDefinition. Encounter belum: FMM 2. [7] Koreksi teknis 4.0.1: Okt 2019. [18]
  • R5 (5.0.0, 26 Mar 2023) berstatus trial use: "None of the content in this specification is considered 'Normative'"; konten yang sudah normative di R4 tetap berlabel Normative. Perubahan yang dicatat antara lain "Complete Rework Subscriptions framework", resource baru, dan rename seperti DeviceUseStatement → DeviceUsage. HL7 "plans to publish the next release as a normative specification." [12]
  • IG besar dibangun di atas R4, misalnya: "The US Core Implementation Guide is based on FHIR Version R4." [13]

Kalimat "R4 adalah versi paling dominan di produksi" adalah pengamatan industri, bukan kalimat spesifikasi. Di interview, dukung dengan fakta di atas: R4 rilis normative pertama, R5 trial use, dan IG utama (termasuk yang dipakai regulator) masih di R4. Posisi SATUSEHAT dibahas di lesson 0006.

Latihan 4 — Versi dan maturity

5. Profile, Extension, dan Implementation Guide (konsep)

Spesifikasi dasar FHIR sengaja menjadi "a common platform or foundation on which a variety of different solutions are implemented", dan karena itu "usually requires further adaptation to particular contexts of use". [14] Filosofinya: resource dasar memenuhi "the majority of common use cases", dan "There is a built-in extension mechanism to cover the remaining content". [2]

Profile

"A set of constraints on a resource represented as a structure definition", ditulis sebagai resource StructureDefinition. [14] Profile bisa: mengubah kardinalitas ("One key function of profiles"), melarang elemen dengan max 0, memaku nilai tetap, membatasi tipe, mengikat ke value set terminologi lain, dan menandai elemen yang "must be 'supported'". [14] Must support berarti implementasi "SHALL provide 'support' for the element in some meaningful way". [15]

Contoh konkret: di Patient dasar, identifier dan name berkardinalitas 0..* [16]; profile US Core Patient (http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient) mempersempitnya menjadi 1..*. [19] Resource bisa menyatakan kesesuaiannya di meta.profile.

Extension

{
  "resourceType": "Patient",
  "id": "123",
  "extension": [{
    "url": "http://hl7.org/fhir/StructureDefinition/patient-birthPlace",
    "valueAddress": { "city": "Bandung", "country": "ID" }
  }]
}
  • url wajib dan "identifies a retrievable extension definition"; ia harus "the canonical URL of a StructureDefinition that defines the extension". [20] URL di contoh adalah extension resmi untuk tempat lahir dengan tipe Address. [21]
  • Isinya value[x]: nama "value" + nama tipe dalam TitleCase (valueAddress, valueCode, valueString), atau sub-extension, "but not both". [20]
  • modifierExtension dipakai "If it is not safe for an application processing the content of the resource to ignore the extension". Aplikasi yang tidak mengenalnya tidak boleh diam-diam mengabaikannya. [20]
  • Kenapa tidak menambah properti sembarang ke JSON: "The use of extensions is what allows the FHIR specification to retain a core simplicity for everyone." [20]

Padanan TypeScript untuk membaca extension: cari berdasarkan url, jangan berdasarkan posisi array.

const BIRTH_PLACE = "http://hl7.org/fhir/StructureDefinition/patient-birthPlace";
const birthPlace = patient.extension?.find(e => e.url === BIRTH_PLACE)?.valueAddress;

Implementation Guide (IG)

"A coherent and bounded set of adaptations that are published as a single unit" [14]: profile, extension, value set, dan contoh untuk satu negara, organisasi, atau use case. US Core "defines the minimum constraints on the FHIR resources to create the US Core Profiles". [13] Resource ImplementationGuide sendiri ("A set of rules of how a particular interoperability or standards problem is solved") masih Trial Use, FMM 1. [22]

6. Server yang mungkin disebut di interview

Cukup kenali namanya; menjalankannya di luar cakupan track ini.

Latihan 6 — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Apa itu FHIR, dan apa bedanya dengan HL7 v2?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"FHIR, Fast Healthcare Interoperability Resources, adalah standar HL7 untuk pertukaran data kesehatan yang dibangun dari komponen modular bernama Resource, misalnya Patient, Encounter, Observation. Setiap resource punya identitas URL, versi, dan bisa dibaca atau diubah sendiri lewat REST API, dengan format JSON (application/fhir+json) atau XML, di atas standar web yang sudah kita kenal: HTTP, JSON, OAuth. HL7 v2 adalah standar pesan yang lebih tua: pesan terdiri dari segment teks berdelimiter, segment tidak bisa dimanipulasi sendiri, dan implementasinya sangat bervariasi antar sistem; data lokal masuk Z-segment yang maknanya harus dijelaskan manual. Di FHIR, data lokal masuk extension yang punya URL ke definisinya, dan variasi dikelola lewat profile dan Implementation Guide. Keduanya bisa hidup berdampingan; banyak integrasi memetakan v2 ke FHIR."

Checklist: apakah Anda menyebut…

  • FHIR = standar HL7, dibangun dari Resource modular (contoh: Patient, Observation)?
  • Resource punya identitas URL dan versi, bisa dibaca/diubah sendiri?
  • REST API + JSON/XML di atas standar web (HTTP, OAuth)?
  • HL7 v2 = pesan dari segment, segment tidak bisa dimanipulasi sendiri?
  • masalah v2: variasi implementasi tinggi; Z-segment maknanya tidak jelas tanpa penjelasan manual?
  • padanan di FHIR: extension ber-URL + profile/IG; v2 dan FHIR bisa berdampingan?

Lulus kalau minimal 4 dari 6.

"Kenapa FHIR 'dasar' tidak langsung cukup untuk sebuah negara atau organisasi? Jelaskan Profile, Extension, dan Implementation Guide." (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Spesifikasi dasar FHIR sengaja menjadi platform bersama: resource-nya hanya memuat elemen yang akan didukung kebanyakan sistem, jadi spesifikasi menyatakan bahwa ia biasanya perlu diadaptasi ke konteks pemakaian. Adaptasi itu ditulis sebagai profile, yaitu StructureDefinition berisi constraint: misalnya identifier pasien wajib (kardinalitas 1..*), elemen tertentu dilarang (max 0), kode harus dari value set tertentu, atau elemen ditandai must support. Kebutuhan yang tidak ada di core ditambahkan sebagai extension: objek dengan url ke definisinya plus value[x]; kalau extension itu mengubah makna data, ia harus menjadi modifierExtension yang tidak boleh diabaikan. Sekumpulan profile, extension, dan terminologi untuk satu konteks diterbitkan sebagai Implementation Guide, misalnya US Core di Amerika yang dibangun di atas R4. Resource bisa menyatakan kesesuaiannya lewat meta.profile. Analogi TypeScript: resource dasar adalah type yang longgar, profile adalah type yang lebih ketat plus aturan validasi, dan IG adalah package berisi kumpulan type itu."

Checklist: apakah Anda menyebut…

  • spesifikasi dasar = platform bersama dengan core kecil, biasanya perlu diadaptasi ke konteks?
  • profile = StructureDefinition berisi constraint (kardinalitas, max 0, binding terminologi, must support)?
  • extension = url ke definisi + value[x]; menambah data yang tidak ada di core?
  • modifierExtension mengubah makna, tidak boleh diabaikan diam-diam?
  • Implementation Guide = kumpulan adaptasi yang diterbitkan sebagai satu unit (contoh US Core di atas R4)?
  • meta.profile untuk menyatakan kesesuaian; analogi TS: type lebih ketat / package type?

Lulus kalau minimal 4 dari 6.

"Kami memakai FHIR R4. Kenapa bukan R5? Dan apa arti label Normative dan FMM yang Anda lihat di spesifikasi?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"R4, versi 4.0.1, adalah rilis pertama yang memuat konten normative, terbit akhir 2018. Normative berarti konten itu stabil dan dikunci: tunduk pada aturan kompatibilitas antarversi, jadi data yang valid di R4 tetap valid di versi berikutnya. Bagian penting seperti REST API, format JSON, Patient, dan Observation sudah normative di R4. Konten lain berstatus Trial Use dengan Maturity Model FMM 0 sampai 5; FMM 5 berarti sudah dipakai di minimal lima sistem produksi independen di lebih dari satu negara, tapi masih bisa berubah. R5 terbit Maret 2023 sebagai rilis trial use: tidak ada konten baru yang normative, ada perubahan seperti rework Subscriptions. Karena itu ekosistem, termasuk IG besar seperti US Core, masih dibangun di atas R4, dan migrasi baru masuk akal saat rilis normative berikutnya."

Checklist: apakah Anda menyebut…

  • R4 = 4.0.1, rilis pertama dengan konten normative (2018–2019)?
  • Normative = stabil, dikunci, tunduk aturan kompatibilitas antarversi?
  • contoh normative di R4: REST API, JSON, Patient, Observation?
  • Trial Use + FMM 0–5; FMM 5 = minimal 5 sistem produksi independen, >1 negara?
  • R5 (Maret 2023) berstatus trial use; contoh perubahan: rework Subscriptions?
  • IG (mis. US Core) dan ekosistem masih di R4; HL7 berencana rilis berikutnya normative?
