FHIR REST API: interaksi, search, Bundle, versioning, dan OperationOutcome

REST yang sudah Anda kenal, ditambah aturan khas FHIR yang ditanyakan di interview

Target lesson ini: Anda bisa menjawab "Bagaimana mengambil semua Observation milik satu pasien beserta Patient-nya dalam satu request? Apa beda Bundle transaction dan batch? Bagaimana mencegah dua user saling menimpa update?" tanpa catatan: dengan URL search yang benar (_include, token system|code, prefix tanggal), paging lewat link next, aturan atomik transaction, dan optimistic locking dengan ETag + If-Match → 412.

Yang tidak perlu diajar ulang: HTTP verb, status code, JSON, fetch. Fokusnya hal yang khas FHIR. Semua klaim diambil dari spesifikasi R4 (4.0.1); kutipan berbahasa Inggris adalah teks asli spesifikasi. Istilah resource (id, Reference, meta, CodeableConcept) dari lesson 0002.

1. Interaksi REST dan status HTTP

FHIR menyebut setiap operasi dasar sebagai interaction. Polanya Express-style biasa: tipe resource di path, id logis setelahnya. JSON resmi bertipe application/fhir+json (minta lewat header Accept atau parameter _format). [1]

InteractionRequestSukses / catatan
readGET [base]/Patient/123200. Tidak dikenal → 404; sudah dihapus → 410
vreadGET [base]/Patient/123/_history/2200, satu versi tertentu
createPOST [base]/Patient201 + Location: [base]/Patient/[id]/_history/[vid]; id di body diabaikan
updatePUT [base]/Patient/123200 (diperbarui) atau 201 (dibuat, kalau server mengizinkan id dari client)
patchPATCH [base]/Patient/123JSON Patch (application/json-patch+json), XML Patch, atau FHIRPath Patch
deleteDELETE [base]/Patient/123200 (ada body) atau 204 (tanpa body)
searchGET [base]/Patient?name=peter atau POST [base]/Patient/_search200 + Bundle searchset
historyGET [base]/Patient/123/_history200 + Bundle history
capabilitiesGET [base]/metadataCapabilityStatement (bagian 7)
batch / transactionPOST [base]Bundle batch/transaction (bagian 5)

Semua baris tabel: [1]. Kutipan kunci: "a GET for a deleted resource returns a 410 status code, whereas a GET for an unknown resource returns 404"; create "SHALL also return a Location header which contains the new Logical Id and Version Id"; "If an id is provided, the server SHALL ignore it."

  • Server menentukan id. Create memakai POST tanpa id; server mengisi id, meta.versionId, dan meta.lastUpdated. PUT ke id yang belum ada ("update as create") hanya boleh kalau server mendukungnya, diumumkan di CapabilityStatement.rest.resource.updateCreate. [1]
  • Search lewat POST (_search, body form-encoded) "has exactly the same semantics as the equivalent GET command"; berguna kalau query panjang atau tidak boleh tampil di log URL. [1]
  • Prefer: return=minimal meminta respons tanpa body, return=representation meminta resource lengkap; "Servers SHOULD honor this header." [1]

2. Search: tipe parameter, modifier, prefix

Setiap resource mendefinisikan search parameter-nya sendiri, dan setiap parameter punya tipe yang menentukan sintaks nilainya. Tipe di R4: number, date, string, token, reference, composite, quantity, uri, special. [2] Empat yang paling sering muncul:

TipeContoh parameterContoh queryPerilaku
stringPatient name, familyPatient?family=sant"case-insensitive and accent-insensitive. May match just the start of a string." :exact = persis termasuk huruf besar-kecil; :contains = di posisi mana saja
tokenObservation code, Patient identifier, genderObservation?code=http://loinc.org|29463-7[system]|[code], system dicocokkan dengan Coding.system / Identifier.system. :not membalik, :text mencari teks
referenceObservation subject, patient, encounterObservation?patient=123menunjuk resource lain; dasar chaining dan _include (bagian 3)
dateObservation date, Patient birthdateObservation?date=ge2024-01-01prefix di depan nilai; tanpa prefix = eq

Perilaku: [2]. Tipe parameter Observation (code token, date date atas Observation.effective, patient reference ke Patient): [7]; Patient (birthdate date, family/name string, identifier/gender token): [8].

Prefix (date, number, quantity)

PrefixArtiPrefixArti
eqsama (default)netidak sama
gt / ltlebih besar / lebih kecilge / lelebih besar atau sama / lebih kecil atau sama
sa / ebmulai setelah / berakhir sebelumapkira-kira sama

Sumber: [2]. Contoh resmi rentang 2 tahun: GET [base]/Patient/23/Procedure?date=ge2010-01-01&date=le2011-12-31.

AND, OR, dan :missing

  • Parameter diulang = AND (date=ge2010-01-01&date=le2011-12-31). Nilai dipisah koma = OR (code=http://loinc.org|29463-7,http://loinc.org|3141-9). [2]
  • gender:missing=true → resource yang tidak punya nilai gender; :missing=false → yang punya. [2]
  • Parameter tak dikenal biasanya diam-diam diabaikan: "servers SHOULD ignore unknown or unsupported parameters". Header Prefer: handling=strict meminta error, handling=lenient meminta diabaikan. Parameter yang benar-benar dipakai server tercatat di link self Bundle hasil, jadi periksa itu kalau hasil terlalu banyak. [2]

Jebakan JS: new URLSearchParams({ date: "ge2010-01-01" }) tidak bisa memuat dua date; pakai params.append("date", …) dua kali. Dan | di token sebaiknya di-encode (%7C), yang otomatis dilakukan URLSearchParams.

Latihan 2 — Menyusun query

3. Chaining, _include, dan _revinclude

Dua hal yang sering tertukar: chaining memfilter lewat referensi, _include menambah resource yang dirujuk ke hasil.

Contoh resmiArtinya
ChainingDiagnosticReport?subject:Patient.name=peter"all the lab reports that have a subject which is a patient, whose name includes "peter"". Hasilnya tetap DiagnosticReport saja.
_includeMedicationRequest?_include=MedicationRequest:patientsertakan "any patient that the medication prescriptions in the result set refer to" (arah maju: hasil → yang dirujuk)
_revincludeMedicationRequest?_revinclude=Provenance:targetsertakan "all the provenance resources that refer to them" (arah balik: yang merujuk → hasil)

Semua: [2]. Nilai _include/_revinclude berbentuk [tipe sumber]:[search parameter] (opsional :[tipe target]); include berantai hanya terjadi dengan modifier :iterate. Chaining terbalik (_has) ada, tapi dukungannya "limited".

Jawaban untuk pertanyaan target, dari dua arah:

// Dari Observation: hasil = Observation, Patient ikut sebagai include
GET [base]/Observation?patient=123&code=http://loinc.org|29463-7&_include=Observation:patient

// Dari Patient: hasil = Patient 123, Observation yang merujuknya ikut sebagai include
GET [base]/Patient?_id=123&_revinclude=Observation:patient

Padanan JS: _include mirip include di Prisma (prisma.observation.findMany({ where: …, include: { patient: true } })), tapi hasilnya tidak bersarang: Patient muncul sebagai entry terpisah di Bundle (bagian 4), dan bisa muncul lagi di halaman berikutnya bila dirujuk Observation di halaman itu. [2] Kode LOINC 29463-7 (Body Weight) diambil dari contoh Observation resmi R4. [10]

4. Paging dan Bundle searchset

Hasil search selalu Bundle dengan type: "searchset". [1] Bentuk ringkasnya:

{
  "resourceType": "Bundle",
  "type": "searchset",
  "total": 5000,                                   // jumlah match di SEMUA halaman (include tidak dihitung)
  "link": [
    { "relation": "self", "url": "https://fhir.example.org/Observation?patient=123&_include=Observation:patient&_count=50" },
    { "relation": "next", "url": "https://fhir.example.org/Observation?_getpages=a1b2c3&_offset=50" }
  ],
  "entry": [
    { "fullUrl": "https://fhir.example.org/Observation/obs-1",
      "resource": { "resourceType": "Observation", "id": "obs-1", "...": "..." },
      "search": { "mode": "match" } },
    { "fullUrl": "https://fhir.example.org/Patient/123",
      "resource": { "resourceType": "Patient", "id": "123", "...": "..." },
      "search": { "mode": "include" } }
  ]
}
  • Bundle.total: "the total number of entries of type 'match' across all pages in the search". entry.search.mode: match | include | outcome. [3] Server "SHALL populate the entry.search.mode element ... so that the client can pick apart matches and includes". [2]
  • _count = berapa resource per halaman (permintaan, bukan janji). _summary=count = hanya jumlah, tanpa resource. _sort = urutan. [2]
  • Link halaman (first, previous, next, last) "are opaque to the client, have no dictated structure, and only the server understands them"; "The client must use the server supplied links in order to traverse the pages." [1] Format URL next di contoh atas hanya ilustrasi.
// Node 18+ / browser: ikuti link "next" sampai habis, tanpa menyusun URL halaman sendiri
async function* searchAll(url: string): AsyncGenerator<any> {
  let next: string | undefined = url;
  while (next) {
    const res = await fetch(next, { headers: { Accept: "application/fhir+json" } });
    if (!res.ok) throw new Error(JSON.stringify(await res.json()));   // body = OperationOutcome (bagian 7)
    const bundle = await res.json();
    for (const entry of bundle.entry ?? []) yield entry;              // cek entry.search.mode
    next = bundle.link?.find((l: any) => l.relation === "next")?.url;
  }
}

Untuk jutaan resource, paging search bukan alat yang tepat; itu tugas Bulk Data $export di lesson 0004.

Latihan 4 — Membaca Bundle hasil search

5. Bundle transaction vs batch, dan conditional create

Keduanya dikirim dengan POST [base]; body-nya Bundle dengan type transaction atau batch, dan setiap entry membawa request.method + request.url ("the HTTP action to be executed for this entry"). [1] [3]

transactionbatch
Definisi"processed by a server as an atomic commit""a group of independent actions"
Satu entry gagalsemua ditolak: "either succeed or fail together"; status 4xx/5xx + satu OperationOutcomeentry lain tetap diproses; "The success or failure of one change SHOULD not alter" yang lain
Respons sukses200 + transaction-response, semua entry sukses200 + batch-response, "some responses may indicate failure and others success"
Referensi antar-entryboleh, lewat fullUrl sementara (urn:uuid:…); server mengganti dengan id barutidak boleh: "there SHALL be no interdependencies between the different entries"
Padanan JSprisma.$transaction([...])Promise.allSettled([...])

Kutipan: [1] [4]. Untuk transaction, server "SHALL also update any references to that resource in the same bundle". Padanan JS hanya analogi perilaku, bukan klaim spesifikasi.

{
  "resourceType": "Bundle",
  "type": "transaction",
  "entry": [
    { "fullUrl": "urn:uuid:61ebe359-bfdc-4613-8bf2-c5e300945f0a",
      "resource": { "resourceType": "Patient",
                    "identifier": [{ "system": "http://rs.example.org/mrn", "value": "12345" }] },
      "request": { "method": "POST", "url": "Patient",
                   "ifNoneExist": "identifier=http://rs.example.org/mrn|12345" } },
    { "resource": { "resourceType": "Observation", "status": "final",
                    "code": { "coding": [{ "system": "http://loinc.org", "code": "29463-7" }] },
                    "subject": { "reference": "urn:uuid:61ebe359-bfdc-4613-8bf2-c5e300945f0a" } },
      "request": { "method": "POST", "url": "Observation" } }
  ]
}

Conditional create (Bundle.entry.request.ifNoneExist: "Instruct the server not to perform the create if a specified resource already exists" [11], atau header If-None-Exist: [search parameters] pada POST biasa) membuat import idempoten: 0 cocok → create biasa; 1 cocok → "The server ignores the post and returns 200 OK"; lebih dari 1 → 412, kriteria "not selective enough". Pola sama untuk conditional update PUT [base]/Patient?identifier=…. [1] Di contoh atas, kalau Patient MRN 12345 sudah ada, Observation tetap dibuat dan merujuk ke Patient lama.

Urutan pemrosesan transaction

"The outcome of processing the transaction SHALL NOT depend on the order of the resources in the transaction": server sendiri yang mengurutkan berdasarkan method. [1] Susun urutan yang ditetapkan spesifikasi:

  1. Proses semua DELETE
  2. Proses semua POST (create)
  3. Proses semua PUT atau PATCH
  4. Proses semua GET atau HEAD

DELETE → POST → PUT/PATCH → GET/HEAD. Jadi GET/HEAD diproses setelah semua perubahan di Bundle yang sama, dan urutan entry yang Anda tulis tidak mengubah hasil. [1]

Latihan 5 — Transaction, batch, conditional create

6. Versioning: vread, ETag, If-Match

  • Setiap update membuat versi baru; nomornya di meta.versionId dan dikirim sebagai header ETag, waktu di meta.lastUpdated sebagai Last-Modified. Version id adalah "weak" ETag, jadi berawalan W/, mis. ETag: W/"3141". [1]
  • Lost update ("two clients update the same resource, and the second overwrites the updates of the first") "can be prevented using a combination of the ETag and If-Match header". Kalau versi di If-Match tidak cocok, "the server returns a 412 Precondition Failed status code instead of updating the resource". [1]
  • Versioning tidak wajib: server "SHOULD provide full version support", tapi boleh tidak; cek CapabilityStatement. Untuk PATCH pun, "Clients SHOULD always consider using version specific PATCH operations". [1]
// Optimistic locking: sama seperti kolom version di ORM, tapi lewat header HTTP
const read = await fetch(`${base}/Patient/123`, { headers: { Accept: "application/fhir+json" } });
const etag = read.headers.get("ETag");          // W/"3"
const patient = await read.json();
patient.telecom = [{ system: "phone", value: "+62-812-0000-0000" }];

const res = await fetch(`${base}/Patient/123`, {
  method: "PUT",
  headers: { "Content-Type": "application/fhir+json", "If-Match": etag! },
  body: JSON.stringify(patient),
});
if (res.status === 412) {
  // user lain sudah menyimpan versi 4: muat ulang, tampilkan perbedaan, minta user memutuskan
}

Melihat versi lama: GET [base]/Patient/123/_history/3 (vread, satu versi) atau GET [base]/Patient/123/_history (Bundle type: "history", semua versi). [1]

Latihan 6 — Versi dan konflik

7. Error: OperationOutcome. Discovery: CapabilityStatement

"In case of failure, servers SHOULD always return a body that contains an OperationOutcome resource." [1] OperationOutcome adalah "A collection of error, warning, or information messages that result from a system action", dan isinya "SHOULD be in alignment with the HTTP response code". [5] 

// 422 Unprocessable Entity
{
  "resourceType": "OperationOutcome",
  "issue": [{
    "severity": "error",                       // fatal | error | warning | information
    "code": "required",                        // dari value set IssueType
    "diagnostics": "Observation.status: minimum required = 1, but only found 0",
    "expression": ["Observation.status"]       // lokasi elemen (subset FHIRPath)
  }]
}

Elemen: [5]. Contoh kode issue.code: invalid, required, value, not-found, conflict ("Edit Version Conflict"), business-rule, security, exception [9]. Teks diagnostics di atas hanya ilustrasi; isinya bebas per server.

StatusKapan (create/update)
400"resource could not be parsed or failed basic FHIR validation rules"
404 / 410tidak dikenal / sudah dihapus
409 / 412konflik versi; If-Match tidak cocok, atau conditional create/update cocok > 1
422"the proposed resource violated applicable FHIR profiles or server business rules"

Sumber tabel: [1]. Di React: issue[].expression bisa dipetakan ke field form untuk menandai input yang salah.

CapabilityStatement "documents a set of capabilities (behaviors) of a FHIR Server for a particular version of FHIR". [6] Ambil dengan GET [base]/metadata: "A Capability Statement that specifies which resource types and interactions are supported." [1] Yang dibaca saat mulai integrasi: fhirVersion, format, rest.security (cara autentikasi, lesson 0005), dan per rest.resource: type, interaction, searchParam. [6] Padanan JS: seperti dokumen OpenAPI, tapi baku dan wajib ada di setiap server FHIR.

Latihan 8 — Ucapkan dengan suara keras (±15 menit)

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Bagaimana Anda mengambil semua Observation berat badan milik satu pasien, beserta Patient-nya, dalam satu request? Bagaimana kalau hasilnya ribuan?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Saya search Observation: GET [base]/Observation?patient=123&code=http://loinc.org|29463-7&_include=Observation:patient&_count=50. code itu token, jadi saya tulis system|code supaya tidak tertukar dengan sistem kode lain; kalau perlu rentang waktu, tambah date=ge2024-01-01&date=le2024-12-31, parameter yang diulang berarti AND. _include membuat server ikut mengirim Patient yang dirujuk, dan di Bundle searchset saya bedakan lewat entry.search.mode: match untuk Observation, include untuk Patient. Alternatifnya dari sisi Patient: Patient?_id=123&_revinclude=Observation:patient. Kalau ribuan, server mem-page hasilnya; saya ikuti Bundle.link dengan relation next sampai habis, tidak menyusun URL halaman sendiri karena link itu opaque. Jumlah total ada di Bundle.total, yang hanya menghitung match. Di Prisma, padanannya findMany dengan include plus cursor pagination."

Checklist: apakah Anda menyebut…

  • search Observation dengan patient=123 (atau subject=Patient/123)?
  • code sebagai token http://loinc.org|29463-7 (system|code)?
  • _include=Observation:patient, atau _revinclude dari sisi Patient?
  • hasil Bundle searchset; entry.search.mode membedakan match dan include?
  • paging: _count dan mengikuti link next yang opaque, bukan menyusun URL sendiri?
  • filter tanggal dengan prefix ge/le, parameter diulang = AND, koma = OR?

Lulus kalau minimal 4 dari 6.

"Apa beda Bundle transaction dan batch? Kapan Anda memakai masing-masing?" (60–90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Keduanya di-POST ke base URL, POST [base], berisi Bundle dengan type transaction atau batch; setiap entry punya request.method dan request.url, jadi satu Bundle bisa berisi create, update, delete, dan read. Transaction itu atomik: semua sukses atau semua gagal. Kalau satu entry gagal, server menolak semuanya dengan 4xx/5xx dan satu OperationOutcome; kalau sukses, saya dapat transaction-response. Di dalam transaction, entry boleh saling merujuk lewat fullUrl urn:uuid:..., dan server mengganti referensi itu dengan id asli. Batch adalah sekumpulan aksi independen: tidak boleh ada ketergantungan antar-entry, dan batch-response berisi status per entry, sebagian bisa gagal. Saya pakai transaction untuk data yang harus konsisten, misalnya Encounter beserta Observation-nya; batch untuk banyak aksi yang tidak saling terkait, misalnya beberapa read sekaligus. Padanan JS: transaction seperti prisma.$transaction, batch seperti Promise.allSettled. Untuk import yang idempoten saya tambahkan conditional create (ifNoneExist) per entry."

Checklist: apakah Anda menyebut…

  • POST [base] dengan Bundle.type transaction/batch, entry berisi request.method + url?
  • transaction atomik: semua sukses atau semua gagal (4xx/5xx + OperationOutcome)?
  • batch: aksi independen, respons per entry, sebagian boleh gagal?
  • referensi antar-entry lewat fullUrl urn:uuid hanya di transaction; batch tanpa ketergantungan?
  • contoh kapan memakai masing-masing (data saling terkait vs aksi lepas)?
  • padanan JS ($transaction vs allSettled) atau conditional create untuk idempoten?

Lulus kalau minimal 4 dari 6.

"Dua user mengedit Patient yang sama di React app Anda. Bagaimana mencegah lost update, dan bagaimana error-nya sampai ke UI?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Setiap resource FHIR punya meta.versionId, dan server mengirimnya sebagai ETag, misalnya W/"3". Saat read saya simpan ETag itu; saat update saya kirim PUT [base]/Patient/123 dengan If-Match: W/"3". Kalau sementara itu user lain sudah menyimpan versi 4, server menolak dengan 412 Precondition Failed, bukan menimpa diam-diam. Ini optimistic locking, sama seperti kolom version di ORM. Di UI saya tangkap 412, ambil versi terbaru, lalu minta user meninjau atau menggabungkan perubahan. Versi lama bisa dilihat dengan vread _history/3 atau seluruh history. Untuk error lain, server mengembalikan OperationOutcome: setiap issue punya severity, code seperti required atau conflict, diagnostics, dan expression yang menunjuk elemen yang salah, jadi saya bisa menandai field di form. 400 artinya body tidak valid secara dasar, 422 melanggar profil atau aturan bisnis."

Checklist: apakah Anda menyebut…

  • meta.versionId = ETag (weak, W/"n")?
  • update dengan If-Match berisi ETag terakhir yang dibaca?
  • versi tidak cocok → 412 Precondition Failed, lalu reload/merge di UI?
  • menyebut optimistic locking / lost update, dan vread atau _history?
  • error dalam OperationOutcome: severity, code, diagnostics, expression?
  • membedakan 400 (tidak valid dasar) dan 422 (profil/aturan bisnis)?
