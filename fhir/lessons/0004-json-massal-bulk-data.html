JSON massal: Bulk Data $export, NDJSON, dan streaming di Node

Dari "ekspor jutaan resource" sampai "insert ke database tanpa kehabisan memori", dalam bahasa yang sudah Anda kenal: fetch, stream, dan for await

Target lesson ini: Anda bisa menjawab "Bagaimana Anda mengekspor jutaan resource dari server FHIR dan memprosesnya di Node tanpa kehabisan memori?" tanpa catatan, dalam 90 detik: tiga level $export, alur kick-off → 202 → polling → manifest → file NDJSON, kenapa JSON.parse satu file besar itu salah, streaming baris per baris dengan backpressure dan pipeline, batching ke database, dan satu jebakan khas FHIR: angka decimal yang kehilangan presisi di JavaScript.

Semua fakta Bulk Data di lesson ini diambil dari Bulk Data Access IG v2.0.0 (STU 2), yang dibangun di atas FHIR R4. Halaman IG itu sendiri mencatat bahwa versi 3.0.0 sudah menggantikannya [1]; alur intinya sama, tapi sebutkan versinya kalau interviewer bertanya detail. Search dan paging biasa ada di lesson 0003; autentikasi SMART Backend Services dibahas di lesson 0005. Lesson ini tanpa lab: potongan HTTP, JSON, dan TypeScript hanya untuk dibaca dan dijelaskan.

1. Kenapa bukan search biasa: tiga level $export

Search dengan paging (GET Observation?_count=1000 lalu ikuti link next) cocok untuk layar aplikasi, bukan untuk jutaan resource: satu request per halaman, dan Anda yang mengatur semuanya. Bulk Data $export membalik perannya: server menyiapkan file di belakang, client mengambil hasilnya nanti. Operasi ini "initiates the asynchronous generation of a requested export dataset - whether that be data for all patients, data for a subset (defined group) of patients, or all FHIR data in the server." [1]

LevelEndpointIsiContoh kebutuhan
Patient[base]/Patient/$exportdata semua pasienmigrasi rekam medis ke sistem baru
Group[base]/Group/[id]/$exportdata anggota satu Groupkohort pasien diabetes untuk analitik, roster pasien dari payer
System[base]/$exportsemua data, terkait pasien atau tidakbackup server, ekspor terminologi dengan _type

Kutipan tabel: [1]. Untuk level Patient dan Group, Patient Compartment dipakai sebagai acuan resource yang dikembalikan; resource pendukung seperti Organization dan Practitioner MAY ikut.

Tiga hal yang perlu disebut saat menjelaskan kick-off:

  • Asinkron. Header Prefer: respond-async: "Currently, only a value of respond-async is supported. A client SHOULD provide this header." Accept di kick-off hanya menentukan format OperationOutcome (application/fhir+json). [1]
  • GET wajib, POST opsional. "A server SHALL support GET requests and MAY support POST requests that supply parameters using the FHIR Parameters Resource." [1]
  • Auth server-ke-server. Tidak ada user yang login: "implementers SHOULD implement OAuth 2.0 access management in accordance with the SMART Backend Services Authorization Profile", dan server "SHALL limit the data returned to only those FHIR resources for which the client is authorized." [1] Detail client credentials + JWT di lesson 0005.

2. Alur asinkron: kick-off → 202 → polling → manifest

token (Backend Services)→ kick-off→ 202 + Content-Location→ polling (202…)→ 200 + manifest→ unduh NDJSON 
GET [base]/Patient/$export?_type=Patient,Observation&_since=2026-10-25T00:00:00Z
Accept: application/fhir+json
Prefer: respond-async
Authorization: Bearer eyJhbGciOi…          ← token dari SMART Backend Services (0005)

HTTP/1.1 202 Accepted
Content-Location: https://fhir.example.org/bulkstatus/42   ← URL status untuk polling

GET https://fhir.example.org/bulkstatus/42
  → 202 Accepted           X-Progress: "50% complete"   Retry-After: 120
  → 429 Too Many Requests  Retry-After: 300              (kalau polling terlalu sering)
  → 200 OK                 Expires: …   Content-Type: application/json   + body manifest
  → 4XX/5XX                body OperationOutcome          (export gagal)
  • Kick-off sukses: "HTTP Status Code of 202 Accepted" plus "Content-Location header with the absolute URL of an endpoint for subsequent status requests (polling location)". Gagal (mis. parameter tidak didukung): 4XX/5XX dengan body OperationOutcome. [1]
  • Polling: "Clients SHOULD follow an exponential backoff approach when polling for status." Retry-After berisi detik (mis. 120) atau http-date. Kalau client terlalu sering, server "SHOULD respond with a 429 Too Many Requests status code in addition to a Retry-After header". Selama berjalan: 202, opsional X-Progress (teks bebas < 100 karakter). [1]
  • Export lain masih jalan: server yang ingin menolak export baru SHOULD membalas 429 + Retry-After juga. [1]
  • Batal: DELETE ke URL status → 202; setelah itu polling ke URL yang sama SHALL menghasilkan 404 + OperationOutcome. [1]

Versi TypeScript singkat dari sisi client (untuk dibaca, bukan dijalankan):

async function waitForManifest(statusUrl: string, token: string): Promise<Manifest> {
  let delay = 10;                                          // detik
  for (;;) {
    const res = await fetch(statusUrl, {
      headers: { Accept: "application/json", Authorization: `Bearer ${token}` },
    });
    if (res.status === 200) return (await res.json()) as Manifest;   // manifest kecil: json() aman
    if (res.status !== 202 && res.status !== 429) {
      throw new Error(`export gagal: ${res.status}`);     // body: OperationOutcome
    }
    const retryAfter = Number(res.headers.get("Retry-After"));       // http-date → NaN
    delay = retryAfter > 0 ? retryAfter : Math.min(delay * 2, 600);  // hormati server, else backoff
    await new Promise(r => setTimeout(r, delay * 1000));
  }
}

Padanan yang mungkin Anda kenal: pola "job + status URL" yang sama dengan antrean job (BullMQ) atau API laporan asinkron. IG menyebutnya "FHIR Asynchronous Request Pattern". [1]

Latihan 2 — Susun urutan alur $export

Urutkan langkahnya dari awal sampai data masuk database. Gunakan ↑/↓, lalu Periksa.

  1. Client meminta access token lewat SMART Backend Services
  2. GET [base]/Group/[id]/$export dengan Prefer: respond-async
  3. Server membalas 202 Accepted + Content-Location
  4. Client polling URL status; menunggu sesuai Retry-After selama masih 202
  5. Server membalas 200 OK dengan manifest JSON
  6. Client mengunduh setiap URL di output dan error sebelum Expires
  7. Setiap file NDJSON di-stream, di-parse per baris, di-insert per batch
  8. transactionTime disimpan sebagai _since untuk export berikutnya

Token dulu (kick-off, status, dan file dengan requiresAccessToken: true dilindungi dengan cara yang sama), lalu kick-off → 202 → polling → 200 + manifest → unduh → proses streaming. transactionTime adalah jam server saat query dijalankan, jadi aman dipakai sebagai _since berikutnya.

3. Manifest, NDJSON, _type dan _since

{
  "transactionTime": "2026-10-26T01:00:00Z",
  "request": "https://fhir.example.org/fhir/Patient/$export?_type=Patient,Observation",
  "requiresAccessToken": true,
  "output": [
    { "type": "Patient",     "url": "https://files.example.org/42/Patient_1.ndjson" },
    { "type": "Observation", "url": "https://files.example.org/42/Observation_1.ndjson", "count": 1000000 },
    { "type": "Observation", "url": "https://files.example.org/42/Observation_2.ndjson", "count": 734120 }
  ],
  "deleted": [],
  "error": [
    { "type": "OperationOutcome", "url": "https://files.example.org/42/err_1.ndjson" }
  ]
}
FieldArti (Bulk Data IG v2.0.0)
transactionTimewajib; "the server's time when the query is run". Export SHALL memuat semua resource yang cocok sampai dan termasuk instant ini.
requiresAccessTokenwajib; true berarti unduhan file butuh token yang sama. Boleh false untuk file server dengan skema lain, mis. URL bucket S3.
outputwajib; satu item {type, url, count?} per file. "Each file SHALL contain resources of only one type, but a server MAY create more than one file for each resource type returned."
errorwajib (boleh kosong); file NDJSON berisi OperationOutcome. Export yang sebagian gagal tetap 200: "In the case of a partial success, the server SHALL use a 200 status code".
deletedopsional; dengan _since, berisi Bundle transaction dengan request.method = DELETE untuk resource yang dihapus sejak waktu itu.
header ExpiresSHOULD; kapan file tidak lagi tersedia. Unduh dan proses sebelum itu.

Kutipan tabel: [1]

NDJSON (newline delimited JSON): "resources are serialized with no whitespace, and separated by a newline pair (characters 13 and 10)", MIME type application/fhir+ndjson, dan "each nd-json document contains only resources of a single type". [2] Padanan JS: format ini sama dengan JSON Lines yang mungkin Anda kenal dari log. Isi Observation_1.ndjson, dua baris pertama: 

{"resourceType":"Observation","id":"obs-1","status":"final","code":{"coding":[{"system":"http://loinc.org","code":"8310-5","display":"Body temperature"}]},"subject":{"reference":"Patient/p-1"},"valueQuantity":{"value":36.50,"unit":"Cel","system":"http://unitsofmeasure.org","code":"Cel"}}
{"resourceType":"Observation","id":"obs-2","status":"final","code":{"coding":[{"system":"http://loinc.org","code":"8310-5","display":"Body temperature"}]},"subject":{"reference":"Patient/p-2"},"valueQuantity":{"value":37.20,"unit":"Cel","system":"http://unitsofmeasure.org","code":"Cel"}}

Kode LOINC 8310-5 (Body temperature) dari profil vital signs R4. [12] Perhatikan 36.50; kita kembali ke angka ini di bagian 7.

Parameter kick-off yang paling sering ditanya: [1]

  • _type: daftar tipe resource dipisah koma; "The response SHALL be filtered to only include resources of the specified resource types(s)." Tanpa _type, server mengembalikan semua tipe yang didukung dalam batas otorisasi client.
  • _since (FHIR instant): hanya resource yang "state has changed after the supplied time (e.g., if Resource.meta.lastUpdated is later than the supplied _since time)". Untuk export inkremental, isi dengan transactionTime dari manifest sebelumnya, seperti pola Group di IG yang menyuruh client "retains the transactionTime value from the response". [1]
  • _outputFormat: default application/fhir+ndjson; server SHALL mendukung NDJSON. _elements dan _typeFilter berstatus experimental.

Data yang diekspor hanya versi terbaru setiap resource: "The exported data SHALL include only the most recent version of any exported resources". [1]

Latihan 3 — Membaca manifest

4. Di Node: kenapa JSON.parse satu file besar itu salah

// JANGAN untuk file hasil $export
const text = await readFile("Observation_1.ndjson", "utf8");   // seluruh file → satu string
const all = JSON.parse(text);                                   // + seluruh objek di heap, sekaligus
MasalahKenapa
Batas stringbuffer.constants.MAX_STRING_LENGTH: "The largest length allowed for a single string instance", dan "This value may depend on the JS engine". [7] Di Node 24.21.0 yang saya cek nilainya 536.870.888 UTF-16 code unit, jauh di bawah file 3 GB.
MemoriTeks mentah dan hasil parse ada di heap bersamaan; jutaan objek kecil ditahan sampai Anda selesai.
Event loop terblokJSON.parse dan JSON.stringify "are O(n) in the length of the input, for large n they can take surprisingly long". Contoh resmi: parse string 50 MB makan 1,3 detik, dan selama itu tidak ada request lain yang dilayani. [8]
FormatNDJSON adalah banyak dokumen JSON dipisah newline, bukan satu array; JSON.parse pada seluruh isi file langsung melempar SyntaxError.

Solusinya selalu sama: jangan pernah memegang seluruh file. Baca potongan demi potongan, parse satu resource setiap kali, lalu buang.

Latihan 4 — Batas JSON.parse

5. Streaming baris per baris, batching, dan stream-json

Versi paling pendek, persis pola resmi dokumentasi readline "Read file stream line-by-line": [6]

import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";

const rl = createInterface({ input: createReadStream("Observation_1.ndjson"), crlfDelay: Infinity });
let batch: Observation[] = [];
for await (const line of rl) {
  if (!line.trim()) continue;
  batch.push(JSON.parse(line));                     // satu resource kecil, bukan seluruh file
  if (batch.length === 1000) { await db.insertMany(batch); batch = []; }
}
if (batch.length) await db.insertMany(batch);
  • crlfDelay: Infinity membuat CR LF (\r\n) dihitung satu pemisah baris; relevan karena nd-json FHIR menyebut "newline pair (characters 13 and 10)". [6] [2]
  • Dua catatan dari dokumentasi async iterator readline: "Errors in the input stream are not forwarded", dan "Performance is not on par with the traditional 'line' event API". [6] Dokumentasi juga tidak menjanjikan input dijeda selama Anda await di dalam loop. Untuk job produksi, rangkai dengan pipeline (bagian 6).
  • Batching (mis. 1.000 resource per insert) mengurangi round-trip ke database; await pada insert adalah tempat "konsumen lambat" yang harus menahan pembacaan file.

JSON besar yang bukan NDJSON (mis. satu Bundle searchset 2 GB dari sistem lain) tidak bisa dibaca per baris, karena JSON biasa boleh punya newline di mana saja. Untuk itu ada stream-json: "Point it at a document far larger than available memory and it streams straight through", dan komponennya dirangkai dengan stream-chain yang "handles the streaming and backpressure". README-nya juga mengingatkan: dirancang untuk "data you own or trust", bukan input publik yang tidak tepercaya. [10] 

import { parser } from "stream-json";
import { pick } from "stream-json/filters/pick.js";
import { streamArray } from "stream-json/streamers/stream-array.js";
import chain from "stream-chain";
import fs from "node:fs";

const entries = chain([
  fs.createReadStream("searchset-besar.json"),     // { "resourceType": "Bundle", "entry": [ ...jutaan... ] }
  parser(),
  pick({ filter: "entry" }),                        // turun ke array "entry", abaikan sisanya
  streamArray(),                                    // satu elemen array setiap kali: { key, value }
]);
entries.on("data", ({ value }) => handle(value.resource));

Pola dan import mengikuti contoh README stream-json 3.x (ESM, pick lalu streamArray). [10] README yang sama menyebut parser JSONL di stream-chain sebagai "the fast path for line-delimited data dumps".

Latihan 5 — Alat yang tepat

6. Backpressure dan pipeline

Disk bisa memberi 500 MB/detik, database mungkin hanya menerima beberapa ribu baris per detik. Tanpa rem, data menumpuk di memori. Panduan Node menyebut ini backpressure: "a buildup of data behind a buffer during data transfer", dan di Node "streams have been the adopted solution". [9]

  • highWaterMark: setelah buffer baca mencapai ambang ini, stream "will temporarily stop reading data from the underlying resource until the data currently buffered can be consumed". Dalam object mode, ambangnya dihitung dalam jumlah objek. Ini "a threshold, not a limit". [5]
  • write() → false: "Once write() returns false, do not write more chunks until the 'drain' event is emitted." Kalau diabaikan, "Node.js will buffer all written chunks until maximum memory usage occurs, at which point it will abort unconditionally." [5]
  • pipeline vs .pipe(): pipeline "pipe[s] between streams and generators forwarding errors and properly cleaning up". Dengan .pipe(), "if the Readable stream emits an error during processing, the Writable destination is not closed automatically". [5] [5]

Versi produksi: unduh dari URL manifest, pecah per baris, batch ke database, semua dalam satu pipeline yang bisa di-await. pipeline dari node:stream/promises menerima async generator sebagai tahap transform dan fungsi async sebagai tujuan. [5]

import { Readable } from "node:stream";
import { pipeline } from "node:stream/promises";

async function* lines(source: AsyncIterable<string>) {
  let rest = "";
  for await (const chunk of source) {               // pull: chunk berikut dibaca setelah body loop selesai
    const parts = (rest + chunk).split("\n");
    rest = parts.pop()!;                            // sisa baris yang belum lengkap
    yield* parts;
  }
  if (rest) yield rest;
}

async function importFile(url: string, token: string) {
  const res = await fetch(url, { headers: { Accept: "application/fhir+ndjson", Authorization: `Bearer ${token}` } });
  if (!res.ok || !res.body) throw new Error(`unduh gagal: ${res.status}`);
  await pipeline(
    Readable.fromWeb(res.body).setEncoding("utf8"), // web stream → Node stream, decode UTF-8 dengan aman
    lines,
    async function (source: AsyncIterable<string>) {
      let batch: unknown[] = [];
      for await (const line of source) {
        if (!line.trim()) continue;
        batch.push(JSON.parse(line));
        if (batch.length === 1000) { await db.insertMany(batch); batch = []; }   // insert lambat = baca berhenti
      }
      if (batch.length) await db.insertMany(batch);
    },
  );                                                // error di tahap mana pun → reject + semua stream dibersihkan
}

Kenapa memori tetap kecil: async iterator stream bersifat pull. Selama await db.insertMany belum selesai, tidak ada yang meminta baris berikutnya, buffer terisi sampai highWaterMark, lalu pembacaan dari jaringan berhenti. Iterasi "will be read in chunks of size equal to the highWaterMark option". [5] setEncoding("utf8") mencegah karakter multibyte (mis. nama pasien beraksen) terpotong di batas chunk.

Latihan 6 — Backpressure

7. Jebakan khas FHIR: decimal di JavaScript

Di FHIR, presisi angka adalah bagian dari data: "0.010 is regarded as different to 0.01, and the original precision should be preserved", dan "Implementations SHALL handle decimal values in ways that preserve and respect the precision of the value as represented for presentation purposes". [4] Di JSON, decimal ditulis sebagai JSON number, dan spesifikasi JSON FHIR sendiri memperingatkan: "When using a JavaScript JSON.parse() implementation, note that JavaScript natively supports only one numeric datatype ... trailing 0s after a decimal point will be lost e.g. 2.00 will be converted to 2." Sarannya: "consider using a custom parser and big number library". [3] 

JSON.parse('{"value":36.50}').value          // 36.5    → "36.50 °C" berubah jadi "36.5 °C" di UI
JSON.parse('{"value":0.010}').value          // 0.01    → presisi alat ukur hilang

// Node 24: reviver menerima context.source, teks asli nilai primitif
JSON.parse('{"value":36.50}', (key, value, context) =>
  key === "value" ? context.source : value)  // { value: "36.50" } → simpan sebagai string / NUMERIC

Hasil di atas saya jalankan di Node 24.21.0. context.source berisi "The original JSON string representing this value" dan hanya ada untuk nilai primitif; MDN juga mengingatkan bahwa reviver berjalan setelah angka dikonversi, jadi nilainya "may lose precision in the process". [11] Simpan ke database sebagai tipe decimal (mis. NUMERIC di PostgreSQL), bukan float. Kabar baiknya, FHIR sendiri mencatat "large and/or highly precise values are extremely rare in medicine"; masalah yang umum adalah nol di belakang koma. [4]

Latihan 8 — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Bagaimana Anda mengekspor jutaan resource dari server FHIR? Jelaskan alurnya dari kick-off sampai file diunduh." (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Saya tidak memakai paging search biasa, tapi Bulk Data $export. Ada tiga level: Patient/$export untuk semua pasien, Group/[id]/$export untuk satu kohort, dan $export di base untuk seluruh server. Client mendapat token lewat SMART Backend Services, lalu kick-off dengan Prefer: respond-async, opsional _type untuk membatasi tipe dan _since untuk export inkremental. Server membalas 202 Accepted dengan header Content-Location, yaitu URL status. Client polling URL itu: selama masih 202, ikuti Retry-After dan exponential backoff; kalau terlalu sering, server membalas 429. Setelah selesai, 200 dengan manifest JSON: transactionTime, requiresAccessToken, array output berisi URL file NDJSON per tipe resource, dan array error berisi OperationOutcome. File diunduh sebelum Expires, diproses secara streaming, dan transactionTime disimpan sebagai _since untuk export berikutnya."

Checklist: apakah Anda menyebut…

  • tiga level: Patient/$export, Group/[id]/$export, system $export?
  • kick-off asinkron dengan Prefer: respond-async, autentikasi lewat SMART Backend Services?
  • 202 Accepted + Content-Location sebagai URL status?
  • polling: 202 selama berjalan, hormati Retry-After/backoff, 429 kalau terlalu sering?
  • 200 + manifest: output (URL file NDJSON per tipe), error, transactionTime?
  • _type untuk membatasi tipe dan _since = transactionTime sebelumnya untuk inkremental?

Lulus jika minimal 4 dari 6.

"File Observation NDJSON 5 GB hasil $export. Bagaimana Anda memprosesnya di Node dan menyimpannya ke database tanpa kehabisan memori?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Saya tidak akan readFile lalu JSON.parse: seluruh file harus jadi satu string, padahal panjang string di V8 dibatasi, parse-nya memblok event loop, dan NDJSON memang bukan satu dokumen JSON. Karena NDJSON satu baris satu resource, saya baca sebagai stream: createReadStream, pecah per baris dengan readline atau async generator, lalu JSON.parse per baris. Saya kumpulkan per batch, misalnya 1.000 resource, lalu await insert batch itu sebelum membaca lagi. Karena konsumen menarik data, stream berhenti membaca saat buffer mencapai highWaterMark; itulah backpressure, jadi memori tetap kecil walau database lebih lambat dari disk. Semua dirangkai dengan pipeline dari stream/promises, supaya error di tahap mana pun menghentikan dan membersihkan semua stream. Kalau datanya JSON biasa yang besar, misalnya Bundle, saya pakai stream-json. Dan saya hati-hati dengan decimal: JSON.parse mengubah 2.00 jadi 2."

Checklist: apakah Anda menyebut…

  • menolak readFile + JSON.parse seluruh file: batas panjang string/heap dan event loop terblok?
  • NDJSON = satu baris satu resource: stream (createReadStream) lalu JSON.parse per baris?
  • batching insert ke database dan await sebelum membaca lagi?
  • menjelaskan backpressure: highWaterMark, write() false / drain, konsumen lambat menahan produsen?
  • pipeline dari stream/promises untuk propagasi error dan cleanup?
  • menyebut stream-json untuk JSON besar non-NDJSON atau jebakan presisi decimal?
