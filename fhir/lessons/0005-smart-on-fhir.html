Keamanan, SMART on FHIR, dan frontend React

OAuth2 yang sudah Anda kenal, ditambah tiga hal khas kesehatan: launch dari EHR, scopes per resource FHIR, dan konteks pasien

Target lesson ini: Anda bisa menjawab "Bagaimana React app Anda mendapat akses ke data pasien di EHR? Apa itu SMART on FHIR?" tanpa catatan dalam 90 detik: EHR launch vs standalone launch, discovery .well-known/smart-configuration, authorization code + PKCE tanpa client secret, scopes seperti patient/Observation.rs, konteks patient di token response, dan kapan memakai Backend Services (job Node tanpa user, misalnya Bulk $export).

Versi yang dipakai: SMART App Launch IG v2.2.0 (STU 2.2), versi terbit saat ini, berbasis FHIR R4 (4.0.1). [0] Dasar OAuth2/JWT, 401 vs 403, CORS, dan localStorage vs cookie HttpOnly tidak diulang di sini; kalau perlu penyegaran, lihat lesson 0017 (track .NET). Fokus lesson ini hanya yang khas SMART.

1. Peta besar: SMART = OAuth 2.0 yang diprofilkan untuk FHIR

SMART App Launch menghubungkan app pihak ketiga ke data EHR, dan app bisa diluncurkan dari dalam maupun dari luar UI EHR. Secara teknis ini adalah "profile on OAuth 2.0" untuk app yang butuh identitas user atau resource FHIR. [1] Padanan dunia JS: "Login with Google" di SPA dengan authorization code + PKCE, plus tiga tambahan:

Yang Anda kenal (OAuth2 di SPA)Tambahan SMART
App selalu dimulai dari tombol "Login"App juga bisa diluncurkan oleh EHR dari dalam rekam medis yang sedang dibuka (EHR launch)
Endpoint OAuth di-hardcode per providerEndpoint ditemukan lewat [fhir-base]/.well-known/smart-configuration
Scope bebas (read:user, repo)Scope mengikuti resource type FHIR: patient/Observation.rs
Token response: token sajaToken response juga membawa launch context: "patient": "123"

Yang tidak diatur SMART: izin dasar user di EHR. SMART hanya mendelegasikan sebagian izin yang sudah dimiliki user ke app, "on top of an EHR's existing user and permissions management system". [1] Mekanisme seperti session time-out dan security auditing yang diwajibkan HIPAA juga di luar cakupan profile ini. [1]

2. Dua cara mulai: EHR launch vs standalone launch, lalu discovery

Langkah tingkat atas SMART App Launch: [1]

Register app (sekali)→ Launch: EHR / standalone→ .well-known/smart-configuration→ authorization code→ access token→ FHIR API→ refresh
EHR launchStandalone launch
Siapa memulaiUser sudah di sesi EHR lalu membuka app (mis. dari tab rekam medis)User membuka app dari luar EHR (mis. ikon di home screen)
Yang diterima app di awalLaunch URL dibuka dengan iss (FHIR endpoint EHR) dan launch (handle opaque)Tidak ada; app sudah tahu server FHIR mana yang dituju
Cara minta konteksScope launch + parameter launch=xyz123 dikirim balik saat authorizeScope launch/patient: EHR bisa menampilkan pemilih pasien

Kutipan tabel: [1] [2]

Location: https://app/launch?iss=https%3A%2F%2Fehr%2Ffhir&launch=xyz123

Setelah tahu base URL FHIR (dari iss atau konfigurasi), app melakukan discovery: GET ke base URL + /.well-known/smart-configuration. Server SHALL menjawab JSON; capabilities, token_endpoint, dan code_challenge_methods_supported wajib ada, authorization_endpoint wajib bila server mendukung launch. Dulu sebagian info ini ada di CapabilityStatement; mekanisme itu sekarang deprecated. [3] 

// GET https://ehr.example.com/fhir/.well-known/smart-configuration  (ilustrasi, dipersingkat)
{
  "authorization_endpoint": "https://ehr.example.com/auth/authorize",
  "token_endpoint": "https://ehr.example.com/auth/token",
  "grant_types_supported": ["authorization_code", "client_credentials"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["openid", "fhirUser", "launch", "launch/patient", "patient/*.rs", "offline_access"],
  "capabilities": ["launch-ehr", "launch-standalone", "client-public", "context-ehr-patient",
                   "context-standalone-patient", "permission-patient", "permission-v2", "sso-openid-connect"]
}

capabilities memberi tahu app fitur apa yang didukung: mode launch (launch-ehr, launch-standalone), tipe client (client-public, client-confidential-symmetric, client-confidential-asymmetric), konteks, dan sintaks scope (permission-v1, permission-v2). [3] Untuk browser app, server SHALL mengaktifkan CORS: discovery untuk origin apa pun, token endpoint dan FHIR API hanya untuk origin yang terdaftar. [1]

3. Authorization code + PKCE: kenapa React SPA tidak punya secret

SMART membedakan confidential dan public app berdasarkan satu pertanyaan: "is your app able to protect a secret?" HTML5/JS in-browser app, termasuk SPA, adalah public app karena secret apa pun di dalamnya "can potentially be extracted". [1] Sebagai gantinya: "All SMART apps SHALL support Proof Key for Code Exchange (PKCE)", server SHALL mendukung S256 dan SHALL NOT mendukung plain. [1]

Masalah yang diselesaikan PKCE: public client rentan terhadap authorization code interception; penyerang yang mendapat code bisa menukarnya menjadi access token. Dengan PKCE, app membuat code_verifier acak (43–128 karakter), mengirim code_challenge = BASE64URL(SHA256(code_verifier)) saat authorize, dan baru mengirim code_verifier aslinya saat menukar code. Penyerang yang hanya punya code tidak bisa menukarnya. [6] 

// Hanya untuk dibaca: inilah yang dikerjakan fhirclient untuk Anda (Web Crypto, browser)
const b64url = (b: Uint8Array) =>
  btoa(String.fromCharCode(...b)).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");

const verifier  = b64url(crypto.getRandomValues(new Uint8Array(32)));          // 43 karakter (RFC 7636 §4.1)
const digest    = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
const challenge = b64url(new Uint8Array(digest));                                // dikirim di authorize
// verifier disimpan sementara di sessionStorage, dikirim nanti ke token endpoint

Authorize request (browser di-redirect ke authorization_endpoint), contoh dari IG ditambah dua parameter PKCE: [1]

https://ehr/authorize?
  response_type=code&
  client_id=app-client-id&
  redirect_uri=https%3A%2F%2Fapp%2Fafter-auth&
  launch=xyz123&                                   // hanya EHR launch
  scope=launch+patient%2FObservation.rs+patient%2FPatient.rs+openid+fhirUser&
  state=98wrghuwuogerg97&
  aud=https://ehr/fhir&                             // FHIR base URL; di EHR launch = iss
  code_challenge=...&code_challenge_method=S256
  • state: wajib, tidak bisa ditebak (≥ 122 bit entropi, mis. UUID acak), mencegah CSRF/session fixation; app SHALL memvalidasinya di redirect_uri. [1]
  • aud: wajib, URL server FHIR tujuan; mencegah token sah bocor ke resource server palsu. [1]
  • Authorization code berumur pendek, "usually expiring within around one minute". [1]

Lalu app POST ke token_endpoint (form-urlencoded) dengan grant_type=authorization_code, code, redirect_uri, code_verifier, dan client_id (wajib untuk public app; public app tidak melakukan client authentication). [1] Responsnya: 

{
  "access_token": "eyJhbG...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "launch patient/Observation.rs patient/Patient.rs openid fhirUser",  // bisa beda dari yang diminta!
  "id_token": "eyJ0eX...",       // karena openid fhirUser
  "patient": "123",              // launch context: Patient/123
  "need_patient_banner": true
}

scope di respons "can be different from the scopes requested by the app"; launch context seperti "patient": "123" datang bersama token. Respons token SHALL memakai header Cache-Control: no-store. Access token SHOULD berumur tidak lebih dari satu jam. [1] Setelah itu setiap request FHIR membawa Authorization: Bearer {{access_token}}; resource server memvalidasi masa berlaku, scope, dan aud. [1]

Latihan 2 — Susun alur EHR launch

Susun dari klik di EHR sampai data tampil. Ucapkan setiap langkah dengan suara keras saat memindahkannya.

  1. EHR membuka launch URL app dengan iss dan launch
  2. App GET [iss]/.well-known/smart-configuration
  3. App membuat code_verifier, code_challenge, dan state
  4. Redirect ke authorization_endpoint dengan scope launch patient/Observation.rs, launch, aud
  5. EHR memutuskan (kebijakan, mungkin bertanya ke user), redirect ke redirect_uri dengan code + state
  6. App memvalidasi state, lalu POST ke token_endpoint dengan code + code_verifier
  7. Token response: access_token, scope yang diberikan, patient
  8. GET Observation?patient=123 dengan Authorization: Bearer

Discovery harus sebelum authorize karena dari sanalah app tahu URL authorize dan token. PKCE dan state dibuat sebelum redirect karena challenge dikirim di authorize, sedangkan verifier baru dikirim saat menukar code. Konteks pasien baru diketahui app dari token response, bukan dari launch URL (launch hanya handle opaque).

4. Scopes: patient/, user/, system/, dan .cruds

Sintaks scope resource: (patient | user | system) / (ResourceType | *) . (subset dari cruds) [?param=value]. [2]

BagianArti
patient/data tentang satu pasien yang sedang dalam konteks. "what and not who": siapa pasiennya ditentukan oleh launch context
user/data yang bisa diakses user yang login (bukan hanya data tentang user itu)
system/data yang client sendiri diizinkan akses, tanpa user (Backend Services)
c r u d screate, read (termasuk vread, history instance), update (termasuk patch), delete, search. Harus urut: .rs sah, .dus tidak

Kutipan tabel: [2]

  • v1 vs v2. SMART 1.0 memakai patient/Observation.read. Di v2: .read ⇒ .rs, .write ⇒ .cud, .* ⇒ .cruds; server SHOULD mengiklankan permission-v1 bila masih menerima v1. v2 juga menambah filter berbasis search parameter, mis. patient/Observation.rs?category=…|laboratory. [2]
  • Konteks: launch (EHR launch), launch/patient, launch/encounter (standalone, atau sebagai petunjuk). [2]
  • Identitas: openid fhirUser menghasilkan id_token; klaim fhirUser adalah URL resource user (Patient, Practitioner, PractitionerRole, RelatedPerson, atau Person). [2]
  • Refresh token: offline_access (tetap bisa dipakai walau user tidak online) atau online_access (selama user masih online). Refresh tidak bisa menambah izin baru. [2] [1]
  • Least privilege: minta scope minimum; patient/*.cruds berarti juga semua jenis data yang nanti ditambahkan ke server. Selalu periksa scope yang benar-benar diberikan. [2]
  • Scope ≠ izin penuh: izin dasar user tetap membatasi. Client bisa menerima 200 dengan sebagian hasil dihilangkan dari Bundle, atau 403 untuk write yang tampak diizinkan scope. [2]

Latihan 4 — Scopes

5. Backend Services: job Node tanpa user (dan kaitannya dengan Bulk Data)

Kalau tidak ada user yang mengotorisasi di runtime (data warehouse, sinkronisasi pasien baru, monitoring lab), pakai SMART Backend Services. Profile ini "is designed to work with FHIR Bulk Data Access", jadi inilah cara service Node di lesson 0004 mendapat token untuk $export. [4]

  1. Sekali di awal: daftarkan client dengan public key (JWKS atau URL JWKS). Private key tetap di server Anda. [5]
  2. Setiap butuh token: buat JWT sekali pakai, ditandatangani private key (SHOULD RS384 atau ES384): iss = sub = client_id, aud = token URL, exp maksimal 5 menit ke depan, jti unik (mencegah replay). [5]
  3. POST ke token endpoint: grant_type=client_credentials, client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, client_assertion=<JWT>, scope=system/…. [4]
  4. Token SHALL berumur pendek, expires_in SHOULD NOT melebihi 300 detik, dan refresh token SHOULD NOT diterbitkan: minta token baru saat perlu. [4]
// Payload JWT assertion (contoh IG); header: { "typ": "JWT", "alg": "RS384", "kid": "eee9f17a..." }
{
  "iss": "https://bili-monitor.example.com",          // client_id
  "sub": "https://bili-monitor.example.com",          // client_id
  "aud": "https://authorize.smarthealthit.org/token", // token URL
  "exp": 1422568860,                                  // ≤ 5 menit dari sekarang
  "jti": "random-non-reusable-jwt-id-123"
}

Padanan JS: ini mirip "service account" Google Cloud (JWT ditandatangani private key, ditukar dengan access token), bukan login user. Bedanya dengan app launch: tidak ada redirect, tidak ada PKCE, tidak ada patient context; scope-nya system/ dan dibatasi oleh izin yang sudah diatur saat registrasi. [4]

Latihan 5 — Backend Services

6. React + fhirclient, dan menampilkan CodeableConcept

Library resmi komunitas SMART untuk JS adalah fhirclient (npm, saat ini v3.x), jalan di browser dan Node 18+. Di browser biasanya ada dua halaman: launch page (launch_uri) yang memanggil authorize(), dan index page (redirect_uri) yang memanggil ready(). [7] authorize() berakhir dengan redirect, jadi kode setelahnya mungkin tidak dijalankan. Untuk EHR launch cukup clientId + scope (iss datang dari URL); untuk standalone tambahkan opsi iss. PKCE dipakai otomatis bila server mendukung (pkceMode: "ifSupported", default). [8] 

// launch.tsx: dibuka EHR dengan ?iss=...&launch=...
import { authorize } from "fhirclient/browser";
authorize({ clientId: "my_web_app", scope: "launch openid fhirUser patient/Patient.rs patient/Observation.rs" });

// App.tsx: halaman redirect_uri
import { ready } from "fhirclient/browser";

export function Vitals() {
  const [obs, setObs] = useState<Observation[]>([]);
  useEffect(() => {
    ready()                                                    // tukar code + verifier, lalu kembalikan Client
      .then(client => client.patient.request("Observation", { flat: true, pageLimit: 0 }))  // /Observation?patient=<id>
      .then(setObs);
  }, []);
  return <ul>{obs.map(o => <li key={o.id}>{conceptLabel(o.code)}</li>)}</ul>;
}

client.patient.id berisi ID pasien dari launch context; client.patient.request("Observation") otomatis menjadi /Observation?patient=patient-id; opsi flat mengembalikan array resource (aman walau Bundle.entry kosong), pageLimit: 0 mengambil semua halaman, dan onPage memproses per halaman supaya hemat memori. client.request() juga me-refresh token otomatis bila hampir kedaluwarsa dan ada refresh token. [9]

Menampilkan CodeableConcept. text adalah "the representation of the concept as entered or chosen by the user"; satu Coding bisa ditandai userSelected, dan bila tidak ada yang ditandai, text (bila ada) adalah sumber makna yang diutamakan. display adalah tampilan kode menurut code system-nya. [10] Jadi UI jangan menampilkan coding[0].code mentah: 

function conceptLabel(cc?: CodeableConcept): string {
  if (!cc) return "—";
  if (cc.text) return cc.text;                                    // 1. apa yang dilihat/dipilih user
  const coding = cc.coding ?? [];
  const pick = coding.find(c => c.userSelected && c.display) ?? coding.find(c => c.display);
  if (pick?.display) return pick.display;                         // 2. display dari Coding
  return coding[0]?.code ?? "(tanpa kode)";                       // 3. terakhir: kode mentah
}

Kalau butuh logika per kode (mis. LOINC 8867-4 untuk heart rate), cocokkan system + code, bukan display: display hanya untuk manusia. Lihat lesson 0002 untuk anatomi CodeableConcept/Coding.

Latihan 6 — fhirclient dan CodeableConcept

7. Token di browser, PHI, dan audit (konsep)

  • Penyimpanan token. App SHALL NOT menyimpan bearer token di cookie yang dikirim sebagai clear text, dan SHOULD menyimpan token di storage khusus app, bukan lokasi yang bisa ditemukan sistem. [1] fhirclient di browser menyimpan state-nya (termasuk token response) di sessionStorage. [11] Itu hilang saat tab ditutup, tapi tetap terbaca oleh script hasil XSS, sama seperti localStorage (lihat 0017).
  • Public vs confidential. Data di backend memberi binding refresh token yang lebih kuat, tapi kebocoran server bisa mengenai banyak user; app murni di perangkat lebih rentan per device. Pilih berdasarkan konteks. [12] Dalam interview, sebut opsi backend-for-frontend (React → backend Node sebagai confidential client) bila butuh akses panjang.
  • Jangan bocorkan token. Jangan ikuti reference ke server lain sambil membawa access token; abaikan atau minta akses baru. [1] Jangan pernah menjadi "open redirector" dan selalu lewat TLS. [1]
  • PHI di log. Spesifikasi FHIR R4 memperingatkan risiko seperti "audit logging of the GET parameters into an unprotected audit log": query search FHIR (?name=…&birthdate=…) sudah berisi data pasien. [13]
  • Audit. FHIR punya resource AuditEvent untuk mencatat event keamanan/privasi (siapa mengakses apa, kapan), dipakai untuk reporting dan deteksi penyalahgunaan. [13] [14]

"Bagaimana React app Anda mendapat akses ke data pasien di EHR? Apa itu SMART on FHIR?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"SMART App Launch adalah profile OAuth 2.0, plus OpenID Connect, di atas FHIR. Ada dua cara mulai: EHR launch, EHR membuka launch URL kami dengan iss dan launch; atau standalone, user membuka app langsung dan kami meminta launch/patient. App mengambil [iss]/.well-known/smart-configuration untuk tahu authorize dan token endpoint, lalu redirect ke authorize dengan response_type=code, scopes seperti launch patient/Observation.rs openid fhirUser, state, aud, dan PKCE S256. Karena React SPA adalah public client, tidak ada client secret; PKCE yang melindungi code. Setelah redirect balik, app memvalidasi state, menukar code + code_verifier, dan menerima access token, scope yang benar-benar diberikan, serta patient ID sebagai launch context. Setiap request FHIR membawa Authorization: Bearer. Di React saya pakai fhirclient: authorize() di launch page, ready() di redirect page."

Checklist: apakah Anda menyebut…

  • SMART = profile OAuth 2.0 (+ OIDC) untuk app FHIR?
  • EHR launch (iss + launch) vs standalone (launch/patient)?
  • discovery lewat .well-known/smart-configuration?
  • authorization code + PKCE S256, tanpa client secret di SPA?
  • state divalidasi dan aud = FHIR base URL?
  • token response: access token, scope yang diberikan, patient context; lalu Bearer?

"Itu kasus SMART Backend Services, karena tidak ada user di runtime. "Di React app yang menampilkan data pasien, di mana Anda menyimpan token, dan apa yang Anda lakukan supaya PHI aman?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Token saya anggap sama sensitifnya dengan datanya. SMART meminta token disimpan di storage khusus app dan tidak di cookie yang dikirim tanpa enkripsi. fhirclient menyimpan state-nya di sessionStorage: hilang saat tab ditutup, tapi tetap terbaca kalau ada XSS, jadi CSP dan sanitasi input penting. Access token sebaiknya maksimal satu jam; kalau butuh akses panjang, saya pindahkan pertukaran token ke backend sebagai confidential client atau pola backend-for-frontend. Untuk PHI: scope seminimal mungkin, tidak menulis isi resource atau query string ke log biasa atau analytics, tidak mengikuti reference ke server lain dengan token yang sama, dan akses dicatat di audit log, misalnya resource AuditEvent."

Checklist: apakah Anda menyebut…

  • storage khusus app; jangan cookie cleartext; fhirclient memakai sessionStorage?
  • XSS tetap bisa membaca storage: CSP, sanitasi?
  • token pendek (≤ 1 jam); akses panjang lebih aman lewat backend (confidential/BFF)?
  • scope seminimal mungkin (least privilege)?
  • jangan log PHI atau query string ke log tak terlindungi?
  • audit akses (AuditEvent), jangan kirim token ke server lain?
