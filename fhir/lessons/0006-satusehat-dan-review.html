Bagian 1 · SATUSEHAT, validasi, dan mapping data legacy (±30 menit)

1a. Apa itu SATUSEHAT, dan bagaimana sistem Anda masuk (±8 menit)

SATUSEHAT adalah "ekosistem pertukaran data kesehatan (HIE: Health Information Exchange)" yang menghubungkan sistem fasyankes, regulator, penjamin, dan penyedia layanan digital. Latar belakangnya: lebih dari 400 aplikasi kesehatan pemerintah yang belum terintegrasi dan tidak adanya standar format interoperabilitas. Tujuannya antara lain spesifikasi terstandar memakai HL7 FHIR dan HTTPS REST API, supaya developer bisa memakai bahasa apa pun, serta nomor SATUSEHAT sebagai single identifier pasien. [1]

Versi FHIR: halaman FHIR di dokumentasi hanya menyebut "HL7 FHIR" tanpa nomor versi [15], tetapi base URL-nya memakai path fhir-r4 [2] dan profile resminya diterbitkan sebagai SATUSEHAT FHIR R4 Implementation Guide di Simplifier, dengan canonical seperti https://fhir.kemkes.go.id/r4/StructureDefinition/Patient. [16] Jadi semua yang Anda pelajari di 0001–0005 tentang R4 berlaku di sini; inilah contoh nyata "IG nasional di atas R4" dari lesson 0001.

Kutipan tabel: [2] [4] [6] Organization ID, Client ID, dan Client Secret dilihat setelah login ke portal SATUSEHAT Platform. Pembatasan resource per "Tipe Kode Akses API" (jenis institusi) ada di dokumen unduhan yang tidak saya baca: belum terverifikasi (diakses 2026-10-26). [4]

Autentikasi: OAuth2 client credentials dengan secret. Ini server-to-server, tanpa user dan tanpa redirect: [3]

// Hanya untuk dibaca: service Node (bukan React!) mengambil token SATUSEHAT
const OAUTH = "https://api-satusehat-stg.dto.kemkes.go.id/oauth2/v1";   // sandbox

const res = await fetch(`${OAUTH}/accesstoken?grant_type=client_credentials`, {   // grant_type di query string
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: new URLSearchParams({ client_id: process.env.SS_CLIENT_ID!, client_secret: process.env.SS_CLIENT_SECRET! }),
});
const { access_token, expires_in } = await res.json();   // contoh di docs: "token_type": "BearerToken", "expires_in": "3599"
// setiap request FHIR berikutnya: Authorization: Bearer ${access_token}
  • client_id dan client_secret diperlakukan seperti username dan password aplikasi; keduanya didapat dari Kemenkes. Respons gagal berupa OperationOutcome. [3]
  • Ada rate limit: "1 request per minute after a failed attempt", dan dokumentasi juga memperingatkan generate token baru yang terlalu sering. Konsekuensi desain: cache token di service Node sampai mendekati expires_in, jangan minta token per request. [3]
  • Bandingkan dengan SMART Backend Services (lesson 0005): sama-sama client_credentials tanpa user, tetapi SMART memakai JWT assertion bertanda tangan private key, sedangkan SATUSEHAT memakai client_secret. Karena secret, token tidak boleh diminta dari browser: React app memanggil backend Node Anda, backend yang memanggil SATUSEHAT.

1b. Prasyarat, NIK, dan nomor IHS (±7 menit)

Sebelum mengirim data pendaftaran pasien dan diagnosis, dokumentasi menetapkan langkah persiapan: [5]

Autentikasi→ Organization (struktur organisasi)→ Location (struktur lokasi)→ nomor IHS Practitioner→ nomor IHS Patient→ Encounter, Condition, Observation, …
  • Nomor IHS pasien ({patient-ihs-number}) didapat dari Master Patient Index (MPI) Kemenkes, yang menyimpan data demografi berskala nasional. Nomor ini boleh disimpan di sistem internal, dan memudahkan pelaporan karena data diri pasien tidak perlu dikirim ulang setiap kali. [6] Resource klinis lalu merujuk pasien sebagai "Patient/{patient-ihs-number}". [10]
  • Alur pasien ber-NIK: cari dulu berdasarkan nomor IHS atau NIK. Kalau tidak ketemu, POST Patient dengan NIK sebagai identifier, nama, tanggal lahir, jenis kelamin, alamat, dsb.; data diverifikasi ke DUKCAPIL, dan bila cocok SATUSEHAT membuat nomor IHS baru. Kalau ada elemen yang tidak cocok, API mengembalikan error. [7]
  • Ini adalah id vs identifier dari lesson 0002 dalam versi Indonesia: NIK adalah business identifier, nomor IHS menjadi logical id di server SATUSEHAT, dan nomor rekam medis lokal adalah identifier lain lagi.

Latihan 2 — Prasyarat dan identifier

1c. Validasi terhadap profile (±7 menit)

Spesifikasi dasar FHIR adalah "platform specification" yang biasanya perlu diadaptasi per konteks: elemen mana yang dipakai, fitur API mana, dan terminologi mana untuk elemen tertentu. Adaptasi itu diterbitkan sebagai Implementation Guide berisi Profile (StructureDefinition), ValueSet, dan ConceptMap. [17] Memvalidasi sebuah resource berarti memeriksa: [18]

AspekContoh pertanyaan
StructureAda property yang tidak dikenal spesifikasi?
Cardinalityname wajib (1..*) tapi kosong?
Value domainsbirthDate berformat tanggal FHIR? kode enum sah?
BindingsKode di Coding/CodeableConcept ada di value set yang diikat?
InvariantsAturan co-occurrence (mis. constraint dom-2) terpenuhi?
ProfilesAturan profile dari meta.profile, CapabilityStatement, IG, atau konteks terpenuhi?
Business rulesDuplikat? reference bisa di-resolve? user berhak? (dibuat di luar spesifikasi)
  • $validate. POST [base]/[Resource]/$validate (opsional ?profile=…, mode=create|update|delete) mengembalikan OperationOutcome; "This operation returns a 200 OK whether or not the resource is valid", sedangkan 4xx/5xx berarti validasinya sendiri gagal dijalankan. Operasi ini tidak menyimpan resource. [19] Apakah SATUSEHAT menyediakan endpoint $validate untuk partner: belum terverifikasi (diakses 2026-10-26); yang terdokumentasi adalah validasi saat data dikirim (di bawah).
  • Validasi di SATUSEHAT. Saat resource interoperabilitas dikirim, sistem memvalidasi kode terminologi (ICD-10, ICD-9 CM, LOINC, SNOMED CT, dan code system lain). API Gateway memeriksa request lewat FHIR Processor dulu; kalau ada kesalahan, respons 4xx berupa OperationOutcome dengan issue.severity, issue.code (duplicate, format, value), details.text, dan expression (resource dan field). [13] Apakah server SATUSEHAT juga memeriksa klaim meta.profile secara penuh: belum terverifikasi (diakses 2026-10-26).
  • Aturan format yang sering membuat ditolak: waktu dikirim dalam UTC +00 (17.35 WIB → 2023-08-23T10:35:00+00:00) dan tanggal tidak boleh sebelum 3 Juni 2014; elemen wajib atau tidak mengikuti panduan per use case. [8]
  • Validasi di production itu trade-off. Spesifikasi menyarankan validasi saat development, tapi memperingatkan di production: validasi penuh dengan terminologi mahal, bisa menyebabkan "the loss of critical health care data" karena satu field buruk, dan bisa menolak data historis yang tidak bisa diperbaiki. Anjurannya Postel's law: konservatif saat mengirim, liberal saat menerima. [18] Terjemahan untuk desain Node: validasi sebelum kirim, dan record yang ditolak disimpan bersama OperationOutcome-nya untuk diperbaiki, bukan dibuang.

1d. Mapping data legacy → FHIR, dan ConceptMap (±8 menit)

Mapping punya dua lapis: struktur (tabel/kolom → resource/elemen) dan kode (kode lokal → terminologi standar). Terminologi standar SATUSEHAT: [11]

// Hanya untuk dibaca: satu baris tabel lama → Condition (struktur + kode)
type DiagnosaRow = { no_reg: string; kode_dx: string; ket: string; tgl: string };  // tgl: "2026-10-26 17:35" WIB, tanpa zona

function toCondition(row: DiagnosaRow, ctx: { patientIhs: string; encounterId: string }, map: Map<string, Coding>): Condition {
  const icd = map.get(row.kode_dx);                        // hasil ConceptMap lokal → ICD-10, bisa undefined
  if (!icd) throw new UnmappedCode(row.kode_dx);           // masuk antrean review coder, jangan dikirim asal
  return {
    resourceType: "Condition",
    code: { coding: [icd,                                  // kode standar
                     { system: "https://simrs.rs-contoh.id/fhir/CodeSystem/dx-lokal", code: row.kode_dx }], // kode asal (system ilustrasi)
            text: row.ket },
    subject:   { reference: `Patient/${ctx.patientIhs}` },
    encounter: { reference: `Encounter/${ctx.encounterId}` },
    recordedDate: wibToUtc(row.tgl),                       // "2026-10-26T10:35:00+00:00"
  };
}

Dokumentasi Condition SATUSEHAT menandai code, subject, dan encounter sebagai wajib; elemen lain wajib atau tidak mengikuti panduan per use case, jadi potongan di atas sengaja tidak lengkap. [9] Membawa kode lokal sebagai Coding tambahan sah karena CodeableConcept boleh berisi beberapa Coding untuk konsep yang sama (lesson 0002); apakah SATUSEHAT menerima Coding tambahan dengan system lokal di setiap elemen: belum terverifikasi (diakses 2026-10-26).

ConceptMap adalah resource FHIR untuk menyatakan mapping kode itu secara formal. Profiling R4 menyebut tujuannya: "Map between local and standard terminologies or content models". [17] Yang perlu Anda ucapkan di interview: [20]

  • Satu arah: "Mappings are one way - from the source to the target system"; kebalikannya tidak bisa diasumsikan benar.
  • Terikat konteks: mapping hanya berlaku untuk use case bisnis tertentu; contoh resminya SNOMED CT → ICD-10 untuk analisis data berbeda dengan untuk billing.
  • Equivalence per target: equivalent, equal, wider, narrower, inexact, unmatched, disjoint, dll.; untuk narrower dan inexact alasannya SHALL dijelaskan di comment. [22]
  • Bukan transformasi struktur: ConceptMap memetakan konsep; transformasi instance (tabel → resource) adalah wilayah StructureMap. ConceptMap tidak dirujuk langsung dari resource lain.
  • Dipakai lewat $translate: terminology server menerjemahkan system + code berdasarkan ConceptMap; client harus memeriksa equivalence setiap hasil. [21]
// Bentuk ConceptMap R4 (struktur mengikuti contoh resmi; kode lokal ilustrasi, target dari dokumentasi SATUSEHAT)
{
  "resourceType": "ConceptMap",
  "status": "active",
  "group": [{
    "source": "https://simrs.rs-contoh.id/fhir/CodeSystem/lab-lokal",
    "target": "http://loinc.org",
    "element": [
      { "code": "NADI", "display": "Nadi per menit",
        "target": [{ "code": "8867-4", "display": "Heart rate", "equivalence": "equivalent" }] },
      { "code": "CEK-UMUM", "display": "Paket cek umum",
        "target": [{ "equivalence": "unmatched", "comment": "Paket, bukan satu tes: pecah per pemeriksaan" }] }
    ]
  }]
}

Struktur group.source/target → element.code → target.code/equivalence/comment mengikuti contoh resmi R4. [23] Padanan JS: tabel lookup Map<kodeLokal, Coding> yang diberi metadata (arah, konteks, tingkat kecocokan) dan bisa dipertukarkan antar sistem. Di proyek nyata, tabel ini disusun dan direview oleh coder klinis, bukan developer sendirian.

Bagian 2 · Review acak 0001–0005 (seam penguasaan, ±40 menit)

Istirahat 5 menit dulu. Bagian ini tanpa materi baru: soal kuis dan lisan dari lesson 0001–0005, diacak bersama (interleaving).

Aturan main

  1. Jangan buka catatan, lesson lama, reference, atau tab lain. Yang diuji adalah kemampuan menjawab pertanyaan interview FHIR tanpa catatan. Kalau Anda mengintip, hasilnya tidak berarti.
  2. Soal kuis: pilih satu jawaban. Ada tepat satu soal kuis untuk setiap topik lesson 0001–0005 (37 topik = 37 kuis), jadi setiap topik diuji minimal sekali.
  3. Soal lisan: jawab dengan suara keras (±60–90 detik, boleh direkam di ponsel) sebelum membuka checklist, lalu centang hanya poin yang benar-benar Anda sebut, bukan yang "sebenarnya tahu".
  4. Kriteria lulus per topik (sama seperti seam di track root, mis. review 0007, 0012, dan 0024): soal kuis acak dijawab benar, dan jawaban lisan memenuhi minimal 4 dari 6 poin checklist. Satu kesalahan di topik itu = topik lemah. Topik yang kuisnya benar tapi tidak mendapat soal lisan tampil sebagai Kuis lulus, lisan belum diuji dan belum dihitung lulus.

Urutan soal mengikuti seed yang tampil di bawah. Tombol "Acak ulang" membuat set baru, tapi kerjakan set pertama sampai selesai sebelum mengacak ulang; hasil set pertama itulah yang dilaporkan. Untuk mengulang set yang sama nanti, tambahkan ?seed=NNN di URL. Soal lisan ditarik 6 dari 14 yang ada, jadi topik lain bisa diuji lewat ?seed= berbeda di sesi berikutnya (pengulangan berjarak).

Setelah selesai: laporkan hasilnya ke agent

  1. Setelah semua soal dijawab, ringkasan per topik muncul di bawah soal terakhir.
  2. Tekan Salin (atau blok teks di kotak ringkasan), lalu tempel ke agent di terminal, misalnya: "Ini hasil review 0006 FHIR, tolong dicatat." Sebut juga skor Latihan 5 (bagian 1) dan bagian 3 bila ingin dicatat di NOTES.
  3. Agent menulis learning record "sudah dikuasai" di fhir/learning-records/ hanya untuk topik yang lulus (kuis benar dan lisan minimal 4 dari 6), dengan seed dan skor sebagai bukti. Topik Kuis lulus, lisan belum diuji dicatat di NOTES saja, tanpa learning record.
  4. Topik yang lemah dicatat sebagai baris "Topik lemah FHIR 0006: …" di fhir/NOTES.md, untuk diulang malam ini (lihat ROADMAP: "ulangi soal lisan yang lemah dari review 0006").

Hanya hasil review di bagian 2 ini yang dicatat sebagai bukti penguasaan FHIR. Skor kuis di lesson 0001–0005 dan kuis bagian 1 tidak dihitung.

Kalau ada topik lemah

Jangan baca ulang seluruh lesson. Buka hanya bagian cheat sheet untuk topik itu (±5 menit): anatomi resource + datatype (topik res-) atau REST, search, Bundle (topik rest-); untuk dasar-, bulk-, dan smart- buka bagian yang sama di lesson asalnya. Lalu tutup, dan jelaskan lagi dengan suara keras.

1. "Kami perlu mengirim data kunjungan rawat jalan dari SIMRS ke SATUSEHAT setiap hari. Rancang service Node-nya." (2 menit)
Bandingkan dengan jawaban contoh dan checklist-nya

"Saya pisahkan menjadi job terjadwal yang mengambil kunjungan baru dari SIMRS, mengubahnya ke resource FHIR, lalu mengirim lewat antrean, misalnya BullMQ, supaya ada retry dan backoff. Token client credentials di-cache sampai mendekati expires_in. Prasyarat seperti nomor IHS Patient dan Practitioner diambil sekali lalu disimpan di tabel mapping. Setiap record punya identifier lokal dengan system organisasi, jadi pengiriman ulang tidak membuat duplikat; secara FHIR umum ini conditional create dengan If-None-Exist, dan SATUSEHAT juga menolak duplikat dengan issue duplicate. Respons sukses menyimpan id dari server untuk reference berikutnya; OperationOutcome gagal disimpan per record untuk diperbaiki. Data pasien adalah PHI: tidak masuk log biasa, secret di secret manager, dan ada audit siapa mengirim apa."

Checklist: apakah Anda menyebut…

  • job terjadwal + antrean dengan retry/backoff?
  • token di-cache, secret di server (bukan di React)?
  • prasyarat (nomor IHS Patient/Practitioner, Organization/Location) disimpan sebagai mapping?
  • idempoten lewat identifier (conditional create / penolakan duplikat)?
  • OperationOutcome per record disimpan untuk koreksi dan kirim ulang?
  • PHI: tidak di log biasa, audit akses?

Lulus kalau minimal 4 dari 6. Sumber: 0003 (conditional create, OperationOutcome), 0005 (PHI, audit), bagian 1 di atas.

2. "Ceritakan perjalanan data dari klik di EHR sampai React menampilkan daftar tanda vital pasien." (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"EHR membuka launch URL app dengan iss dan launch. App melakukan discovery di .well-known/smart-configuration, redirect ke authorize dengan PKCE, state, aud, dan scope launch patient/Observation.rs, lalu menukar code dan mendapat token plus patient. Lalu search GET Observation?patient=123&category=vital-signs&_sort=-date&_count=50; hasilnya Bundle searchset, dan halaman berikutnya diambil dari link relation next, bukan URL buatan sendiri. Di React, label diambil dari code.text, lalu display, baru kode mentah; nilai dari valueQuantity dengan satuan UCUM, dan angka decimal dijaga presisinya."

Checklist: apakah Anda menyebut…

  • EHR launch: iss + launch, discovery?
  • authorization code + PKCE, scope patient/Observation.rs, konteks patient?
  • search dengan parameter (patient, category/code, sort, _count)?
  • Bundle searchset + paging lewat link next?
  • CodeableConcept ditampilkan dari text/display, bukan kode mentah?
  • valueQuantity/UCUM atau presisi decimal?

Lulus kalau minimal 4 dari 6. Sumber: 0003, 0004, 0005.

3. "Tim data minta salinan semua Observation tiap malam untuk warehouse. Bagaimana Anda melakukannya?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Bukan search biasa, tapi Bulk Data $export dengan _type=Observation. Autentikasinya SMART Backend Services: JWT assertion, scope system/Observation.rs. Kick-off dengan Prefer: respond-async, dapat 202 dan Content-Location, polling mengikuti Retry-After sampai 200 dengan manifest berisi URL file NDJSON. Setiap file diproses streaming baris per baris dengan readline atau pipeline, insert ke database per batch dengan backpressure, tidak pernah JSON.parse satu file utuh. Malam berikutnya pakai _since = transactionTime dari manifest sebelumnya supaya inkremental."

Checklist: apakah Anda menyebut…

  • $export (bukan search), dengan _type?
  • Backend Services + scope system/?
  • kick-off → 202 → polling (Retry-After) → manifest?
  • NDJSON diproses streaming per baris, batch insert?
  • backpressure / tidak JSON.parse file utuh?
  • inkremental dengan _since = transactionTime?

Lulus kalau minimal 4 dari 6. Sumber: 0004, 0005.

4. "Satu kunjungan menghasilkan Encounter, dua Condition, dan lima Observation. Bagaimana mengirimnya supaya tidak setengah tersimpan?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Di FHIR umum, Bundle transaction ke POST [base]: atomik, semua berhasil atau semua gagal. Encounter diberi fullUrl urn:uuid:… dan Condition/Observation merujuk ke urn itu; server mengganti reference dengan id asli. batch tidak cocok karena setiap entry independen dan tidak boleh saling merujuk. Untuk retry aman, setiap entry memakai conditional create berdasarkan identifier. Untuk SATUSEHAT khususnya, panduan IGD menyebut beberapa resource dikirim bersamaan memakai bundle; detail tipe Bundle dan aturan atomiknya perlu saya cek lagi di panduan use case."

Checklist: apakah Anda menyebut…

  • Bundle transaction, atomik?
  • fullUrl urn:uuid: untuk saling merujuk?
  • kenapa bukan batch (independen, tanpa ketergantungan)?
  • conditional create / identifier untuk retry idempoten?
  • respons transaction-response berisi lokasi/id per entry?
  • jujur tentang detail SATUSEHAT yang perlu dicek di panduan?

Lulus kalau minimal 4 dari 6. Sumber: 0003. Dukungan Bundle di SATUSEHAT: panduan interoperabilitas IGD menyebut Medication dan MedicationDispense "dikirimkan secara bersamaan menggunakan bundle" [24]; tipe Bundle dan perilaku atomiknya belum terverifikasi (diakses 2026-10-26).

5. "Pasien yang sama terdaftar di tiga sistem dengan nomor berbeda. Bagaimana FHIR membantu, dan apa jebakannya?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Logical id berbeda di setiap server dan tidak boleh dipakai sebagai identitas lintas sistem. Yang dipakai adalah identifier: pasangan system + value, misalnya NIK dengan system https://fhir.kemkes.go.id/id/nik, plus nomor rekam medis per rumah sakit dengan system masing-masing. Satu Patient boleh punya banyak identifier. Search memakai token identifier=system|value, dan create memakai conditional create supaya tidak dobel. Di Indonesia, MPI SATUSEHAT memberi nomor IHS setelah verifikasi NIK ke DUKCAPIL. Jebakannya: pasien tanpa NIK, misalnya bayi, punya alur sendiri, dan value tanpa system tidak bermakna."

Checklist: apakah Anda menyebut…

  • id vs identifier (id lokal per server)?
  • system + value, beberapa identifier per Patient?
  • search token identifier=system|value?
  • conditional create untuk mencegah duplikat?
  • MPI/nomor IHS, verifikasi NIK ke DUKCAPIL?
  • jebakan: pasien tanpa NIK, value tanpa system?

Lulus kalau minimal 4 dari 6. Sumber: 0002, 0003, bagian 1b. Alur pasien tanpa NIK dan bayi ada di menu MPI dokumentasi SATUSEHAT (pasien-bayi, pasien-no-nik) dan tidak dibahas di lesson ini.

6. "Kenapa kami memakai FHIR R4, bukan R5? Dan apa itu profile SATUSEHAT?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"R4 adalah rilis pertama yang memuat konten Normative, jadi bagian intinya stabil dan dijaga kompatibilitasnya; R5 masih Trial Use. Ekosistem IG besar dibangun di atas R4, dan SATUSEHAT juga: base URL-nya fhir-r4 dan IG-nya SATUSEHAT FHIR R4 Implementation Guide. Profile adalah StructureDefinition yang mempersempit resource dasar untuk konteks tertentu: elemen wajib, cardinality, binding terminologi seperti ICD-10 dan LOINC, serta extension Indonesia seperti kode wilayah administratif. Resource bisa mengklaim profile di meta.profile, dan validator memeriksa aturan itu."

Checklist: apakah Anda menyebut…

  • R4 = konten Normative pertama; R5 Trial Use?
  • IG nasional dibangun di atas R4, termasuk SATUSEHAT?
  • profile = StructureDefinition berisi constraint?
  • contoh constraint: elemen wajib, binding terminologi?
  • extension untuk data lokal (mis. kode wilayah)?
  • meta.profile + validasi?

Lulus kalau minimal 4 dari 6. Sumber: 0001, bagian 1a dan 1c.
