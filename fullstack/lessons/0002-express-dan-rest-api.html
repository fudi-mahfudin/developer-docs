Express dan REST API: status code, middleware, error handling, Zod

Mendesain resource REST untuk inventaris aset, memilih status code sesuai RFC 9110, lalu menyusun API Express 5 dengan middleware, error handling terpusat, validasi Zod, dan layering route → service → Prisma

Target lesson ini: Anda bisa menulis daftar endpoint REST untuk resource "aset" beserta status code-nya, menjelaskan urutan middleware Express dan bagaimana error async sampai ke error handler di Express 5, dan menunjukkan di layer mana validasi, aturan bisnis, dan query database diletakkan.

1. Desain resource REST

REST memodelkan API sebagai resource (kata benda, jamak) yang dimanipulasi dengan method HTTP. Method punya semantik baku: GET dan HEAD bersifat safe (tidak mengubah state), dan PUT serta DELETE bersifat idempotent (mengulang request yang sama memberi efek yang sama). POST tidak idempotent. [1]

EndpointArtiStatus sukses
GET /aset?page=1&q=laptop&kategoriId=2List dengan pagination, search, filter200
GET /aset/:idDetail satu aset200
POST /asetBuat aset baru201 + header Location
PATCH /aset/:idUbah sebagian field200 (body aset baru)
DELETE /aset/:idHapus (atau soft delete, lesson 0005)204 tanpa body
GET /karyawan/:id/peminjamanSub-resource: peminjaman milik satu karyawan200

Hindari kata kerja di URL (/getAset, /hapusAset). Aksi yang bukan CRUD murni boleh dimodelkan sebagai resource baru, misalnya POST /peminjaman untuk "pinjamkan aset".

2. Status code yang sering ditanya (RFC 9110)

KodeKapan dipakai di API aset
200 OKGET berhasil, PATCH berhasil dan mengembalikan data
201 CreatedPOST membuat resource; header Location menunjuk resource baru [2]
204 No ContentDELETE berhasil, tidak ada body
400 Bad RequestRequest rusak: JSON tidak valid, query param bukan angka
401 UnauthorizedBelum login atau token tidak valid (sebenarnya berarti "unauthenticated") [3]
403 ForbiddenSudah login, tapi tidak berhak (staf biasa mencoba menghapus aset) [4]
404 Not FoundAset dengan id itu tidak ada
409 ConflictBentrok dengan state saat ini: kode aset sudah dipakai, aset sedang dipinjam [5]
422 Unprocessable ContentJSON-nya valid tapi isinya melanggar aturan (harga negatif) [6]
500 Internal Server ErrorBug atau kegagalan tak terduga; detailnya hanya di log, tidak dikirim ke klien

Banyak tim memakai 400 untuk semua error validasi. Itu juga wajar. Yang penting konsisten dan terdokumentasi, misalnya: "validasi Zod gagal → 400 dengan daftar field yang salah".

3. Routing dan middleware Express 5

Middleware adalah fungsi (req, res, next) yang dijalankan berurutan sesuai urutan app.use() dan pendaftaran route. Ia bisa membaca/mengubah req dan res, mengakhiri request, atau memanggil next() untuk lanjut. [7] express.Router() mengelompokkan route per resource. [8] 

import express from 'express';
import { asetRouter } from './aset/aset.routes.js';
import { requireAuth } from './auth/require-auth.js';
import { errorHandler } from './errors/error-handler.js';

const app = express();
app.use(express.json());                 // 1. parse body JSON
app.use(requestLogger);                  // 2. log method, path, durasi
app.use('/aset', requireAuth, asetRouter); // 3. auth, lalu route aset
app.use((req, res) => res.status(404).json({ error: 'Tidak ditemukan' }));
app.use(errorHandler);                   // 4. paling akhir: error handler
export { app };

4. Error handling terpusat (Express 5)

Di Express 5, route handler dan middleware yang mengembalikan Promise otomatis memanggil next(err) bila Promise-nya reject atau melempar error. Karena fungsi async selalu mengembalikan Promise, error-nya sampai ke Express tanpa kode tambahan. [9] Di Express 4, error di handler async tidak tertangkap kecuali dibungkus try/catch + next(err) atau memakai paket seperti express-async-errors. [10]

Error handler dibedakan dari middleware biasa oleh empat argumen (err, req, res, next) dan didaftarkan paling akhir. Bila header respons sudah terkirim, delegasikan ke handler bawaan dengan next(err). [9]

export class HttpError extends Error {
  constructor(status, message, details) {
    super(message);
    this.status = status;
    this.details = details;
  }
}

export function errorHandler(err, req, res, next) {
  if (res.headersSent) return next(err);
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: err.message, details: err.details });
  }
  req.log?.error(err);                    // stack trace hanya di log server
  res.status(500).json({ error: 'Terjadi kesalahan di server' });
}

5. Validasi dengan Zod

Zod adalah library validasi skema untuk TypeScript/JavaScript (versi 4). schema.safeParse(data) tidak melempar error, tapi mengembalikan objek dengan success; bila gagal, daftar masalahnya ada di error.issues. [11] z.coerce.number() mengubah string query param menjadi angka, dan .partial() membuat semua field opsional, cocok untuk PATCH. [12] 

import { z } from 'zod';

export const asetCreateSchema = z.object({
  kode: z.string().regex(/^[A-Z]{3}-\d{3}$/),       // contoh: LTP-001
  nama: z.string().min(1).max(100),
  kategoriId: z.number().int().positive(),
  harga: z.number().nonnegative(),
  status: z.enum(['TERSEDIA', 'DIPINJAM', 'RUSAK']).default('TERSEDIA'),
});
export const asetUpdateSchema = asetCreateSchema.partial();

export const validate = (schema) => (req, res, next) => {
  const result = schema.safeParse(req.body);
  if (!result.success) throw new HttpError(400, 'Validasi gagal', result.error.issues);
  req.body = result.data;                 // data yang sudah bersih dan bertipe
  next();
};

6. Layering: route → service → Prisma

Route: HTTP (path, status, validasi)→ Service: aturan bisnis→ Prisma: query database
  • Route hanya tahu HTTP: ambil input, panggil service, pilih status code. Tidak ada query di sini.
  • Service berisi aturan bisnis ("aset yang sedang dipinjam tidak boleh dihapus") dan tidak tahu req/res, sehingga bisa dipakai ulang dan di-test tanpa HTTP.
  • Prisma adalah ORM: prisma.aset.findUnique(...) diterjemahkan menjadi SQL berparameter. [13]
// aset.routes.js
export const asetRouter = express.Router();
asetRouter.get('/:id', async (req, res) => {
  res.json(await asetService.detail(Number(req.params.id)));
});
asetRouter.post('/', validate(asetCreateSchema), async (req, res) => {
  const aset = await asetService.buat(req.body);
  res.status(201).location(`/aset/${aset.id}`).json(aset);
});

// aset.service.js
export async function detail(id) {
  const aset = await prisma.aset.findUnique({ where: { id }, include: { kategori: true } });
  if (!aset) throw new HttpError(404, 'Aset tidak ditemukan');
  return aset;
}

Tidak ada try/catch di route: di Express 5 error dari await otomatis diteruskan ke errorHandler. Pelanggaran unique dari database (Prisma error P2002) bisa diterjemahkan ke 409 di service atau di error handler. [14]

Latihan: tanpa melihat tabel, sebutkan status code untuk (a) membuat aset dengan kode yang sudah ada, (b) staf biasa menghapus aset, (c) token kedaluwarsa, (d) hapus berhasil. Jawaban: 409, 403, 401, 204.
