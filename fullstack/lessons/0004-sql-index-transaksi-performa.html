SQL: index, transaksi, dan performa

Kapan index membantu dan kapan merugikan, cara membaca EXPLAIN, transaksi dan isolation level untuk kasus "pinjam aset", masalah N+1 di Prisma, dan pagination OFFSET vs keyset, dengan catatan perbedaan PostgreSQL dan MySQL

Target lesson ini: Anda bisa memilih index (termasuk urutan kolom composite index) untuk query di skema inventaris aset, membuktikannya dengan EXPLAIN ANALYZE, menulis transaksi "pinjam aset" yang aman dari race condition, mengenali dan memperbaiki N+1, dan menjelaskan kenapa keyset pagination lebih stabil daripada OFFSET.

Semua contoh memakai skema lesson 0003: kategori, karyawan, aset, peminjaman.

1. Index B-tree dan composite index

Index adalah struktur data terpisah yang membuat pencarian baris tidak perlu membaca seluruh tabel. Jenis default di PostgreSQL adalah B-tree, yang menangani perbandingan =, <, >, BETWEEN, IN, IS NULL, dan pengurutan. [1] PRIMARY KEY dan UNIQUE otomatis membuat index. Foreign key tidak: PostgreSQL tidak otomatis mengindex kolom yang merujuk, padahal JOIN dan DELETE di tabel induk membutuhkannya. [2] 

-- JOIN dan "riwayat pinjam aset X" butuh index di kolom foreign key
CREATE INDEX idx_peminjaman_aset ON peminjaman (aset_id);
CREATE INDEX idx_peminjaman_karyawan ON peminjaman (karyawan_id);

-- Halaman daftar aset: filter kategori, lalu status
CREATE INDEX idx_aset_kategori_status ON aset (kategori_id, status);

-- Partial unique index: satu aset hanya boleh punya SATU peminjaman aktif
CREATE UNIQUE INDEX uq_peminjaman_aktif ON peminjaman (aset_id)
  WHERE tanggal_kembali IS NULL;

Urutan kolom composite penting. Index (kategori_id, status) paling efisien bila ada kondisi pada kolom paling kiri. [3] Ia membantu WHERE kategori_id = 2 dan WHERE kategori_id = 2 AND status = 'TERSEDIA', tapi hampir tidak membantu WHERE status = 'TERSEDIA' saja. Aturan praktis: kolom dengan kondisi kesamaan (=) dulu, kolom range atau ORDER BY di belakang.

Partial index hanya mengindex baris yang memenuhi WHERE-nya. Index uq_peminjaman_aktif di atas sekaligus menjadi aturan bisnis: database menolak peminjaman aktif kedua untuk aset yang sama. [4]

Kapan index merugikan:

  • Setiap INSERT/UPDATE/DELETE juga harus memperbarui semua index tabel itu, jadi index yang tidak dipakai hanya menambah biaya tulis dan ruang disk. [5]
  • Kolom dengan sedikit nilai berbeda (status dengan 3 nilai) atau tabel kecil: planner sering memilih membaca seluruh tabel (sequential scan) karena lebih murah.
  • WHERE nama ILIKE '%laptop%' tidak bisa memakai B-tree karena pola diawali wildcard. Untuk pencarian teks seperti ini dibutuhkan jenis index lain (misalnya GIN dengan ekstensi trigram) atau full-text search.

2. EXPLAIN dan EXPLAIN ANALYZE

EXPLAIN menampilkan rencana eksekusi yang dipilih planner beserta estimasi biaya dan jumlah baris. EXPLAIN ANALYZE benar-benar menjalankan query lalu menambahkan waktu dan jumlah baris aktual. Karena dijalankan, bungkus EXPLAIN ANALYZE untuk UPDATE/DELETE di dalam BEGIN ... ROLLBACK. [6] 

EXPLAIN ANALYZE
SELECT * FROM peminjaman WHERE aset_id = 42;

-- Sebelum index (ilustrasi):
--   Seq Scan on peminjaman  (actual time=0.02..18.4 rows=7 loops=1)
--     Filter: (aset_id = 42)
--     Rows Removed by Filter: 199993
-- Sesudah CREATE INDEX idx_peminjaman_aset:
--   Index Scan using idx_peminjaman_aset on peminjaman  (actual time=0.03..0.05 rows=7 loops=1)

Yang dibaca saat interview: jenis scan (Seq Scan vs Index Scan/Index Only Scan/Bitmap Heap Scan), selisih besar antara baris estimasi dan aktual (statistik usang, jalankan ANALYZE), dan "Rows Removed by Filter" yang besar (tanda index yang hilang). [7]

3. Transaksi, ACID, dan isolation level

Transaksi menggabungkan beberapa langkah menjadi satu operasi semua-atau-tidak-sama-sekali. [8] ACID: Atomicity (semua langkah sukses atau semua dibatalkan), Consistency (constraint tetap terpenuhi), Isolation (transaksi bersamaan tidak saling mengganggu sesuai level isolasinya), Durability (setelah COMMIT, data bertahan walau server mati). 

-- Pinjam aset 42 untuk karyawan 7: dua perubahan, satu transaksi
BEGIN;
UPDATE aset SET status = 'DIPINJAM'
WHERE id = 42 AND status = 'TERSEDIA';       -- 0 baris berubah = sudah dipinjam orang lain
INSERT INTO peminjaman (aset_id, karyawan_id) VALUES (42, 7);
COMMIT;                                      -- atau ROLLBACK bila UPDATE mengubah 0 baris

Race condition klasik: dua admin meminjamkan aset yang sama pada detik yang sama. Pertahanannya berlapis: UPDATE ... WHERE status = 'TERSEDIA' (atomik per baris; transaksi kedua menunggu lalu mengubah 0 baris), atau SELECT ... FOR UPDATE untuk mengunci baris dulu, ditambah partial unique index di bagian 1 sebagai jaring pengaman terakhir.

Sumber tabel: dokumentasi PostgreSQL 18. [9] Dirty read = membaca data transaksi lain yang belum di-commit; non-repeatable read = membaca baris yang sama dua kali dan hasilnya berubah; phantom read = menjalankan query yang sama dua kali dan himpunan barisnya berubah. Level lebih tinggi lebih aman tapi transaksi bisa gagal dengan serialization error dan harus diulang.

Di Prisma 7, transaksi interaktif memakai $transaction dengan callback; error yang dilempar di dalamnya membatalkan seluruh transaksi. [10]

await prisma.$transaction(async (tx) => {
  const { count } = await tx.aset.updateMany({
    where: { id: asetId, status: 'TERSEDIA' },
    data: { status: 'DIPINJAM' },
  });
  if (count === 0) throw new HttpError(409, 'Aset sedang dipinjam');
  await tx.peminjaman.create({ data: { asetId, karyawanId } });
});

4. N+1 dan cara Prisma menghindarinya

N+1 adalah pola satu query untuk daftar (1), lalu satu query tambahan untuk setiap baris (N). 50 peminjaman = 51 round-trip ke database.

// N+1: satu query per peminjaman
const daftar = await prisma.peminjaman.findMany({ where: { tanggalKembali: null } });
for (const p of daftar) {
  p.aset = await prisma.aset.findUnique({ where: { id: p.asetId } });
}

// Perbaikan: muat relasi sekaligus dengan include
const daftar2 = await prisma.peminjaman.findMany({
  where: { tanggalKembali: null },
  include: { aset: true, karyawan: true },
});

Dengan include, Prisma memuat relasi tanpa query per baris. Strateginya diatur relationLoadStrategy: "join" mengambil semua data dalam satu query (LATERAL JOIN di PostgreSQL), "query" mengirim satu query per tabel lalu menggabungkannya di aplikasi; opsi ini masih Preview (relationJoins) di Prisma 7. [11] Dua-duanya bukan N+1: jumlah query tetap, tidak tumbuh dengan jumlah baris. Bila datanya sudah berupa daftar id, pakai findMany({ where: { id: { in: ids } } }).

5. Pagination: OFFSET vs keyset

Baris yang dilewati OFFSET tetap harus dihitung di server, jadi OFFSET besar lambat. [12] Selain itu, bila ada baris baru disisipkan di antara dua permintaan, halaman berikutnya bisa menampilkan baris ganda atau melewatkan baris.

-- OFFSET: mudah, bisa lompat ke halaman 37, makin lambat di halaman jauh
SELECT id, kode, nama FROM aset ORDER BY id LIMIT 20 OFFSET 720;

-- Keyset: "lanjutkan setelah id terakhir yang sudah dilihat", memakai index PK
SELECT id, kode, nama FROM aset WHERE id > 740 ORDER BY id LIMIT 20;

Di Prisma 7, OFFSET = skip/take, keyset = cursor + skip: 1 + take; dokumentasinya juga menyebut offset makin mahal saat offset membesar. [13] Untuk tabel admin internal dengan ribuan baris, OFFSET dengan nomor halaman biasanya cukup. Keyset dipilih untuk data besar, infinite scroll, atau ekspor.

Beda di MySQL (MySQL 8.4 LTS):
  • Id otomatis memakai AUTO_INCREMENT, bukan GENERATED ALWAYS AS IDENTITY/SERIAL. [14]
  • Upsert: PostgreSQL INSERT ... ON CONFLICT (kode) DO UPDATE SET ... [15]; MySQL INSERT ... ON DUPLICATE KEY UPDATE .... [16]
  • Isolation level default InnoDB adalah REPEATABLE READ, bukan READ COMMITTED. [17]
  • InnoDB mewajibkan index di kolom foreign key dan membuatnya otomatis bila belum ada. [18]
  • Partial index (CREATE INDEX ... WHERE) tidak ada; aturan "satu peminjaman aktif per aset" dijaga di transaksi aplikasi.
  • Window function dan CTE baru ada di MySQL ≥ 8.0; EXPLAIN ANALYZE ada dan selalu memakai format TREE. [19]

Pertanyaan interview

Query lambat di production. Apa langkah Anda?
Temukan query-nya dulu (log slow query atau monitoring), jalankan EXPLAIN ANALYZE di data yang mirip production, cari Seq Scan pada tabel besar atau estimasi baris yang meleset jauh, lalu perbaiki: tambah index yang sesuai, tulis ulang query, atau jalankan ANALYZE. Ukur ulang setelah perubahan.
Kenapa tidak mengindex semua kolom?
Setiap index memperlambat tulis dan memakan disk, dan index pada kolom dengan sedikit nilai berbeda jarang dipakai planner. Index dibuat untuk pola query nyata, misalnya kolom foreign key dan kolom filter halaman daftar.
Index composite (a, b): apakah membantu query WHERE b = ??
Hampir tidak. Composite index paling efisien bila ada kondisi pada kolom paling kiri. Untuk WHERE b = ? saja, buat index terpisah di b atau balik urutannya bila pola query utamanya memang dimulai dari b.
Jelaskan ACID dengan contoh.
Meminjamkan aset = ubah status aset + buat baris peminjaman. Atomicity: keduanya jadi atau tidak sama sekali. Consistency: constraint seperti foreign key dan unique tetap terpenuhi. Isolation: dua admin yang meminjamkan aset yang sama tidak menghasilkan dua peminjaman. Durability: setelah COMMIT, data tidak hilang walau server restart.
Apa isolation level default PostgreSQL dan MySQL?
PostgreSQL READ COMMITTED, MySQL InnoDB REPEATABLE READ. Di READ COMMITTED, setiap statement melihat data yang sudah di-commit saat statement itu mulai, jadi dua SELECT di satu transaksi bisa memberi hasil berbeda.
Apa itu N+1 dan bagaimana mendeteksinya?
Satu query untuk daftar lalu satu query per baris. Terdeteksi dari log query yang menampilkan puluhan query serupa untuk satu request, atau dari await query di dalam loop. Perbaikannya JOIN, include di Prisma, atau satu query dengan IN (...).
OFFSET atau keyset pagination?
OFFSET sederhana dan mendukung lompat ke halaman tertentu, tapi lambat di halaman jauh dan bisa menggandakan atau melewatkan baris saat data berubah. Keyset (WHERE id > last_id) cepat dan stabil, tapi hanya maju/mundur berurutan. Untuk tabel admin kecil OFFSET cukup.

Tulis query

Soal 1. Halaman daftar aset sering memanggil query di bawah dan lambat. Index apa yang Anda buat?

SELECT id, kode, nama, harga
FROM aset
WHERE kategori_id = $1 AND status = 'TERSEDIA' AND deleted_at IS NULL
ORDER BY tanggal_beli DESC
LIMIT 20;

-- Jawaban:
CREATE INDEX idx_aset_daftar ON aset (kategori_id, status, tanggal_beli DESC)
  WHERE deleted_at IS NULL;

Penjelasan: dua kolom dengan kondisi kesamaan (kategori_id, status) di depan, lalu kolom ORDER BY, sehingga PostgreSQL bisa membaca 20 baris pertama langsung berurutan dari index tanpa sort. Bagian WHERE deleted_at IS NULL membuat partial index yang lebih kecil karena aset terhapus tidak pernah ditampilkan. Buktikan dengan EXPLAIN ANALYZE sebelum dan sesudah.

Soal 2. Tampilkan halaman berikutnya dari riwayat peminjaman (terbaru dulu, 20 per halaman) dengan keyset pagination. Baris terakhir halaman sebelumnya: tanggal_pinjam = '2026-10-03', id = 812.

SELECT p.id, p.tanggal_pinjam, a.kode, kr.nama
FROM peminjaman p
JOIN aset a      ON a.id = p.aset_id
JOIN karyawan kr ON kr.id = p.karyawan_id
WHERE (p.tanggal_pinjam, p.id) < ('2026-10-03', 812)
ORDER BY p.tanggal_pinjam DESC, p.id DESC
LIMIT 20;

Penjelasan: tanggal_pinjam tidak unik, jadi kunci keyset ditambah id sebagai pemecah seri. Perbandingan row value (a, b) < (x, y) berarti a < x OR (a = x AND b < y), sama persis dengan urutan ORDER BY. Index pendukungnya (tanggal_pinjam DESC, id DESC).
