Lesson 0005 · Fullstack · ±30 menit

CRUD end-to-end: fitur "Aset" dari halaman Next.js sampai tabel PostgreSQL

Satu fitur utuh langkah demi langkah: skema Prisma, migrasi, endpoint Express, halaman Next.js, loading/error state, dan test, dengan auth, CORS, CSRF, XSS, SQL injection, dan RBAC disisipkan tepat di langkah tempat risikonya muncul

Target lesson ini: Anda bisa menjawab "jelaskan langkah membuat fitur CRUD dari frontend sampai backend" dalam ±3 menit, menyebut potongan kode kunci di setiap langkah, dan menunjukkan di langkah mana setiap kontrol keamanan dipasang dan kenapa.

Fitur yang dibangun: tim administrasi bisa melihat daftar aset (dengan pencarian, filter kategori/status, dan pagination), melihat detail, menambah, mengubah, dan menghapus aset. Hanya role ADMIN yang boleh mengubah dan menghapus.

1. Skema (Prisma)→ 2. Migrasi→ 3. API (Express + Zod)→ 4. UI (Next.js)→ 5. Test

Langkah 1: skema Prisma

Tabel aset dari lesson 0003 ditulis ulang di schema.prisma. Nama model dan field memakai camelCase di JavaScript, dipetakan ke nama tabel/kolom snake_case dengan @map/@@map. [1]

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"        // URL koneksi ada di prisma.config.ts (Prisma 7)
}

enum StatusAset {
  TERSEDIA
  DIPINJAM
  RUSAK
}
model Aset {
  id          Int          @id @default(autoincrement())
  kode        String       @unique
  nama        String
  kategoriId  Int          @map("kategori_id")
  kategori    Kategori     @relation(fields: [kategoriId], references: [id])
  harga       Decimal      @db.Decimal(12, 2)
  status      StatusAset   @default(TERSEDIA)
  tanggalBeli DateTime     @map("tanggal_beli") @db.Date
  deletedAt   DateTime?    @map("deleted_at")
  peminjaman  Peminjaman[]

  @@index([kategoriId, status])
  @@map("aset")
}

Di Prisma 7, URL database ditulis di prisma.config.ts lewat env("DATABASE_URL"), bukan di schema.prisma. [2] Di sini status dibuat enum (menjadi tipe ENUM PostgreSQL) sebagai ganti CHECK di lesson 0003; keduanya sah.

Langkah 2: migrasi

# Development: buat file SQL migrasi dari perubahan skema, lalu terapkan ke DB lokal
npx prisma migrate dev --name tambah_aset
#   -> prisma/migrations/20261116090000_tambah_aset/migration.sql

# Prisma 7: generate client dijalankan sendiri
npx prisma generate

# Production (di pipeline deploy): hanya menerapkan migrasi yang sudah di-commit
npx prisma migrate deploy

migrate dev menghasilkan file migration.sql yang di-commit ke Git, jadi perubahan skema ikut di-review seperti kode. [3] Sejak Prisma 7, migrate dev tidak lagi otomatis menjalankan prisma generate, dan client dibuat dengan driver adapter seperti @prisma/adapter-pg. [4] 

// src/db.js
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from './generated/prisma/client.js';

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
export const prisma = new PrismaClient({ adapter });

Migrasi yang mengubah kolom berisi data (rename, ubah tipe) dilakukan bertahap: tambah kolom baru, isi datanya, ubah kode, baru hapus kolom lama. Selalu backup database sebelum migrate deploy di production.

Langkah 3: endpoint Express

Lima endpoint mengikuti desain di lesson 0002. Yang baru di sini: list dengan pagination, search, dan filter. Query string divalidasi Zod; z.coerce.number() mengubah "2" menjadi 2.

const listQuery = z.object({
  q: z.string().trim().max(50).optional(),
  kategoriId: z.coerce.number().int().positive().optional(),
  status: z.enum(['TERSEDIA', 'DIPINJAM', 'RUSAK']).optional(),
  page: z.coerce.number().int().min(1).default(1),
  pageSize: z.coerce.number().int().min(1).max(100).default(20),
});

asetRouter.get('/', async (req, res) => {
  const parsed = listQuery.safeParse(req.query);
  if (!parsed.success) throw new HttpError(400, 'Query tidak valid', parsed.error.issues);
  res.json(await asetService.list(parsed.data));
});
export async function list({ q, kategoriId, status, page, pageSize }) {
  const where = {
    deletedAt: null,
    ...(kategoriId && { kategoriId }),
    ...(status && { status }),
    ...(q && { OR: [
      { kode: { contains: q, mode: 'insensitive' } },
      { nama: { contains: q, mode: 'insensitive' } },
    ] }),
  };
  const [data, total] = await prisma.$transaction([
    prisma.aset.findMany({ where, include: { kategori: true }, orderBy: { id: 'desc' },
      skip: (page - 1) * pageSize, take: pageSize }),
    prisma.aset.count({ where }),
  ]);
  return { data, total, page, pageSize };
}

mode: 'insensitive' adalah filter case-insensitive yang didukung Prisma untuk PostgreSQL. [5] count memakai where yang sama supaya total halaman sesuai filter.

Keamanan: SQL injection. SQL injection terjadi bila input pengguna disambung ke string SQL sehingga bisa mengubah struktur query. Pertahanan utamanya query berparameter (prepared statement). [6] Query builder Prisma dan $queryRaw dengan tagged template sudah berparameter; $queryRawUnsafe dengan string hasil sambungan input berisiko SQL injection. [7] Contoh salah: $queryRawUnsafe("... WHERE nama LIKE '%" + q + "%'"). Contoh benar: $queryRaw`... WHERE nama ILIKE ${'%' + q + '%'}`.

Update dan delete hanya untuk ADMIN. Delete memakai soft delete: kolom deletedAt diisi, baris tidak dihapus, sehingga riwayat peminjaman yang merujuk aset itu tetap utuh dan bisa diaudit.

asetRouter.patch('/:id', requireRole('ADMIN'), validate(asetUpdateSchema), async (req, res) => {
  res.json(await asetService.ubah(Number(req.params.id), req.body));
});
asetRouter.delete('/:id', requireRole('ADMIN'), async (req, res) => {
  await asetService.hapus(Number(req.params.id));
  res.status(204).end();
});

export async function hapus(id) {
  const aktif = await prisma.peminjaman.count({ where: { asetId: id, tanggalKembali: null } });
  if (aktif > 0) throw new HttpError(409, 'Aset sedang dipinjam');
  const { count } = await prisma.aset.updateMany({
    where: { id, deletedAt: null }, data: { deletedAt: new Date() },
  });
  if (count === 0) throw new HttpError(404, 'Aset tidak ditemukan');
}

Auth: session vs JWT, cookie httpOnly

Session (server-side)JWT
Isi cookie/tokenID acak; data user disimpan di server (tabel session atau Redis)Klaim (id, role, kedaluwarsa) yang ditandatangani, dibawa klien [8]
Logout / cabut aksesHapus baris session, langsung berlakuToken tetap valid sampai exp, kecuali ada daftar blokir
Cocok untukAplikasi internal satu domain (pilihan di sini)Banyak service yang memverifikasi token tanpa database bersama

Atribut HttpOnly membuat cookie tidak bisa dibaca JavaScript lewat document.cookie, sehingga XSS tidak bisa mencuri session ID. [9] Secure hanya mengirim cookie lewat HTTPS, dan SameSite=Lax tidak mengirim cookie pada request POST lintas situs. [10] Session ID harus acak dan panjang, dan dibuat ulang setelah login. [11] Password disimpan sebagai hash dengan algoritma lambat seperti Argon2id atau bcrypt, tidak pernah plaintext. [12] 

// POST /auth/login (setelah password diverifikasi)
res.cookie('sid', sesi.id, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 8 * 3600 * 1000 });

// RBAC sederhana: role disimpan di karyawan.role, dicek per endpoint
export const requireRole = (...roles) => (req, res, next) => {
  if (!req.user) throw new HttpError(401, 'Belum login');
  if (!roles.includes(req.user.role)) throw new HttpError(403, 'Tidak berhak');
  next();
};

RBAC (role-based access control) memberi izin berdasarkan role, bukan per orang. Pemeriksaannya wajib di server untuk setiap request dan default-nya menolak; menyembunyikan tombol "Hapus" di UI hanya kenyamanan, bukan keamanan. [13]

CORS

CORS (Cross-Origin Resource Sharing) adalah mekanisme browser: header seperti Access-Control-Allow-Origin dari server memberi tahu browser apakah JavaScript dari origin lain boleh membaca respons. [14] Di arsitektur ini, Next.js memanggil Express dari server ke server, sehingga CORS tidak berlaku. CORS baru perlu bila Client Component memanggil API langsung dari browser. Saat itu, pakai allowlist origin, bukan *, karena cookie (credentials) tidak boleh dipakai dengan wildcard. [15] CORS bukan pengganti auth: ia tidak menghentikan curl atau Postman. 

import cors from 'cors';
app.use(cors({ origin: ['https://aset.kantor.example'], credentials: true }));

Langkah 4: halaman Next.js

Semua panggilan ke API lewat satu helper server-only yang meneruskan cookie session pengguna ke Express. Dengan begitu Express tetap satu-satunya tempat pemeriksaan auth dan RBAC.

// lib/api.js
import 'server-only';
import { cookies } from 'next/headers';

export async function api(path, init = {}) {
  const sid = (await cookies()).get('sid')?.value;
  const res = await fetch(`${process.env.API_URL}${path}`, {
    ...init,
    headers: { 'Content-Type': 'application/json', Cookie: `sid=${sid}`, ...init.headers },
  });
  if (!res.ok) throw new ApiError(res.status, await res.json());
  return res.status === 204 ? null : res.json();
}

List (Server Component). Data yang tergantung request dibungkus <Suspense> supaya judul dan form cari tampil dulu dan tabel di-stream; tanpa Cache Components, file loading.js di folder route memberi efek serupa untuk satu halaman penuh. [16]

// app/aset/page.jsx
export default function HalamanAset({ searchParams }) {
  return (
    <main>
      <h1>Daftar aset</h1>
      <FormCari />
      <Suspense fallback={<p>Memuat aset…</p>}>
        <TabelAset searchParams={searchParams} />
      </Suspense>
    </main>
  );
}

async function TabelAset({ searchParams }) {
  const { q = '', page = '1' } = await searchParams;
  const { data, total } = await api(`/aset?${new URLSearchParams({ q, page })}`);
  return <Tabel baris={data} total={total} />;
}

Create lewat Server Action. Setelah sukses, revalidatePath menyegarkan daftar lalu redirect kembali ke daftar. [17] Error validasi dari API dikembalikan sebagai state, bukan dilempar, supaya form bisa menampilkannya.

// app/aset/actions.js
'use server';
import { revalidatePath } from 'next/cache';
import { redirect } from 'next/navigation';

export async function simpanAset(prevState, formData) {
  const body = Object.fromEntries(formData);
  body.kategoriId = Number(body.kategoriId);
  body.harga = Number(body.harga);
  try {
    await api('/aset', { method: 'POST', body: JSON.stringify(body) });
  } catch (err) {
    if (err instanceof ApiError && err.status < 500) return { error: err.body.error, details: err.body.details };
    throw err;
  }
  revalidatePath('/aset');
  redirect('/aset');
}
// app/aset/baru/form-aset.jsx
'use client';
import { useActionState } from 'react';
import { simpanAset } from '../actions';

export function FormAset() {
  const [state, action, pending] = useActionState(simpanAset, null);
  return (
    <form action={action}>
      <label htmlFor="kode">Kode</label>
      <input id="kode" name="kode" required pattern="[A-Z]{3}-\d{3}" />
      <label htmlFor="nama">Nama</label>
      <input id="nama" name="nama" required />
      {/* kategoriId (select), harga, tanggalBeli: pola yang sama */}
      {state?.error && <p role="alert">{state.error}</p>}
      <button disabled={pending}>{pending ? 'Menyimpan…' : 'Simpan'}</button>
    </form>
  );
}

Edit dan hapus memakai pola yang sama: halaman app/aset/[id]/edit/page.jsx memuat detail lewat api(`/aset/${id}`) lalu mengisi form dengan defaultValue; tombol hapus adalah form kecil dengan action={hapusAset.bind(null, aset.id)}. Argumen yang di-bind tidak dienkripsi, jadi id tetap divalidasi di server. [18]

// app/aset/error.js: error boundary per route, wajib Client Component
'use client';
export default function Error({ error, retry }) {
  return (
    <div role="alert">
      <p>Gagal memuat data aset. Coba lagi, atau hubungi tim IT bila berulang.</p>
      <button onClick={() => retry()}>Coba lagi</button>
    </div>
  );
}

Loading/error state: <Suspense> atau loading.js untuk loading, pending dari useActionState untuk tombol submit, error.js untuk error tak terduga, dan state dari Server Action untuk error validasi. Di production, pesan error dari Server Component disamarkan dan hanya membawa digest untuk dicocokkan dengan log server. Prop retry stabil sejak Next.js 16.3. [19]

Keamanan: CSRF dan XSS di UI. CSRF (Cross-Site Request Forgery) = situs lain membuat browser korban mengirim request yang membawa cookie korban. [20] Server Action hanya menerima POST, cookie SameSite menahan sebagian besar serangan, dan Next.js membandingkan header Origin dengan Host lalu menolak bila berbeda. [18] Untuk Route Handler atau API Express yang dipanggil langsung dari browser, perlindungan CSRF dipasang sendiri (SameSite cookie + cek Origin atau CSRF token), dan GET tidak boleh mengubah data.
XSS (Cross-Site Scripting) = input pengguna (misalnya nama aset <script>…) dijalankan sebagai kode di browser orang lain. Pertahanan utamanya output encoding sesuai konteks. [21] React meng-escape teks di JSX secara otomatis; lubangnya adalah dangerouslySetInnerHTML, yang hanya boleh dipakai untuk HTML tepercaya atau yang sudah disanitasi. [22]

Langkah 5: test

Prioritas test untuk sole developer: integration test API dengan supertest terhadap database test, karena satu test mencakup route, validasi, service, Prisma, dan SQL sekaligus. Ditambah sedikit test end-to-end browser (misalnya Playwright) untuk alur terpenting.

import { test } from 'node:test';
import assert from 'node:assert/strict';
import request from 'supertest';
import { app } from '../src/app.js';

test('POST /aset menolak harga negatif dengan 400', async () => {
  const res = await request(app).post('/aset').set('Cookie', sesiAdmin)
    .send({ kode: 'LTP-099', nama: 'Laptop uji', kategoriId: 1, harga: -5 });
  assert.equal(res.status, 400);
});

test('staf tidak boleh menghapus aset (403)', async () => {
  const res = await request(app).delete('/aset/1').set('Cookie', sesiStaf);
  assert.equal(res.status, 403);
});

Kasus yang layak di-test: create sukses (201 + Location), validasi gagal (400), kode duplikat (409), tanpa login (401), role salah (403), hapus aset yang sedang dipinjam (409), dan aset yang sudah di-soft delete tidak muncul di list.

Contoh jawaban lisan (±3 menit)

"Tolong jelaskan langkah membuat fitur CRUD dari frontend sampai backend."

"Saya ambil contoh fitur data aset di aplikasi inventaris kantor. Saya mulai dari kebutuhan: siapa yang memakai, field apa saja, dan aturan bisnisnya, misalnya kode aset unik dan aset yang sedang dipinjam tidak boleh dihapus.

Langkah pertama skema database. Saya definisikan model Aset di Prisma dengan relasi ke Kategori, constraint unique di kode, index untuk filter yang sering dipakai, dan kolom deletedAt untuk soft delete. Lalu saya jalankan prisma migrate dev, sehingga terbentuk file migrasi SQL yang ikut di-commit dan di-review. Di production saya hanya menjalankan migrate deploy, setelah backup.

Langkah kedua API di Express. Ada lima endpoint: GET list dengan pagination, search, dan filter, GET detail, POST, PATCH, dan DELETE. Saya pisahkan route, service, dan akses data. Route mengurus HTTP dan status code, input divalidasi dengan Zod, dan aturan bisnis ada di service. Error dikumpulkan di satu error handler, jadi formatnya konsisten: 400 untuk validasi, 404 kalau tidak ada, 409 kalau kode duplikat. Di Express 5, error dari handler async otomatis sampai ke handler itu.

Keamanan saya pasang di sini juga. Login memakai session dengan cookie httpOnly, Secure, dan SameSite, password di-hash. Ada RBAC sederhana: hanya admin yang boleh ubah dan hapus, dan itu dicek di server, bukan hanya menyembunyikan tombol. SQL injection tertangani karena Prisma memakai query berparameter, dan saya tidak menyambung string ke raw query.

Langkah ketiga UI di Next.js. Halaman daftar adalah Server Component yang memanggil API, dengan Suspense untuk loading state. Form tambah dan edit memakai Server Action yang meneruskan cookie session ke API, menampilkan pesan validasi, lalu revalidatePath dan redirect setelah sukses. Ada error.js untuk error tak terduga. React meng-escape output, jadi XSS tertutup selama saya tidak memakai dangerouslySetInnerHTML, dan Server Action hanya menerima POST dengan pengecekan Origin, jadi CSRF juga tertangani. CORS baru saya atur kalau browser memanggil API langsung, dengan allowlist origin.

Langkah terakhir test. Saya tulis integration test dengan supertest terhadap database test untuk kasus utama dan kasus gagal: validasi, duplikat, tidak login, dan role salah. Setelah itu deploy, lalu saya catat perubahan di dokumentasi dan changelog supaya tim operasional tahu fitur barunya."

Berikutnya, lesson 0006: Anda bukan hanya menulis fitur, tapi menjadi satu-satunya developer. Bagaimana bekerja dari requirement sampai maintenance record?
