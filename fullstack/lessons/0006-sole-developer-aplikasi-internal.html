Sole developer aplikasi internal: dari requirement sampai maintenance record

Cara bekerja sendirian dari permintaan user non-teknis sampai aplikasi yang terawat: MVP, stack, testing, deploy, backup, monitoring, preventive maintenance, dan dokumentasi, lengkap dengan contoh dokumen dan cerita STAR

Target lesson ini: Anda bisa menceritakan alur kerja sole developer dalam delapan langkah tanpa melompat, menunjukkan contoh SOP dan maintenance record yang konkret, menjawab pertanyaan "bagaimana kalau kamu satu-satunya developer?" dengan contoh nyata, dan membawakan satu cerita STAR yang punya angka di bagian Result.

JD posisi ini meminta lebih dari menulis kode: menerjemahkan kebutuhan tim operasional dan administrasi, deploy, maintenance, monitoring, dan dokumentasi. Interviewer ingin tahu satu hal: kalau aplikasi ini hanya dipegang Anda, apakah ia tetap jalan, datanya aman, dan orang lain bisa melanjutkan? Lesson ini memakai contoh berjalan aplikasi inventaris aset kantor (aset, kategori, karyawan, peminjaman).

1. Alur kerja dalam satu baris

Requirement dari user→ Scoping MVP→ Stack yang bisa dirawat sendiri→ Testing→ Deploy→ Backup→ Monitoring + preventive maintenance→ Dokumentasi: teknis, SOP, maintenance record

Hafalkan urutan ini sebagai kerangka jawaban. Saat ditanya "ceritakan cara kerja Anda", sebut kedelapan langkahnya dulu dalam satu kalimat, lalu perdalam dua atau tiga langkah yang paling relevan dengan pertanyaan. Langkahnya berulang: setelah rilis pertama, permintaan baru masuk lagi ke langkah requirement.

2. Requirement dari user non-teknis

User bagian umum jarang berkata "saya butuh tabel peminjaman dengan foreign key ke karyawan". Mereka berkata "saya capek mencari laptop yang dipinjam siapa". Tugas Anda menerjemahkan keluhan itu menjadi kebutuhan yang bisa diuji.

  • Lihat proses yang sekarang berjalan. Minta file Excel, formulir kertas, atau chat yang dipakai saat ini. Data nyata menunjukkan kolom yang benar-benar dipakai.
  • Tanya kejadian terakhir, bukan keinginan umum. "Kapan terakhir kali aset sulit ditemukan? Apa yang Anda lakukan waktu itu?"
  • Tulis sebagai user story + kriteria terima. Satu kalimat "sebagai ... saya ingin ... supaya ...", ditambah kondisi yang bisa dicek.
  • Konfirmasi dengan mockup sederhana (sketsa kertas atau wireframe) sebelum menulis kode. Lebih murah mengubah gambar daripada mengubah skema database.

3. Scoping MVP

MVP (minimum viable product) adalah versi terkecil yang sudah menyelesaikan masalah utama dan bisa dipakai sungguhan. Bagi sole developer, MVP adalah alat untuk berkata "belum sekarang" tanpa berkata "tidak".

Must (rilis 1)Should (rilis 2)Could (nanti)
CRUD aset dan kategori, import dari Excel, pinjam dan kembalikan aset, daftar peminjaman terlambat, login admin Laporan per lokasi, ekspor ke Excel, riwayat perubahan aset Label QR code, notifikasi email otomatis, foto aset

Tulis daftar ini dan minta user menyetujuinya. Saat ada permintaan baru di tengah jalan, tunjukkan daftar dan tanya: "masuk Must, berarti apa yang kita geser?"

4. Stack yang bisa dirawat sendiri

Kriteria memilih stack untuk aplikasi internal yang dipegang satu orang:

  • Satu bahasa di frontend dan backend (JavaScript/TypeScript) supaya konteks tidak berpindah-pindah.
  • Teknologi yang dokumentasinya panjang umur dan mudah dicari orang berikutnya: Next.js untuk UI, Express untuk API, PostgreSQL untuk data, Prisma untuk akses database dan migrasi.
  • Sesedikit mungkin komponen yang harus dijaga. Satu server aplikasi dan satu database lebih mudah dirawat daripada microservices. Tambah komponen hanya bila ada masalah nyata.
  • Semua perubahan skema lewat migrasi yang tersimpan di Git, bukan diubah manual di database produksi.

5. Testing

Sebagai sole developer, tidak ada QA yang menangkap kesalahan Anda. Prioritaskan test pada aturan bisnis yang mahal jika salah:

  • Unit test di service layer untuk aturan seperti "aset yang sedang dipinjam tidak bisa dipinjam lagi".
  • Integration test endpoint (request HTTP ke API Express dengan database test) untuk status code dan validasi.
  • User acceptance test (UAT): user bagian umum mencoba skenario nyata di server staging sebelum rilis, berpegang pada kriteria terima di langkah 2.
// test/peminjaman.service.test.js (node:test)
test('aset yang sedang dipinjam tidak bisa dipinjam lagi', async () => {
  const aset = await buatAset({ status: 'DIPINJAM' });
  await assert.rejects(
    () => pinjamAset({ asetId: aset.id, karyawanId: 7 }),
    /sedang dipinjam/
  );
});

6. Deploy

Untuk aplikasi internal, satu server (VM kantor atau cloud) sudah cukup. Next.js bisa di-deploy sebagai server Node.js dengan next build lalu next start, dan mode ini mendukung semua fitur Next.js. [1] Migrasi database di produksi dijalankan dengan prisma migrate deploy, yang hanya menerapkan migrasi yang belum jalan dan tidak me-reset database; prisma migrate dev adalah perintah development dan tidak boleh dipakai di produksi. [2] 

# Checklist rilis (ditulis di SOP rilis)
1. Semua test hijau di branch main
2. Backup database manual sebelum migrasi
3. git pull di server, npm ci
4. npx prisma migrate deploy
5. npm run build, restart service (API dan web)
6. Smoke test: login, list aset, pinjam lalu kembalikan 1 aset
7. Catat versi dan waktu rilis di maintenance record

Rencana rollback juga ditulis sebelum rilis: kembali ke tag Git sebelumnya, dan restore backup bila migrasi merusak data.

7. Backup

PostgreSQL punya tiga pendekatan backup yang berbeda: SQL dump, backup di level file system, dan continuous archiving. [3] pg_dump menghasilkan export yang konsisten walaupun database sedang dipakai, dan tidak memblokir user lain (baca maupun tulis). Format custom (-Fc) dikompresi dan di-restore dengan pg_restore. [4] 

#!/bin/sh
# /opt/inventaris/backup.sh, dijalankan cron setiap hari 01.00
set -e
TGL=$(date +%F)
pg_dump -Fc -d inventaris -f /backup/inventaris-$TGL.dump
# salinan kedua ke NAS kantor, salinan ketiga ke cloud storage
cp /backup/inventaris-$TGL.dump /mnt/nas/inventaris/
rclone copy /backup/inventaris-$TGL.dump offsite:inventaris/
# simpan 30 hari terakhir di server
find /backup -name 'inventaris-*.dump' -mtime +30 -delete
  • Aturan 3-2-1: simpan 3 salinan (1 utama + 2 backup), di 2 jenis media berbeda, dengan 1 salinan di luar lokasi kantor. [5] Script di atas menerapkannya: server, NAS, dan cloud.
  • Backup yang belum pernah di-restore belum terbukti. Uji restore sebulan sekali ke database terpisah dan catat hasilnya di maintenance record.
  • Dokumentasi PostgreSQL mengingatkan bahwa, kecuali untuk kasus sederhana, pg_dump umumnya bukan pilihan tepat untuk backup rutin database produksi. [4] Database inventaris kecil termasuk kasus sederhana. Bila data makin kritis, tambahkan continuous archiving: base backup dengan pg_basebackup plus arsip WAL, yang memungkinkan point-in-time recovery ke titik waktu mana pun sejak base backup. [6]

8. Monitoring dan preventive maintenance

Monitoring menjawab "apakah sistem sehat sekarang?". Preventive maintenance adalah pekerjaan terjadwal supaya masalah tidak muncul.

  • Health check: endpoint GET /health yang mengecek koneksi database, dipantau uptime checker setiap 5 menit dan mengirim notifikasi bila gagal.
  • Log aplikasi: catat kegagalan validasi input, login berhasil dan gagal, serta kegagalan otorisasi. Jangan pernah mencatat password, session ID, access token, atau connection string database. [7]
  • Database: view pg_stat_activity berisi satu baris per proses server beserta query yang sedang berjalan, berguna saat aplikasi terasa lambat. [8]
  • VACUUM wajib berjalan rutin, antara lain untuk memakai ulang ruang disk dari baris yang di-update/dihapus dan memperbarui statistik query planner. Autovacuum aktif secara default dan sangat disarankan tetap aktif; tugas Anda memastikan ia tidak dimatikan dan memeriksa tabel yang jarang ter-vacuum. [9]
FrekuensiPreventive maintenance aplikasi inventaris aset
Harian (otomatis)Backup database, cek hasil job backup, health check
MingguanBaca log error, cek sisa disk server (alarm di 80%)
BulananUji restore backup, update patch OS, npm audit dan update dependency minor, cek masa berlaku sertifikat TLS
Per kuartalReview akun admin (hapus yang sudah keluar), review query lambat, update dokumentasi

9. Dokumentasi: teknis, SOP, dan maintenance record

  • Dokumentasi teknis (README di repo): arsitektur singkat, cara menjalankan lokal, variabel environment, cara deploy, lokasi backup. Ukurannya: developer pengganti bisa deploy tanpa menelepon Anda.
  • SOP sistem: prosedur langkah demi langkah untuk kegiatan berulang (rilis, backup dan restore, membuat akun). Ditulis supaya orang lain bisa mengikutinya saat Anda cuti.
  • Maintenance record: log semua kegiatan maintenance, preventive maupun corrective, sebagai bukti dan bahan analisis masalah berulang.

10. Pertanyaan sole developer tersering dan contoh jawaban

"Bagaimana Anda menghadapi permintaan yang terus bertambah dari banyak bagian?"
Contoh jawaban: "Saya catat semua permintaan di satu backlog, lalu sepakati prioritasnya dengan atasan atau pemilik proses, bukan dengan siapa yang paling sering menghubungi saya. Setiap permintaan saya beri estimasi kasar. Kalau ada permintaan mendesak di tengah rilis, saya tunjukkan apa yang harus digeser supaya keputusannya jelas dan tercatat."

"Siapa yang me-review kode Anda kalau Anda satu-satunya developer?"
Contoh jawaban: "Saya mengganti review rekan dengan beberapa pengaman: test otomatis untuk aturan bisnis yang penting, linter dan format otomatis, pull request ke diri sendiri yang saya baca ulang keesokan harinya, dan UAT dengan user sebelum rilis. Untuk keputusan besar seperti skema database, saya tulis catatan keputusan singkat supaya alasannya bisa dicek orang lain."

"Bagaimana kalau Anda sakit atau keluar? Apa yang terjadi dengan aplikasinya?"
Contoh jawaban: "Saya merancang supaya aplikasi tidak bergantung pada ingatan saya. README menjelaskan cara menjalankan dan deploy, SOP mencakup rilis dan restore, kredensial disimpan di password manager kantor, dan staf IT support pernah mencoba SOP restore bersama saya. Ukurannya: orang lain bisa memulihkan aplikasi dari backup tanpa menelepon saya."

"Bagaimana Anda tahu aplikasi bermasalah sebelum user melapor?"
Contoh jawaban: "Ada health check yang dicek setiap 5 menit dan mengirim notifikasi, log error yang saya baca setiap minggu, dan cek hasil job backup setiap hari. Saya juga punya jadwal preventive maintenance bulanan, misalnya uji restore dan update patch, yang hasilnya dicatat di maintenance record."

"User tidak bisa menjelaskan apa yang mereka mau. Apa yang Anda lakukan?"
Contoh jawaban: "Saya minta ditunjukkan cara kerja mereka sekarang, misalnya file Excel atau formulir yang dipakai, dan menanyakan kejadian terakhir yang menyulitkan. Dari situ saya buat sketsa layar dan minta mereka mencoba alurnya di atas kertas. Biasanya kebutuhan sebenarnya muncul saat mereka melihat sketsa itu."

11. Contoh cerita STAR lengkap

STAR (Situation, Task, Action, Result) adalah struktur cerita untuk pertanyaan perilaku seperti "ceritakan proyek yang Anda bangun sendiri". Cerita di bawah adalah contoh skenario untuk menunjukkan bentuk dan takarannya. Ganti detail dan angkanya dengan pengalaman Anda sendiri; jangan membawakan angka yang tidak bisa Anda pertanggungjawabkan.

Situation. Kantor dengan ±120 karyawan mencatat ±850 aset (laptop, printer, proyektor) di satu file Excel bersama, dan peminjaman dicatat lewat chat. Saat stock opname tahunan, 37 aset tidak jelas lokasinya, dan stock opname memakan 5 hari kerja tiga staf bagian umum.

Task. Saya satu-satunya developer di kantor itu dan diminta membuat aplikasi inventaris aset internal dalam ±2 bulan, termasuk memindahkan data lama, tanpa mengganggu pekerjaan bagian umum.

Action. Saya mengamati proses mereka dan mengumpulkan file Excel serta riwayat chat, lalu menyepakati MVP: CRUD aset, pinjam/kembali, daftar peminjaman terlambat, dan import Excel. Saya memilih Next.js, Express, dan PostgreSQL dengan Prisma supaya satu bahasa dan mudah dirawat sendiri. Saya menulis script import yang membersihkan 140 baris duplikat atau kode aset tidak konsisten dan mengonfirmasi hasilnya dengan staf. Aturan bisnis peminjaman saya lindungi dengan unit test, lalu dua minggu UAT di server staging. Setelah rilis, saya menyiapkan backup harian dengan aturan 3-2-1, health check, dan tiga SOP (rilis, restore, akun), lalu melatih staf IT support menjalankan SOP restore.

Result. Aplikasi dipakai sejak minggu ke-9. Pada stock opname berikutnya, waktu stock opname turun dari 5 hari menjadi 2 hari, dan aset yang tidak jelas lokasinya turun dari 37 menjadi 4. Peminjaman terlambat lebih dari 7 hari turun ±60% dalam 3 bulan karena muncul di dashboard. Uji restore bulanan selalu berhasil, dan selama 6 bulan pertama tidak ada data yang hilang.

Kunci cerita ini: Action memakai kata "saya" dan menyebut keputusan, bukan sekadar daftar teknologi; Result punya angka sebelum dan sesudah. Bawakan dalam ±2 menit, lalu siapkan jawaban lanjutan untuk pertanyaan "apa yang akan Anda lakukan berbeda?" (mis. "melibatkan kepala bagian sejak hari pertama supaya prioritas tidak berubah di tengah jalan").
