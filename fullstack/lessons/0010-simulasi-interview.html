Simulasi interview tiga babak

Pertanyaan yang paling mungkin muncul dari JD posisi Fullstack Web Developer aplikasi internal, dikelompokkan dalam tiga babak, masing-masing dengan contoh jawaban lisan siap baca atau pseudocode dan tautan ke lesson yang membahasnya

Target lesson ini: Anda bisa menjawab setiap pertanyaan di bawah dengan suara keras dalam 30–60 detik tanpa membaca, menulis pseudocode babak live coding dalam ±10 menit per soal sambil menjelaskan langkahnya, dan tahu lesson mana yang harus dibaca ulang bila sebuah jawaban masih tersendat.

Cara memakai simulasi ini

Baca pertanyaan→ Tutup jawaban, jawab keras-keras→ Bandingkan dengan contoh→ Tersendat? Baca ulang lesson terkait

Setiap pertanyaan diberi label asal JD-nya, karena interviewer biasanya menurunkan pertanyaan langsung dari kalimat di JD. Contoh jawaban ditulis untuk diucapkan: kalimat pendek, satu contoh konkret dari aplikasi inventaris aset, lalu berhenti. Jangan menghafal kata per kata; hafalkan urutan poinnya. Untuk latihan tambahan, pakai dua reference: ±30 pertanyaan SQL dan soal coding tambahan.

Babak 1: Fundamental & SQL

1. Apa beda Server Component dan Client Component di Next.js App Router? (JD: konsep front-end modern)
"Di App Router, komponen secara default adalah Server Component: dirender di server, bisa langsung mengambil data, dan kodenya tidak dikirim ke browser. Client Component ditandai 'use client' dan dipakai bila butuh state, event handler seperti onClick, atau API browser. Di aplikasi inventaris, halaman daftar aset saya buat Server Component yang memanggil API, sedangkan kotak pencarian dan tombol konfirmasi hapus jadi Client Component kecil. Prinsipnya, dorong batas 'use client' sejauh mungkin ke daun supaya JavaScript di browser sedikit." Lihat 0001.
2. Jelaskan event delegation dan closure dengan contoh. (JD: HTML, CSS, JavaScript)
"Event dari elemen anak menggelembung (bubbling) ke induknya, jadi daripada memasang listener di setiap baris tabel aset, saya pasang satu listener di <tbody> dan memeriksa event.target.closest('button'). Itu event delegation: lebih hemat dan tetap jalan untuk baris yang ditambahkan belakangan. Closure adalah fungsi yang tetap mengingat variabel dari scope tempat ia dibuat, misalnya fungsi debounce untuk kotak pencarian yang menyimpan timer-nya sendiri di antara pemanggilan." Lihat 0001.
3. Bagaimana Anda mendesain REST API untuk aset, dan status code apa yang dipakai? (JD: REST API, back-end)
"Resource-nya kata benda jamak: GET /aset untuk daftar dengan pagination dan filter, GET /aset/:id, POST /aset, PATCH /aset/:id, dan DELETE /aset/:id. Status code mengikuti RFC 9110: 201 untuk create, 204 untuk delete tanpa body, 400 atau 422 untuk validasi gagal, 401 bila belum login, 403 bila role tidak boleh, 404 bila tidak ada, dan 409 bila kode aset duplikat. Di Express 5 saya pisahkan route, service, dan Prisma, validasi dengan Zod, dan satu error handler terpusat supaya format error konsisten." Lihat 0002.
4. Jelaskan normalisasi dan rancang tabel untuk inventaris aset. (JD: desain database dasar)
"Normalisasi memastikan setiap fakta disimpan sekali. 1NF: nilai atomik, tanpa daftar dalam satu sel. 2NF: kolom bergantung pada seluruh key. 3NF: tidak ada kolom yang bergantung pada kolom non-key lain. Untuk inventaris saya buat empat tabel: kategori, karyawan, aset dengan foreign key ke kategori dan kode unik, serta peminjaman sebagai tabel penghubung N-N antara aset dan karyawan yang menyimpan tanggal pinjam dan kembali. Constraint CHECK menjaga misalnya tanggal kembali tidak sebelum tanggal pinjam." Lihat 0003.
5. Tulis query: jumlah aset per kategori, hanya kategori dengan lebih dari 5 aset. (JD: MySQL/PostgreSQL)
SELECT k.nama, COUNT(a.id) AS jumlah
FROM kategori k
JOIN aset a ON a.kategori_id = k.id
WHERE a.deleted_at IS NULL
GROUP BY k.id, k.nama
HAVING COUNT(a.id) > 5
ORDER BY jumlah DESC;
"WHERE menyaring baris sebelum dikelompokkan, HAVING menyaring hasil kelompok. Bila kategori tanpa aset juga harus muncul dengan nol, saya ganti menjadi LEFT JOIN dan memindahkan syarat deleted_at ke klausa ON." Lihat 0003 dan reference SQL.
6. Query daftar peminjaman lambat. Apa yang Anda lakukan? (JD: memonitor performa sistem)
"Saya ukur dulu, bukan menebak: jalankan EXPLAIN ANALYZE pada query-nya dan lihat apakah ada sequential scan di tabel besar atau estimasi baris yang jauh meleset. Bila filter-nya WHERE karyawan_id = ? ORDER BY tanggal_pinjam DESC, saya buat composite index dengan urutan kolom yang sama. Di level aplikasi saya cek N+1, yaitu query di dalam loop, dan menggantinya dengan include Prisma atau satu query IN. Untuk halaman yang dalam, pagination keyset lebih stabil daripada OFFSET besar. Setelah itu saya ukur lagi dan mencatatnya di maintenance record." Lihat 0004.
7. Kapan Anda memakai transaksi, dan apa itu isolation level? (JD: integrasi database)
"Transaksi dipakai bila beberapa perubahan harus berhasil atau gagal bersama, misalnya mencatat peminjaman sekaligus mengubah status aset menjadi dipinjam; di Prisma lewat $transaction. ACID menjamin atomik, konsisten, terisolasi, dan tahan lama. Isolation level mengatur seberapa banyak transaksi lain terlihat: default PostgreSQL READ COMMITTED, default InnoDB MySQL REPEATABLE READ. Untuk mencegah satu aset dipinjam dua orang sekaligus, saya andalkan constraint di database atau penguncian baris, bukan hanya pengecekan di aplikasi." Lihat 0004.

Babak 2: CRUD & sole dev

1. Jelaskan langkah membuat fitur CRUD dari frontend sampai backend. (JD: membangun aplikasi web front-end, back-end, integrasi database, API)
"Saya mulai dari kebutuhan dan aturan bisnis, lalu skema Prisma dan prisma migrate dev sehingga file migrasi ikut di-commit. Kedua, endpoint Express untuk list dengan pagination dan filter, detail, create, update, dan soft delete, dengan validasi Zod dan error handler terpusat. Ketiga, halaman Next.js: daftar sebagai Server Component dengan loading state, form dengan Server Action yang memanggil API lalu revalidate. Keamanan dipasang di sepanjang jalan: session dengan cookie httpOnly, RBAC dicek di server, query berparameter untuk mencegah SQL injection. Terakhir integration test dengan supertest, lalu deploy dan catat di changelog." Versi lengkap ±3 menit ada di 0005.
2. Kenapa Server Action tidak langsung mengakses database, tapi memanggil API Express? (JD: back-end, server-side logic)
"Karena aturan bisnis dan validasi cukup ada di satu tempat, yaitu service di Express, dan API yang sama bisa dipakai klien lain seperti aplikasi mobile atau integrasi dengan sistem kantor lain. Server Action tetap endpoint POST publik, jadi di dalamnya saya tetap cek session dan validasi input, lalu meneruskan cookie ke API. Kalau aplikasinya kecil dan hanya punya satu klien, akses langsung lewat Prisma dari Server Action juga sah; saya akan menyebut trade-off itu." Lihat 0001 dan 0005.
3. Bagaimana Anda mengamankan aplikasi internal dari XSS, CSRF, dan SQL injection? (JD: troubleshooting dan maintenance sistem)
"XSS: React meng-escape output secara default, jadi saya hindari dangerouslySetInnerHTML, dan cookie session bertanda httpOnly supaya tidak bisa dibaca script. CSRF: cookie SameSite, dan Server Action hanya menerima POST dengan pengecekan Origin; untuk API yang dipanggil browser saya pakai token CSRF atau header khusus. SQL injection: Prisma memakai query berparameter, dan bila terpaksa raw SQL saya pakai tagged template yang juga berparameter, tidak pernah menyambung string. Terakhir, otorisasi dicek di server per role, bukan hanya menyembunyikan tombol." Lihat 0005.
4. Anda satu-satunya developer. Bagaimana Anda bekerja dari permintaan user sampai aplikasi berjalan? (JD: bekerja dengan tim operasional dan administrasi untuk menerjemahkan kebutuhan bisnis)
"Saya mulai dengan mengamati proses user dan mengumpulkan contoh data nyata, lalu menyepakati MVP tertulis: apa yang masuk versi pertama dan apa yang ditunda. Stack saya pilih yang bisa saya rawat sendiri. Aturan bisnis penting saya lindungi dengan test, rilis dulu ke staging untuk UAT, lalu deploy dengan langkah yang terdokumentasi. Setelah live, saya pasang backup terjadwal yang diuji restore, monitoring, dan jadwal preventive maintenance. Semuanya dicatat: dokumentasi teknis, SOP, dan maintenance record, supaya orang lain bisa melanjutkan bila saya tidak ada." Lihat 0006.
5. Ceritakan proyek yang Anda banggakan (STAR). (JD: membangun dan merawat sistem internal)
"Situation: kantor dengan sekitar 850 aset mencatat semuanya di Excel bersama, dan stock opname memakan 5 hari kerja dengan 37 aset tidak jelas lokasinya. Task: sebagai satu-satunya developer, saya diminta membuat aplikasi inventaris dalam sekitar 2 bulan, termasuk migrasi data. Action: saya menyepakati MVP, memilih Next.js, Express, dan PostgreSQL, membersihkan 140 baris data ganda saat import, menulis unit test untuk aturan peminjaman, menjalankan UAT, lalu menyiapkan backup 3-2-1 dan tiga SOP. Result: stock opname turun dari 5 hari menjadi 2 hari dan aset yang tidak jelas lokasinya dari 37 menjadi 4." Versi lengkap ada di 0006.
6. Apa isi dokumentasi teknis, SOP, dan maintenance record Anda? (JD: menyiapkan dokumentasi teknis, prosedur sistem, dan maintenance record)
"Dokumentasi teknis menjelaskan arsitektur, cara menjalankan aplikasi secara lokal, variabel environment, dan skema data. SOP adalah langkah bernomor untuk tugas berulang yang bisa dijalankan orang lain, misalnya rilis versi baru, restore backup, dan membuat atau menonaktifkan akun. Maintenance record mencatat setiap tindakan: tanggal, apa yang dikerjakan, alasannya, hasilnya, dan tindak lanjut, misalnya uji restore bulanan atau update dependency. Ketiganya disimpan di repo atau wiki internal, bukan di kepala saya." Lihat 0006.
7. Seorang user tidak bisa membuka aplikasi internal. Bagaimana Anda menanganinya? (JD: perawatan jaringan dan perangkat user)
"Pertama saya tentukan cakupannya: hanya dia atau semua orang. Kalau semua, saya cek server aplikasi, health check, dan log. Kalau hanya dia, saya cek dari sisi perangkat: koneksi jaringan, ipconfig untuk melihat apakah ia dapat IP dari DHCP, ping ke gateway dan ke server, lalu nslookup nama aplikasinya untuk memastikan DNS benar. Setelah itu baru browser: cache, cookie session, atau akun yang terkunci. Penyebab dan solusinya saya catat supaya kasus serupa lebih cepat." Lihat 0007.
8. Bagaimana kemampuan multimedia Anda? (JD: multimedia dasar)
"Saya jujur tentang levelnya: saya bisa mengerjakan kebutuhan kantor sehari-hari seperti mengedit foto, membuat poster atau banner sederhana, dan memotong video pendek, dengan memperhatikan resolusi, aspect ratio, dan kompresi sesuai kanalnya. Saya tidak memposisikan diri sebagai desainer grafis. Saya membawa portofolio berisi beberapa karya dengan konteks singkat, dan untuk kebutuhan yang di atas kemampuan saya, saya usulkan template atau vendor." Lihat 0007.

Babak 3: Live coding

Di babak ini jawaban utamanya pseudocode. Ucapkan urutan tujuh langkah: soal, pertanyaan klarifikasi, ide, pseudocode, implementasi, kompleksitas, edge case. Implementasi JavaScript lengkap dan penjelasannya ada di lesson yang ditautkan.

1. Cek apakah integer adalah palindrome tanpa mengubahnya menjadi string. (JD: JavaScript, server-side logic)
Klarifikasi: angka negatif dianggap bukan palindrome? Ide: balik separuh angka dengan mod 10 dan pembagian integer, lalu bandingkan dengan separuh sisanya; teknik separuh ini juga mencegah overflow. 
fungsi isPalindrome(x):
    jika x < 0 atau (x mod 10 = 0 dan x ≠ 0): kembalikan false
    rev ← 0
    selama x > rev:
        rev ← rev × 10 + (x mod 10)
        x ← x div 10
    kembalikan x = rev atau x = rev div 10
Kompleksitas O(log n) waktu, O(1) ruang. Edge case: negatif, berakhiran 0 (mis. 10), 0 sendiri, satu digit. Lihat 0008.
2. Cek apakah string kurung ()[]{} valid. (JD: JavaScript)
Ide: kurung yang terakhir dibuka harus pertama ditutup, jadi pakai stack. 
fungsi isValid(s):
    pasangan ← { ")": "(", "]": "[", "}": "{" }
    stack ← kosong
    untuk setiap c di s:
        jika c kurung buka: push c
        selain itu jika stack kosong atau pop() ≠ pasangan[c]: kembalikan false
    kembalikan stack kosong
O(n) waktu dan ruang. Edge case: string kosong (valid), kurung tutup di awal, kurung buka tersisa, susunan silang ([)]. Lihat 0008.
3. Cari dua index yang nilainya berjumlah target. (JD: server-side logic)
Klarifikasi: array terurut? Bila tidak, pakai hash map; bila terurut dan memori harus O(1), pakai two pointers. 
fungsi twoSum(nums, target):
    dilihat ← map kosong              // nilai → index
    untuk i dari 0 sampai n − 1:
        butuh ← target − nums[i]
        jika butuh ada di dilihat: kembalikan [dilihat[butuh], i]
        dilihat[nums[i]] ← i
    kembalikan []
O(n) waktu, O(n) ruang, dibanding brute force O(n²). Edge case: nilai kembar [3, 3], tidak ada pasangan, angka negatif. Lihat 0009.
4. Panjang substring terpanjang tanpa karakter berulang. (JD: JavaScript)
Ide: sliding window [kiri, i] yang selalu bebas duplikat, dengan map index terakhir setiap karakter. 
fungsi terpanjang(s):
    terakhir ← map kosong;  kiri ← 0;  terbaik ← 0
    untuk i dari 0 sampai n − 1:
        jika s[i] ada di terakhir dan terakhir[s[i]] ≥ kiri:
            kiri ← terakhir[s[i]] + 1
        terakhir[s[i]] ← i
        terbaik ← maks(terbaik, i − kiri + 1)
    kembalikan terbaik
O(n) waktu. Edge case: string kosong, semua karakter sama, "abba" (kemunculan lama di luar jendela). Lihat 0009.
5. Cari sebuah nilai di daftar ID aset yang sudah terurut. (JD: server-side logic, performa sistem)
Ide: binary search, buang separuh ruang pencarian setiap perbandingan. 
fungsi binarySearch(nums, target):
    lo ← 0;  hi ← n − 1
    selama lo ≤ hi:
        mid ← lo + (hi − lo) div 2
        jika nums[mid] = target: kembalikan mid
        jika nums[mid] < target: lo ← mid + 1
        selain itu: hi ← mid − 1
    kembalikan −1
O(log n) waktu. Edge case: array kosong, target di ujung, overflow (lo + hi) / 2 di bahasa 32-bit. "Di database, index B-tree memberi efek yang sama untuk kolom yang sering dicari." Lihat 0009 dan 0004.

Penutup: pertanyaan balik untuk interviewer

Di akhir interview biasanya ada kesempatan bertanya. Pertanyaan yang menunjukkan Anda sudah memikirkan pekerjaannya:

  • "Sistem internal apa saja yang sekarang berjalan, dan mana yang paling sering bermasalah?"
  • "Bagaimana pembagian waktu yang diharapkan antara development dan support IT?"
  • "Apakah sudah ada dokumentasi, backup, dan server staging, atau itu bagian dari yang perlu saya bangun?"
  • "Siapa yang biasanya menyampaikan kebutuhan aplikasi, dan bagaimana prioritasnya diputuskan?"
