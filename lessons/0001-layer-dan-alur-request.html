Di mana kode ini tinggal?

Layer & alur request di ASP.NET Core Web API, dilihat dari kacamata Express

Target lesson ini: Anda bisa menjawab pertanyaan interview "Bagaimana Anda menstruktur project ASP.NET Core Web API?" dalam 60 detik, dan bisa menentukan layer yang tepat untuk sepotong kode yang ditunjukkan pewawancara.

1. Anda sudah tahu 80%-nya

Di Express Anda mungkin sudah memisahkan routes/, controllers/, services/, dan models/. ASP.NET Core memakai ide yang sama. Yang berbeda: pemisahan ini diharapkan oleh pewawancara, dan semuanya disambungkan oleh dependency injection bawaan, bukan oleh require/import manual.

Express / NodeASP.NET CoreTanggung jawab (satu kalimat)
routes/ + controllers/Controllers/Menerjemahkan HTTP ↔ panggilan method. Tidak berisi aturan bisnis.
schema Zod / JoiDTOs/Bentuk data yang masuk/keluar API.
services/Services/Aturan bisnis: "harga harus > 0", "nama tidak boleh duplikat".
data-access di atas PrismaRepositories/Query & simpan data untuk satu Entity.

config/ + .envappsettings.json + Config/Konfigurasi bertipe lewat Options pattern.

Template baru ASP.NET Core memang dimulai sebagai satu project, dengan pemisahan lewat folder. Microsoft menyebutnya all-in-one: "separation of concerns is achieved through the use of folders." [1]

2. Alur satu request

HTTP request→ Middleware→ Controller→ Service→ Repository→ DbContext→ SQL Server

Hasilnya kembali ke arah sebaliknya: Entity diubah menjadi DTO di Service, lalu Controller membungkusnya menjadi Ok(...), NotFound(), atau CreatedAtAction(...).

Aturannya, setiap layer hanya bicara dengan layer di bawahnya. Microsoft menulis: "The UI layer shouldn't make any requests to the DAL directly" [1]. Artinya Controller tidak boleh menyentuh DbContext secara langsung.

3. Kenapa ada interface di antara layer

Di N-layer klasik, Service bergantung langsung pada kelas data access. Akibatnya, menurut Microsoft, "Testing business logic in such an architecture is often difficult, requiring a test database." [1]

Solusinya, Service bergantung pada interface, dan implementasinya dipasang dari luar:

// Services/ProductService.cs — hanya tahu kontraknya
public class ProductService(IProductRepository repo) : IProductService { ... }

// Program.cs — satu-satunya tempat yang tahu implementasi konkret
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();

Tempat penyambungan ini disebut composition root: "The place where this logic is performed is known as the app's composition root" [1]. Di unit test, Anda tinggal memberikan mock IProductRepository tanpa database. Ini adalah huruf D di SOLID, yang akan dibahas di lesson berikutnya.

Kalau Anda pernah memakai NestJS, ini sama dengan providers di module dan constructor injection. Kalau hanya Express, bayangkan app.js yang membuat semua instance sekali lalu menyerahkannya ke constructor. Bedanya, di .NET framework yang melakukannya untuk Anda.

Latihan 1 — Kode ini milik layer mana?

Pewawancara sering menunjukkan potongan kode lalu bertanya, "Ini seharusnya ada di mana?" Jawab tanpa scroll ke atas.

return product is null ? NotFound() : Ok(product);

Memilih status HTTP (404/200) adalah urusan HTTP, jadi tempatnya di Controller.

if (request.Price <= 0) throw new ValidationException("Price must be greater than 0.");

"Harga harus > 0" adalah aturan bisnis. Aturan ini tetap berlaku walaupun request datang dari selain HTTP (misalnya background job), jadi tempatnya di Service.

return await _db.Products.AnyAsync(p => p.Name == name);

Query langsung ke DbContext adalah akses data. Service cukup memanggil repo.ExistsByNameAsync(name).

builder.Services.AddScoped<IProductService, ProductService>();

Menghubungkan interface ke implementasi adalah tugas composition root. Bisa dipindah ke extension method di Config/, tapi tetap dipanggil dari Program.cs.

[HttpPost] public async Task<ActionResult<ProductResponse>> Create(CreateProductRequest req)

Attribute [HttpPost] dan ActionResult adalah konsep HTTP. Ini action method di Controller.

"Kalau jumlah yang diminta melebihi Stock, tolak dengan pesan error."

Ini aturan bisnis tentang Stock, jadi tempatnya di Service. Repository hanya mengambil dan menyimpan angkanya.

builder.Services.Configure<JwtSettings>(builder.Configuration.GetSection("Jwt"));

Ini Options pattern: bagian Jwt dari appsettings di-bind ke kelas JwtSettings (yang tinggal di Config/). Registrasinya dilakukan di composition root.

_db.Products.Add(product); await _db.SaveChangesAsync();

Menyimpan lewat DbContext adalah akses data, jadi tempatnya di Repository.

Latihan 2 — Alasannya

Pewawancara mid-level jarang berhenti di "di mana". Mereka biasanya lanjut bertanya "kenapa".

Sebuah Controller langsung memakai _db.Products untuk menyimpan produk baru. Apa masalah utamanya?

Secara teknis kode ini bisa jalan (jadi C salah). Masalahnya, validasi harga dan cek duplikat di Service ikut dilewati, dan Controller jadi sulit di-unit-test.

Di N-layer klasik tanpa interface, kenapa business logic sulit di-unit-test?

Dependensi compile-time mengalir dari atas ke bawah, sehingga test Service ikut menyeret database. Interface dan DI memutus rantai itu.

Di mana IProductRepository dihubungkan ke ProductRepository?

Composition root. Memakai new di constructor justru bertentangan dengan DI. OnModelCreating mengatur pemetaan tabel, bukan DI.

Kenapa API mengembalikan DTO, bukan Entity secara langsung?

Dengan DTO, kolom baru di tabel tidak otomatis bocor ke API, dan client tidak bisa mengisi field yang tidak boleh (over-posting). Entity sebenarnya bisa diserialisasi, tapi berisiko circular reference.

Latihan 3 — Ucapkan dengan suara keras

Pasang timer 60 detik. Jawab pertanyaan ini dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Mengingat tanpa melihat inilah yang membuat materi menempel.

"Bagaimana Anda menstruktur project ASP.NET Core Web API, dan kenapa?"
Bandingkan dengan jawaban contoh dan checklist-nya

"Untuk API ukuran kecil–menengah saya pakai layered architecture dalam satu project. Controller hanya menangani HTTP: binding request, memanggil service, dan mengembalikan status code yang tepat. Service berisi aturan bisnis. Repository membungkus akses data lewat EF Core DbContext. Data keluar-masuk API lewat DTO, jadi skema database tidak bocor. Setiap layer bergantung pada interface, dan semuanya didaftarkan di Program.cs sebagai composition root. Karena itu Service bisa di-unit-test dengan mock repository. Konfigurasi ada di appsettings.json dan dibaca lewat Options pattern. Kalau domainnya makin kompleks, saya akan memecahnya menjadi Clean Architecture dengan beberapa project."

Checklist: apakah Anda menyebut…

  • tanggung jawab Controller / Service / Repository masing-masing?
  • DTO dan alasannya?
  • interface + DI + composition root?
  • manfaatnya untuk testing?
  • config/Options pattern?
  • kapan Anda akan memilih struktur lain (trade-off)?
