Anatomi Node: V8, libuv, dan kenapa cocok untuk I/O-bound

Apa saja isi proses Node, di mana JavaScript Anda berjalan, siapa yang menunggu I/O, dan kenapa satu thread JavaScript bisa melayani ribuan koneksi

Target lesson ini: Anda bisa menyebut tiga lapisan Node (V8, binding C++, libuv) beserta tugasnya, menjelaskan kenapa JavaScript berjalan di satu thread tapi I/O tetap asinkron, dan memutuskan apakah sebuah workload cocok untuk Node (I/O-bound) atau tidak (CPU-bound).

Anda sudah pernah membuat API Express. Lesson ini menjawab pertanyaan yang biasanya dibuka interviewer: "apa sebenarnya Node itu, dan kenapa ia cepat untuk API?"

1. Tiga lapisan di dalam satu proses Node

Kode JS Anda→ API Node (fs, net, http)→ Binding C++→ libuv: event loop + thread pool→ Sistem operasi
  • V8 adalah engine yang menjalankan JavaScript. Node menjalankan V8, engine yang sama dengan Chrome, di luar browser. [1] V8 sendiri adalah engine JavaScript dan WebAssembly open source buatan Google, ditulis dalam C++. [2] V8 hanya tahu JavaScript: objek, fungsi, heap, garbage collection. V8 tidak tahu apa itu file atau socket.
  • libuv adalah library C lintas platform yang awalnya ditulis untuk Node, dirancang di sekitar model I/O asinkron berbasis event. [3] Isinya event loop (lesson 0002) dan thread pool (lesson 0004).
  • Binding C++ adalah lem di antara keduanya: kode C++ di dalam Node yang membuat fungsi JavaScript seperti fs.readFile bisa memanggil libuv dan sistem operasi, lalu memanggil callback JavaScript Anda saat hasilnya siap.

2. Satu thread JavaScript, I/O tetap asinkron

Eksekusi JavaScript di Node bersifat single-threaded. [4] Aplikasi Node berjalan di satu proses tanpa membuat thread baru untuk setiap request. [1] Lalu siapa yang menunggu database atau file? Bukan thread JavaScript Anda:

  • I/O jaringan (socket, HTTP, koneksi database) ditangani mekanisme polling sistem operasi: epoll di Linux, kqueue di macOS, IOCP di Windows. Semua dipantau dari satu thread milik loop. [3]
  • I/O file dan beberapa operasi lain yang tidak punya versi asinkron di OS dijalankan di thread pool libuv, lalu hasilnya dikembalikan ke loop. [3]
app.get('/orders/:id', async (req, res) => {
  // 1. Thread JS menyiapkan query, lalu bebas melayani request lain
  const order = await db.order.findUnique({ where: { id: req.params.id } });
  // 2. Saat jawaban database datang, callback ini dijadwalkan lagi
  res.json(order);
});

Selama await menunggu database, thread JavaScript tidak diam. Ia menjalankan callback request lain. Inilah arti concurrency di Node: kemampuan event loop menjalankan callback JavaScript setelah pekerjaan lain selesai, bukan menjalankan JavaScript di banyak thread sekaligus. [4]

3. I/O-bound vs CPU-bound

I/O-bound berarti sebagian besar waktu habis untuk menunggu (database, HTTP ke service lain, disk). CPU-bound berarti sebagian besar waktu habis untuk menghitung (resize gambar, hashing berat, parsing data besar).

Contoh dari panduan resmi Node: request butuh 50 ms, dan 45 ms di antaranya adalah I/O database yang bisa dikerjakan asinkron. Dengan operasi non-blocking, 45 ms itu bebas dipakai untuk melayani request lain. [4] Karena itu satu proses Node bisa menangani ribuan koneksi bersamaan tanpa repot mengelola concurrency antar-thread. [1]

WorkloadWaktu habis untukCocok di Node?
REST API ke database, gateway, BFF, chatMenunggu I/OYa. Thread JS hampir selalu bebas.
Encode video, hitung 10 juta baris di memoriMenghitung di CPUTidak di thread utama. Selama menghitung, semua request lain menunggu.

CPU-bound bukan berarti dilarang di Node. Artinya pekerjaan itu harus dipindah dari thread utama, misalnya ke worker_threads atau proses lain (lesson 0010). Menjalankannya di thread utama membuat seluruh server berhenti merespons sampai hitungan selesai (lesson 0004).

"Node itu single-threaded. Bagaimana ia bisa melayani ribuan request bersamaan, dan kapan Node bukan pilihan yang baik?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Yang single-threaded adalah eksekusi JavaScript-nya. Node terdiri dari V8 yang menjalankan JS, libuv yang menyediakan event loop dan thread pool, dan binding C++ yang menghubungkan API seperti fs atau net ke libuv. Saat handler menunggu database, thread JS tidak ikut menunggu. I/O jaringan dipantau OS lewat epoll, kqueue, atau IOCP, dan I/O file dikerjakan thread pool libuv. Begitu hasilnya siap, callback dijadwalkan ke event loop. Jadi kalau 45 dari 50 ms request adalah menunggu database, waktu itu dipakai untuk request lain. Itu sebabnya Node cocok untuk API yang I/O-bound. Kebalikannya, pekerjaan CPU-bound seperti encode video atau hashing berat menahan satu-satunya thread JS, jadi semua request lain ikut menunggu. Pekerjaan seperti itu dipindah ke worker thread atau proses terpisah."

Checklist: apakah Anda menyebut…

  • yang single-threaded adalah eksekusi JavaScript, bukan seluruh proses?
  • V8 menjalankan JavaScript, libuv menyediakan event loop dan thread pool?
  • binding C++ menghubungkan API Node ke libuv dan sistem operasi?
  • I/O jaringan dipantau OS (epoll/kqueue/IOCP), I/O file lewat thread pool?
  • waktu menunggu I/O dipakai melayani request lain, jadi cocok untuk I/O-bound?
  • CPU-bound memblokir semua request, dan solusinya worker thread atau proses lain?

Lulus kalau minimal 4 dari 6.
