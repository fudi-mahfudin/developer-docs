Fase event loop; setTimeout vs setImmediate

Event loop bukan satu antrean, melainkan putaran beberapa fase. Urutan fase itu menjelaskan kapan callback Anda dijalankan

Target lesson ini: Anda bisa menyebut fase event loop secara berurutan beserta isinya, menjelaskan di fase mana callback setTimeout, I/O, dan setImmediate berjalan, dan menjelaskan kapan urutan setTimeout(fn, 0) vs setImmediate(fn) tidak deterministik.

Sebelumnya, di lesson 0001: libuv menyediakan event loop, dan thread JavaScript menjalankan callback saat hasil I/O siap. Lesson ini membuka isi loop itu.

1. Enam fase dalam satu putaran

Setiap fase punya antrean callback sendiri. Saat loop masuk ke sebuah fase, ia menjalankan callback di antrean fase itu, lalu pindah ke fase berikutnya. [1]

timers→ pending callbacks→ idle, prepare→ poll→ check→ close callbacks↻
FaseIsinya
timersCallback setTimeout() dan setInterval() yang waktunya sudah lewat.
pending callbacksCallback I/O yang ditunda ke putaran berikutnya (mis. beberapa jenis error TCP).
idle, prepareHanya dipakai internal.
pollAmbil event I/O baru dan jalankan callback I/O (hampir semua, selain close, timer, dan setImmediate). Node menunggu di sini kalau tidak ada pekerjaan lain.
checkCallback setImmediate().
close callbacksCallback penutupan, mis. socket.on('close', …).

Isi tabel mengikuti panduan resmi Node. [1] Dokumentasi libuv menjabarkan langkah yang sama: jalankan timer, pending callback, idle dan prepare handle, blok untuk I/O (poll), check handle, lalu close callback. [2]

Fase poll adalah tempat proses "tidur" saat server sepi: tidak ada timer yang jatuh tempo dan tidak ada setImmediate, jadi loop menunggu koneksi atau data baru. Karena check tepat setelah poll, setImmediate berarti "jalankan begitu poll selesai di putaran ini".

2. setTimeout(fn, 0) bukan "segera"

Delay di bawah 1 diubah menjadi 1 ms, dan Node tidak menjamin waktu persis maupun urutan callback timer. [3] Delay timer adalah batas minimum: callback baru dicek di fase timers, dan bisa terlambat kalau loop sedang sibuk menjalankan callback lain.

3. setTimeout vs setImmediate: kapan urutannya pasti?

// Kasus A: di main module (top-level file)
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// output: bisa "timeout, immediate" ATAU "immediate, timeout"

// Kasus B: di dalam callback I/O
const fs = require('node:fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// output: selalu "immediate, timeout"
  • Kasus A tidak deterministik. Menurut panduan resmi, kalau keduanya dipanggil dari main module, urutannya bergantung pada performa proses, yang bisa dipengaruhi aplikasi lain di mesin yang sama. [1] Penjelasannya: saat loop pertama kali masuk fase timers, apakah 1 ms sudah lewat atau belum? Kalau sudah, timeout jalan duluan; kalau belum, loop lanjut ke poll lalu check, dan immediate jalan duluan.
  • Kasus B deterministik. Callback readFile berjalan di fase poll. Fase berikutnya adalah check, jadi immediate selalu jalan sebelum timer apa pun, berapa pun jumlah timer-nya. [1] Timer baru jalan di fase timers pada putaran berikutnya.

Di interview, jawaban "setTimeout 0 selalu duluan" atau "setImmediate selalu duluan" sama-sama salah. Jawaban yang benar: bergantung konteks, lalu sebutkan dua kasus di atas.

"Jelaskan fase event loop Node. Mana yang jalan duluan, setTimeout(fn, 0) atau setImmediate(fn)?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Satu putaran event loop punya fase berurutan: timers untuk setTimeout dan setInterval, pending callbacks untuk callback I/O yang ditunda, idle/prepare yang internal, poll untuk mengambil event I/O baru dan menjalankan callback-nya, di sini juga Node menunggu kalau tidak ada kerjaan, lalu check untuk setImmediate, dan close callbacks untuk event close. Soal mana yang duluan: bergantung konteks. Di main module urutannya tidak deterministik, karena delay 0 sebenarnya 1 ms dan bergantung apakah 1 ms itu sudah lewat saat loop masuk fase timers. Tapi kalau keduanya dipanggil di dalam callback I/O, setImmediate selalu duluan, karena callback I/O berjalan di poll dan fase sesudahnya adalah check, sedangkan timers baru di putaran berikutnya."

Checklist: apakah Anda menyebut…

  • urutan fase: timers → pending callbacks → poll → check → close callbacks?
  • setTimeout/setInterval di timers, setImmediate di check?
  • callback I/O di poll, dan Node menunggu di poll kalau tidak ada pekerjaan?
  • di main module urutan setTimeout 0 vs setImmediate tidak deterministik?
  • alasannya: delay 0 menjadi 1 ms, bergantung apakah sudah lewat saat masuk timers?
  • di dalam callback I/O, setImmediate selalu duluan karena check tepat setelah poll?
