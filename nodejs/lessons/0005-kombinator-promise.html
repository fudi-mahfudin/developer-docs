Kombinator Promise; await berurutan vs paralel

Promise.all, allSettled, race, any, dan cara menjalankan banyak pekerjaan async tanpa menunggu satu per satu, juga tanpa membanjiri database

Sebelumnya, lesson 0004: event loop hanya satu, dan I/O dikerjakan di luar thread JavaScript. Artinya, beberapa query atau HTTP call bisa menunggu bersamaan. Lesson ini membahas cara menulis kode yang memanfaatkannya, dan batasnya.

Target lesson ini: Anda bisa menjawab "Endpoint ini memanggil tiga service dengan tiga await berurutan dan butuh 900 ms. Bagaimana mempercepatnya, dan bagaimana kalau salah satunya gagal?" tanpa catatan: kapan await berurutan memang perlu, kapan diganti Promise.all, beda empat kombinator, jebakan await di dalam loop, dan cara membatasi concurrency. Anda juga bisa menulis fungsi pembatas concurrency di kertas.

1. await berurutan vs paralel

await menghentikan fungsi async sampai Promise selesai. Kalau tiga panggilan tidak saling bergantung tetapi ditulis berurutan, waktu totalnya adalah jumlah ketiganya. Kalau ketiganya dimulai dulu lalu ditunggu bersama, waktu totalnya kira-kira sama dengan yang paling lama. 

// Berurutan: ±300 + 300 + 300 = ±900 ms
const user   = await getUser(id);
const orders = await getOrders(id);
const promos = await getPromos(id);

// Paralel: ketiga Promise dibuat dulu, lalu ditunggu bersama: ±300 ms
const [user, orders, promos] = await Promise.all([
  getUser(id), getOrders(id), getPromos(id),
]);
mulai getUser, getOrders, getPromos→ ketiganya menunggu I/O bersamaan→ Promise.all resolve saat yang terakhir selesai

"Paralel" di sini artinya menunggu bersamaan (concurrent), bukan menjalankan JavaScript di beberapa thread. Kode JS Anda tetap di satu thread; yang tumpang-tindih adalah waktu tunggu I/O. Berurutan tetap benar kalau langkah kedua butuh hasil langkah pertama, misalnya getOrders(user.accountId).

2. Empat kombinator

Semuanya menerima iterable berisi Promise dan mengembalikan satu Promise. Bedanya ada di kapan Promise itu selesai dan apa isinya [1] [2]:

KombinatorResolve kapanReject kapanPakai untuk
Promise.allsemua fulfilled; hasil berupa array, urutannya sama dengan inputbegitu satu reject (fail-fast)semua hasil wajib ada
Promise.allSettledsemua selesai, apa pun hasilnya; array {status, value} / {status, reason}tidak pernah rejectbatch yang boleh gagal sebagian, mis. kirim notifikasi
Promise.raceyang pertama selesai fulfilledyang pertama selesai rejecttimeout manual
Promise.anyyang pertama fulfilledsemuanya reject, dengan AggregateError (berisi errors)beberapa replika/mirror, ambil yang tercepat berhasil

Fakta yang sering dilupakan: saat Promise.all reject karena satu Promise gagal, Promise lain tetap berjalan. Panduan resmi Node menulisnya terang: "even if rejection occurs, the Promises continue to execute." Hal yang sama berlaku untuk race: pemenang tidak membatalkan yang kalah [1]. Promise tidak punya mekanisme pembatalan; untuk benar-benar menghentikan pekerjaan dipakai AbortSignal (lesson 0007). 

const results = await Promise.allSettled(userIds.map(sendEmail));
const failed = results
  .map((r, i) => ({ r, id: userIds[i] }))
  .filter(x => x.r.status === "rejected");
log.warn({ failed: failed.map(x => x.id) }, "sebagian email gagal");

Promise.any reject dengan AggregateError, yaitu error yang membawa array errors berisi alasan setiap Promise yang gagal [3]. Jangan tertukar dengan race: race ikut reject kalau yang pertama selesai adalah kegagalan.

3. await di dalam loop

Tiga cara menulis loop async, dengan perilaku yang sangat berbeda:

// A. for...of + await: berurutan, satu per satu. Benar kalau urutan penting
for (const id of ids) await process(id);

// B. forEach(async): forEach TIDAK menunggu callback async.
//    Baris berikutnya jalan sebelum pekerjaan selesai; reject tidak tertangkap di sini
ids.forEach(async id => { await process(id); });

// C. map + Promise.all: semua dimulai sekaligus, ditunggu bersama
await Promise.all(ids.map(id => process(id)));

B adalah bug klasik: forEach mengabaikan Promise yang dikembalikan callback-nya, jadi fungsi luar selesai lebih dulu, dan error di dalamnya menjadi unhandled rejection (lesson 0006). Linter ESLint punya aturan no-await-in-loop yang menandai pola A, tetapi A tidak salah; A hanya lambat kalau iterasinya sebenarnya independen.

4. Membatasi concurrency

Pola C bermasalah kalau ids berisi 10.000 elemen: 10.000 query dimulai sekaligus. Connection pool database (kumpulan koneksi terbatas yang dipakai bergantian) penuh, API pihak ketiga membalas 429 (Too Many Requests), dan memori naik. Panduan Node mengingatkan hal yang sama: memakai Promise.all untuk Promise dalam jumlah besar "can strain the system's memory" [1]. Solusinya: batasi berapa pekerjaan yang berjalan bersamaan, misalnya 5. 

async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;                 // aman: JS satu thread, tidak ada race di sini
      results[i] = await fn(items[i], i);
    }
  }
  const n = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: n }, worker));
  return results;
}
// await mapLimit(ids, 5, id => process(id));

Idenya: buat limit "worker" async yang masing-masing mengambil indeks berikutnya sampai habis. Paling banyak limit pekerjaan menunggu bersamaan, dan hasil tetap berurutan sesuai input. Alternatif yang lebih kasar adalah batch: potong array per 5, lalu await Promise.all(batch) per potongan. Ini lebih mudah, tetapi setiap batch menunggu item paling lambatnya. Di produksi, orang biasanya memakai paket kecil seperti p-limit; di interview, Anda diminta menulis versi di atas.

Latihan lisan — Tulis kode di kertas

Pasang timer 5 menit. Tulis di kertas tanpa IDE, lalu jelaskan dengan suara keras. Jangan buka jawaban contoh sebelum selesai.

"Tulis fungsi mapLimit(items, limit, fn) yang menjalankan fn untuk setiap item dengan paling banyak limit pekerjaan berjalan bersamaan, dan mengembalikan hasil sesuai urutan input." (5 menit)
Bandingkan dengan jawaban contoh dan checklist-nya 
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

"Saya membuat limit worker. Masing-masing mengambil indeks berikutnya, menunggu fn, lalu mengambil lagi sampai habis. Mengambil indeks dengan next++ aman karena JavaScript satu thread. Hasil disimpan per indeks supaya urutannya sama dengan input. Kalau satu fn reject, Promise.all reject, tapi worker lain tetap jalan; kalau perlu semua hasil, saya simpan error per item seperti allSettled."

Checklist: apakah Anda menyebut atau menulis…

  • Paling banyak limit pekerjaan berjalan bersamaan (worker atau antrean), bukan semuanya sekaligus
  • Setiap worker mengambil item berikutnya sampai habis, bukan batch kaku yang menunggu item paling lambat
  • Hasil disimpan per indeks sehingga urutan sama dengan input
  • Menunggu semua worker selesai (mis. Promise.all atas worker) sebelum mengembalikan hasil
  • Menjelaskan kenapa next++ aman: JavaScript berjalan di satu thread
  • Menyebut perilaku saat ada yang gagal (fail-fast seperti all atau dikumpulkan seperti allSettled)
