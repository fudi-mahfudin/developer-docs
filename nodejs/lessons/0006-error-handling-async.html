Error handling async: unhandled rejection, uncaughtException, Error.cause

Ke mana error pergi kalau tidak ditangkap, kenapa proses Node mati karenanya, dan error mana yang boleh ditangani versus harus membuat proses restart

Sebelumnya, lesson 0005: forEach(async ...) membuat reject "lepas" tanpa ada yang menangkap. Lesson ini menjawab: apa yang terjadi pada error yang lepas itu, dan bagaimana merancang error handling yang tidak menelan bug.

Target lesson ini: Anda bisa menjawab "Kenapa service Node kami tiba-tiba mati dengan exit code 1 padahal tidak ada error di log request? Bagaimana Anda mencegahnya?" tanpa catatan: kapan try/catch tidak menangkap error async, perilaku unhandled rejection sejak Node 15, peran uncaughtException sebagai jalan terakhir, event 'error' di EventEmitter, Error.cause, dan beda operational error vs programmer error.

1. try/catch di fungsi async, dan kapan ia tidak menangkap

Di dalam fungsi async, try/catch menangkap reject dari Promise yang di-await. Tiga jebakan sering muncul:

async function getUser(id) {
  try {
    return fetchUser(id);          // 1. tanpa await: reject lolos dari catch ini
  } catch (err) { return null; }
}

async function handler() {
  try {
    setTimeout(() => { throw new Error("boom"); }, 10);  // 2. callback jalan nanti,
  } catch (err) { /* tidak pernah ke sini */ }           //    try sudah lama selesai
  saveAudit();                     // 3. Promise tanpa await/catch: reject-nya "lepas"
}

Perbaikannya: return await fetchUser(id) kalau memang ingin ditangkap di situ; bungkus isi callback dengan try/catch-nya sendiri; dan setiap Promise harus di-await atau diberi .catch(). Dokumentasi Node menjelaskan alasan yang sama untuk error yang dikirim lewat callback atau event: error itu "cannot be intercepted using try…catch as they are thrown after the calling code has already exited." [1]

2. Unhandled rejection: proses mati (Node ≥ 15)

Promise yang reject tanpa handler disebut unhandled rejection. Node memancarkan event process.on('unhandledRejection') saat sebuah Promise reject "and no error handler is attached to the promise within a turn of the event loop" [2]. Apa yang terjadi selanjutnya diatur flag --unhandled-rejections, yang default-nya throw sejak Node 15 (sebelumnya hanya warning): kalau tidak ada listener unhandledRejection, rejection itu dilempar sebagai uncaught exception [3].

Promise reject, tanpa catch→ event 'unhandledRejection' (ada listener? selesai di situ)→ tanpa listener: jadi uncaught exception→ stack trace ke stderr, exit code 1

Jadi di Node 24, satu saveAudit() tanpa await yang gagal bisa mematikan seluruh server, termasuk request lain yang sedang berjalan. Itu jawaban untuk "mati dengan exit code 1": secara default Node mencetak stack trace ke stderr dan "exiting with code 1" [2]. Mode lain (strict, warn, warn-with-error-code, none) ada, tetapi mematikan peringatan hanya menyembunyikan bug.

3. uncaughtException: jalan terakhir, bukan "On Error Resume Next"

process.on('uncaughtException') menangkap error yang lolos dari semua handler. Dokumentasi Node tegas: ini "a crude mechanism for exception handling intended to be used only as a last resort", dan "It is not safe to resume normal operation after 'uncaughtException'." Pemakaian yang benar adalah membersihkan resource secara sinkron, mencatat log, lalu keluar [2]. 

process.on("unhandledRejection", (reason) => {
  throw reason;                 // samakan jalurnya: biarkan jadi uncaught exception
});
process.on("uncaughtException", (err) => {
  logger.fatal({ err }, "uncaught, proses akan berhenti");
  process.exit(1);              // process manager / orchestrator menyalakan ulang
});

Kalimat aman di interview: "Saya tidak melanjutkan setelah uncaughtException. Saya log, lalu exit, dan mengandalkan process manager (systemd, PM2, atau orchestrator container) untuk restart. Yang saya perbaiki adalah Promise yang lupa di-await."

4. Event 'error' di EventEmitter

API berbasis event (stream, socket, server) melaporkan kegagalan lewat event 'error', bukan lewat throw atau reject. Aturannya keras: kalau EventEmitter memancarkan 'error' dan tidak ada listener, "the error is thrown, a stack trace is printed, and the Node.js process exits" [4]. Karena itu setiap stream atau socket yang Anda buat sendiri butuh .on('error', ...). EventEmitter dibahas lebih dalam di lesson 0007.

5. Error.cause: membungkus tanpa kehilangan error asli

Saat menangkap error tingkat rendah lalu melempar error yang lebih bermakna, jangan buang yang asli. Opsi cause di konstruktor Error (ECMAScript 2022, ada di Node ≥ 16.9) menyimpannya [1] [5]: 

try {
  await db.query("UPDATE accounts SET ...", [id]);
} catch (err) {
  throw new Error(`gagal memperbarui akun ${id}`, { cause: err });
}
// logger mencetak err.message dan err.cause (error asli dari driver database)

6. Operational error vs programmer error

Pembedaan ini menentukan apa yang Anda lakukan dengan sebuah error:

Operational errorProgrammer error
ApaKegagalan yang diharapkan terjadi di dunia nyataBug di kode
Contohtimeout ke API lain, koneksi DB putus, input user tidak valid, file tidak adaundefined is not a function, lupa await, argumen salah tipe
TindakanTangani: retry, kembalikan 4xx/503, fallback, log sebagai warningJangan "ditangani" di runtime: log, crash, restart, lalu perbaiki kodenya

Alasannya sama dengan peringatan di bagian 3: setelah bug yang tidak terduga, state aplikasi tidak bisa dipercaya lagi. Dokumentasi Node menyebut unhandled exception "inherently mean that an application is in an undefined state" [2]. Di NestJS nanti, operational error biasanya dilempar sebagai HttpException dan dibentuk oleh exception filter.

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Service Node kami di Node 24 sesekali mati dengan exit code 1, padahal log request tidak menunjukkan error. Apa dugaan Anda, dan bagaimana Anda mencegahnya?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Dugaan pertama saya unhandled rejection: ada Promise yang reject tanpa await atau catch, misalnya fire-and-forget atau forEach dengan callback async. Sejak Node 15 default --unhandled-rejections adalah throw, jadi rejection itu menjadi uncaught exception dan proses keluar dengan code 1. Dugaan kedua, EventEmitter seperti stream atau socket memancarkan 'error' tanpa listener, yang juga mematikan proses. Untuk mencegahnya: setiap Promise di-await atau diberi catch, setiap stream diberi handler error, dan saya pasang lint seperti no-floating-promises. Saya tetap memasang handler uncaughtException hanya untuk log dan exit, bukan untuk melanjutkan, karena state-nya tidak bisa dipercaya; process manager yang me-restart. Error yang diharapkan, seperti timeout ke service lain, saya tangani sebagai operational error dan saya bungkus dengan Error cause supaya penyebab aslinya tetap tercatat."

Checklist: apakah Anda menyebut…

  • Unhandled rejection sebagai dugaan utama, dengan contoh penyebabnya (Promise tanpa await/catch)
  • Default --unhandled-rejections=throw sejak Node 15, sehingga proses keluar dengan code 1
  • Event 'error' tanpa listener di EventEmitter/stream juga mematikan proses
  • uncaughtException hanya untuk log + exit, tidak melanjutkan; restart oleh process manager
  • Pencegahan konkret: await/catch setiap Promise, handler error di stream, lint
  • Beda operational error (ditangani) dan programmer error (crash + perbaiki), atau Error.cause untuk menjaga error asli
