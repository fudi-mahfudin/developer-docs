EventEmitter dan AbortController

Pola event yang dipakai hampir semua API inti Node, peringatan "possible memory leak", dan cara membatalkan fetch atau pekerjaan async yang sudah tidak dibutuhkan

Sebelumnya, lesson 0006: event 'error' tanpa listener mematikan proses, dan Promise tidak bisa dibatalkan. Lesson ini melengkapi keduanya: cara kerja EventEmitter, dan AbortSignal sebagai cara standar untuk membatalkan.

Target lesson ini: Anda bisa menjawab "Log produksi kami penuh MaxListenersExceededWarning, dan request ke service lain kadang menggantung selamanya. Apa artinya, dan bagaimana memperbaikinya?" tanpa catatan: listener dipanggil sinkron, on vs once, kenapa warning itu tanda leak dan bukan sekadar batas yang perlu dinaikkan, serta memberi batas waktu dan membatalkan fetch dengan AbortSignal.timeout dan AbortController.

1. EventEmitter: listener dipanggil sinkron

EventEmitter (modul node:events) adalah dasar stream, socket, HTTP server, dan process. Satu hal yang sering salah diasumsikan: emit() "calls all listeners synchronously in the order in which they were registered" [1]. Listener yang lambat memblokir pemanggil emit(), dan error yang di-throw listener naik ke pemanggil itu. 

import { EventEmitter, once } from "node:events";   // ESM: top-level await boleh
const orders = new EventEmitter();

orders.on("created", o => console.log("kirim email", o.id));    // setiap kali
orders.once("created", o => console.log("pesanan pertama"));    // sekali, lalu dilepas
orders.on("error", err => console.error("gagal", err));         // wajib (lesson 0006)

orders.emit("created", { id: 1 });   // kedua listener jalan sekarang, sebelum baris berikut
console.log("setelah emit");

const [order] = await once(orders, "created");   // versi Promise, menunggu emit berikutnya

emitter.once() menambah listener yang dilepas sebelum dipanggil. Fungsi events.once(emitter, name) mengembalikan Promise yang resolve saat event datang, dan "rejected if the EventEmitter emits 'error' while waiting"; ia juga menerima opsi signal untuk berhenti menunggu [1].

2. MaxListenersExceededWarning: tanda leak

Secara default, lebih dari 10 listener untuk satu event memicu warning. Ini "not a hard limit": listener tetap ditambahkan, tetapi Node mencetak "possible EventEmitter memory leak" dengan nama MaxListenersExceededWarning [1]. Penyebab paling umum adalah menambah listener di dalam kode yang berjalan per request: 

// BUG: setiap request menambah listener ke emitter yang hidup selamanya
app.get("/stream", (req, res) => {
  const onPrice = p => res.write(JSON.stringify(p));
  prices.on("update", onPrice);
  req.on("close", () => prices.off("update", onPrice));   // perbaikan: lepas saat selesai
});

Tanpa baris off, setiap request meninggalkan listener yang memegang res, sehingga memori tidak pernah dibebaskan. Menaikkan batas dengan setMaxListeners() hanya membungkam peringatannya. Naikkan batas hanya kalau jumlah listener memang tetap dan disengaja (mis. 20 modul yang masing-masing mendengarkan satu event).

3. AbortController dan AbortSignal

AbortController adalah API standar web yang juga ada di Node sebagai global. Pemanggil memegang controller; pekerjaan menerima controller.signal. Memanggil abort(reason) membuat signal memancarkan event 'abort' dan menyimpan signal.reason [2].

pemanggil: new AbortController()→ kirim controller.signal ke fetch / pekerjaan→ controller.abort() atau timeout→ Promise reject: AbortError / TimeoutError

Yang perlu diingat, dengan label versinya [2]:

  • AbortSignal.timeout(ms) (Node ≥ 17.3): signal yang abort otomatis setelah ms milidetik.
  • AbortSignal.any([s1, s2]) (Node ≥ 20.3): abort kalau salah satu signal abort; reason-nya dari signal yang memicu.
  • fetch global tidak lagi eksperimental sejak Node 21 (Node ≥ 21), berbasis undici.

Nama error membedakan penyebabnya. Spesifikasi DOM: abort() tanpa alasan menyimpan DOMException bernama "AbortError", sedangkan AbortSignal.timeout() memakai "TimeoutError" [3]. API khas Node yang menerima signal (mis. events.once) melempar error dengan name === 'AbortError' [4].

4. Membatalkan fetch dan pekerjaan async

fetch tanpa batas waktu bisa menunggu sangat lama kalau service tujuan menggantung. Beri setiap panggilan keluar batas waktu, dan batalkan juga saat client yang memicunya sudah pergi: 

async function getProfile(id, clientSignal) {
  const signal = AbortSignal.any([clientSignal, AbortSignal.timeout(2000)]);
  try {
    const res = await fetch(`${PROFILE_URL}/users/${id}`, { signal });
    return await res.json();
  } catch (err) {
    if (err.name === "TimeoutError") throw new Error("profile service timeout", { cause: err });
    throw err;                       // AbortError: client pergi, tidak perlu dilanjutkan
  }
}

Untuk pekerjaan Anda sendiri, teruskan signal ke setiap langkah dan periksa sebelum langkah mahal berikutnya: signal.throwIfAborted() melempar signal.reason kalau sudah abort. Banyak API inti Node menerima opsi { signal }, misalnya setTimeout dari node:timers/promises, yang reject dengan 'AbortError' saat dibatalkan [5]. Ingat lesson 0005: Promise.race dengan timer hanya berhenti menunggu; AbortSignal yang benar-benar menghentikan request di bawahnya.

Latihan lisan — Tulis kode di kertas

Pasang timer 5 menit. Tulis di kertas tanpa IDE, lalu jelaskan dengan suara keras. Jangan buka jawaban contoh sebelum selesai.

"Tulis fungsi fetchJson(url, ms) yang memanggil fetch dengan batas waktu ms, melempar error yang jelas kalau timeout, dan tetap meneruskan error lain. Jelaskan apa yang terjadi pada request-nya saat timeout." (5 menit)
Bandingkan dengan jawaban contoh dan checklist-nya 
async function fetchJson(url, ms) {
  try {
    const res = await fetch(url, { signal: AbortSignal.timeout(ms) });
    if (!res.ok) throw new Error(`HTTP ${res.status} dari ${url}`);
    return await res.json();
  } catch (err) {
    if (err.name === "TimeoutError") {
      throw new Error(`timeout ${ms} ms ke ${url}`, { cause: err });
    }
    throw err;
  }
}

"Saya memberi fetch signal dari AbortSignal.timeout. Saat waktunya habis, signal abort, fetch reject dengan TimeoutError, dan request HTTP di bawahnya benar-benar dibatalkan, bukan hanya diabaikan seperti kalau saya memakai Promise.race. Error timeout saya bungkus dengan cause; error lain, termasuk status non-2xx, saya teruskan. Kalau fungsi ini dipanggil dari handler request, saya gabungkan dengan signal client memakai AbortSignal.any."

Checklist: apakah Anda menulis atau menyebut…

  • Meneruskan signal ke fetch (lewat AbortSignal.timeout atau AbortController + timer)
  • Membedakan timeout lewat err.name (TimeoutError, atau AbortError untuk controller manual)
  • Error lain tetap diteruskan, tidak ditelan
  • Memeriksa res.ok, karena fetch tidak reject untuk status 4xx/5xx
  • Menjelaskan bahwa abort benar-benar membatalkan request, beda dengan Promise.race
  • Menyebut Error.cause, AbortSignal.any, atau versi Node (fetch stabil ≥ 21)
