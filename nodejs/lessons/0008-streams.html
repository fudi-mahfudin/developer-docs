Streams: Readable, Writable, Duplex, Transform, dan pipeline

Memproses data per potongan, bukan sekaligus: kenapa ini penting untuk file besar dan banyak request, dan cara merangkai stream dengan aman

Modul ini pindah dari "bagaimana event loop bekerja" ke "bagaimana memindahkan data besar tanpa menghabiskan memori". Pertanyaan interview yang klasik: "Bagaimana Anda mengirim file 2 GB ke client di Node?" Jawaban yang dicari bukan readFile, melainkan stream.

Target lesson ini: Anda bisa menjawab "Apa itu stream di Node, dan kapan Anda memakainya?" tanpa catatan, dalam 60 detik: empat jenis stream dengan contohnya, kenapa stream lebih hemat memori daripada readFile untuk file besar, dan menulis di kertas satu pipeline yang aman terhadap error.

1. Empat jenis stream

Dokumentasi Node v24 membagi stream menjadi empat jenis dasar: [1]

JenisArah dataContoh
ReadableSumber: data dibaca darinyafs.createReadStream(), request HTTP di sisi server, process.stdin
WritableTujuan: data ditulis ke dalamnyafs.createWriteStream(), response HTTP di sisi server, process.stdout
DuplexBisa dibaca dan ditulis; dua sisi independennet.Socket (koneksi TCP)
TransformDuplex yang output-nya dihitung dari inputzlib.createGzip(), enkripsi, parser CSV

Beda Duplex dan Transform sering ditanyakan. Di socket TCP, data yang Anda tulis dikirim ke peer, dan data yang Anda baca datang dari peer; keduanya tidak saling diturunkan. Di gzip, setiap byte yang keluar adalah hasil kompresi byte yang masuk. Setiap Duplex dan Transform punya dua buffer internal terpisah, satu untuk sisi baca dan satu untuk sisi tulis. [2]

Semua stream adalah instance EventEmitter: mereka memancarkan event seperti 'data', 'end', 'finish', dan 'error'. [1]

2. Stream vs readFile untuk file besar

fs.readFile() "reads the entire contents of a file" ke memori sebagai satu Buffer. [3] Ia asinkron (tidak memblokir event loop), tapi memorinya sebanding dengan ukuran file. Satu request untuk file 2 GB berarti ±2 GB memori; sepuluh request bersamaan berarti ±20 GB.

fs.createReadStream() membaca file per potongan (chunk). Ukuran potongan diatur highWaterMark, default 64 * 1024 byte (64 KiB) untuk stream file. [4] Memori yang dipakai kira-kira beberapa potongan, berapa pun ukuran filenya.

File di disk (2 GB)→ Readable, potongan 64 KiB→ Transform (gzip)→ Writable (response HTTP)

Aturan praktis: readFile wajar untuk file kecil yang memang perlu utuh di memori (file config, template). Untuk upload, download, log, CSV, atau ekspor data yang ukurannya tidak dibatasi, pakai stream. Stream juga mulai mengirim byte pertama ke client sebelum seluruh file selesai dibaca.

3. Merangkai stream: stream.pipeline, bukan .pipe() polos

Cara lama merangkai stream adalah .pipe(). Masalahnya, dokumentasi Node sendiri memberi peringatan: kalau Readable error di tengah jalan, "the Writable destination is not closed automatically", dan setiap stream harus ditutup manual untuk mencegah memory leak. [5]

stream.pipeline() menyelesaikan itu: ia meneruskan error dari stream mana pun ke satu callback, dan "will call stream.destroy(err) on all streams" yang belum selesai. [6] Versi Promise ada di node:stream/promises, cocok dengan async/await: [7] 

const { pipeline } = require('node:stream/promises');
const fs = require('node:fs');
const zlib = require('node:zlib');

async function gzipFile(src, dest) {
  await pipeline(
    fs.createReadStream(src),   // Readable
    zlib.createGzip(),          // Transform
    fs.createWriteStream(dest), // Writable
  );
}

gzipFile('access.log', 'access.log.gz').catch(err => {
  console.error('gagal', err); // error dari stream mana pun sampai di sini
});

Di handler HTTP, response juga Writable, jadi pola yang sama berlaku: pipeline(fs.createReadStream(path), res). Kalau client memutus koneksi di tengah download, pipeline menghancurkan stream file sehingga file descriptor tidak bocor.

4. Async iterator: membaca stream dengan for await

Readable bisa dibaca dengan for await...of; setiap iterasi memberi satu potongan. Ini cara paling mudah dibaca untuk memproses stream baris demi baris atau potongan demi potongan. Satu jebakan: kalau loop berhenti lewat break, return, atau throw, "the stream will be destroyed". [8] 

async function countBytes(path) {
  let total = 0;
  for await (const chunk of fs.createReadStream(path)) {
    total += chunk.length; // chunk adalah Buffer, maks. 64 KiB
  }
  return total;
}

pipeline juga menerima async generator sebagai langkah tengah, jadi Transform sederhana tidak perlu ditulis sebagai class: pipeline(src, async function* (source) { for await (const c of source) yield c.toString().toUpperCase(); }, dest).

const { pipeline } = require('node:stream/promises');
const fs = require('node:fs');
const zlib = require('node:zlib');

async function gzipFile(src, dest) {
  await pipeline(
    fs.createReadStream(src),

  );

"readFile memuat seluruh file ke memori; untuk file besar dan banyak request, memori habis. Stream membaca per potongan, 64 KiB secara default. pipeline dari stream/promises mengembalikan Promise, meneruskan error dari stream mana pun, dan menghancurkan semua stream kalau gagal, sedangkan .pipe() tidak menutup tujuan saat sumber error."

Checklist: apakah Anda…

  • memakai fs.createReadStream dan fs.createWriteStream, bukan readFile/writeFile?
  • menaruh zlib.createGzip() sebagai Transform di tengah?
  • memakai pipeline dari node:stream/promises (atau versi callback dengan penanganan error)?
  • meng-await pipeline sehingga error bisa ditangkap pemanggil?
  • menyebut readFile memuat seluruh file ke memori?
  • menyebut .pipe() tidak meneruskan error dan tidak menutup stream tujuan?
