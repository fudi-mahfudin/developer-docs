Backpressure, highWaterMark, dan Buffer

Apa yang terjadi kalau sumber data lebih cepat daripada tujuannya, bagaimana stream memberi sinyal "berhenti dulu", dan apa sebenarnya isi sebuah chunk

Di lesson 0008, stream membaca file per potongan supaya memori tetap kecil. Itu hanya benar kalau ada backpressure. Membaca dari disk bisa jauh lebih cepat daripada mengirim ke client lewat jaringan lambat; tanpa rem, potongan yang sudah dibaca menumpuk di memori.

Target lesson ini: Anda bisa menjawab "Apa itu backpressure, dan apa yang terjadi kalau diabaikan?" tanpa catatan, dalam 60 detik: peran highWaterMark, arti write() yang mengembalikan false dan event 'drain', kenapa pipe tanpa error handling berbahaya, dan beda panjang string dengan jumlah byte di Buffer.

1. Buffer internal dan highWaterMark

Setiap Readable dan Writable menyimpan data di buffer internal. Ukurannya diatur highWaterMark: jumlah byte untuk stream biasa, jumlah objek untuk stream objectMode. [1]

  • Readable: begitu buffer baca mencapai highWaterMark, stream berhenti membaca dari sumber sampai data dikonsumsi.
  • Writable: selama buffer tulis di bawah highWaterMark, write() mengembalikan true; begitu mencapai atau melewatinya, write() mengembalikan false. [1]

Default-nya (Node ≥ 22): 65536 byte (64 KiB) untuk stream byte di non-Windows, 16384 (16 KiB) di Windows, dan 16 objek untuk objectMode. Default byte dinaikkan dari 16 KiB di Node v22.0.0, jadi artikel lama yang menyebut 16 KiB tidak salah, hanya untuk versi lama. [2]

Jebakan interview: highWaterMark adalah "a threshold, not a limit". [1] write() yang mengembalikan false tetap menerima chunk itu. Stream tidak menolak data; ia hanya memberi sinyal.

2. write() = false, lalu tunggu 'drain'

Kalau write() mengembalikan false, "further attempts to write data to the stream should stop until the 'drain' event is emitted". [3] Event 'drain' muncul "when it is appropriate to resume writing data". [4]

Menulis manual dengan backpressure yang benar:

const { once } = require('node:events');

async function writeAll(ws, rows) {
  for (const row of rows) {
    if (!ws.write(row + '\n')) {
      await once(ws, 'drain'); // buffer penuh: tunggu kosong dulu
    }
  }
  ws.end();
}

Seberapa besar bedanya? Panduan Node.js Learn membandingkan proses yang sama dengan dan tanpa backpressure: memori maksimum ±88 MB vs ±1,52 GB, dan GC berjalan lebih tidak teratur saat backpressure diabaikan. [5] Panduan yang sama merangkum aturannya: "Never call .write() after it returns false but wait for 'drain' instead."

3. Kenapa pipe tanpa error handling berbahaya

pipe() dan pipeline() sama-sama menangani backpressure secara otomatis: mereka berhenti membaca saat write() mengembalikan false dan lanjut saat 'drain'. Bedanya di error. Dengan pipe(), kalau sumber error, tujuan "is not closed automatically", dan setiap stream harus ditutup manual untuk mencegah memory leak. [6] Error juga tidak diteruskan antar stream: a.pipe(b).pipe(c) butuh handler 'error' di setiap stream, dan EventEmitter tanpa listener 'error' akan melempar error itu dan bisa mematikan proses. [11] 

// Berbahaya: error di gzip atau res tidak ditangani, stream file bisa tetap terbuka
fs.createReadStream(path).pipe(zlib.createGzip()).pipe(res);

// Aman: satu tempat untuk error, semua stream dihancurkan kalau gagal
pipeline(fs.createReadStream(path), zlib.createGzip(), res, err => {
  if (err) console.error('download gagal', err);
});

4. Buffer dan encoding

Chunk dari stream byte adalah Buffer: "a fixed-length sequence of bytes", subclass dari Uint8Array. [7] Saat mengubah antara string dan Buffer, encoding default adalah UTF-8; encoding lain yang umum: 'hex', 'base64', 'base64url', 'latin1'. [8] 

const s = 'é';
s.length;                         // 1  (code unit UTF-16)
Buffer.byteLength(s);             // 2  (byte UTF-8)
Buffer.from('hi').toString('hex');    // '6869'
Buffer.from('hi').toString('base64'); // 'aGk='

Buffer.byteLength() menghitung byte setelah di-encode, berbeda dengan String.prototype.length. [9] Ini penting saat menghitung header Content-Length atau batas ukuran payload: pakai byte, bukan panjang string.

Jebakan kedua: batas chunk dihitung dalam byte, jadi karakter UTF-8 multi-byte bisa terbelah di antara dua chunk, dan chunk.toString() per chunk menghasilkan karakter rusak. Panggil readable.setEncoding('utf8'); stream lalu "will properly handle multi-byte characters" dan memberi string utuh. [10]

Bandingkan dengan jawaban contoh dan checklist-nya

"Backpressure adalah sinyal dari tujuan yang lebih lambat bahwa sumber harus berhenti dulu. Setiap stream punya buffer internal dengan ambang highWaterMark, default 64 KiB sejak Node 22. Begitu buffer Writable mencapai ambang itu, write() mengembalikan false. Penulis harus berhenti dan menunggu event 'drain'. Kalau diabaikan, data tetap ditampung di memori karena highWaterMark hanya ambang, bukan batas; contoh di dokumentasi Node memakai ±1,5 GB memori tanpa backpressure vs ±88 MB dengan backpressure, dan GC bekerja lebih keras. Cara paling mudah: pakai stream.pipeline, yang menangani backpressure dan error otomatis. Kalau menulis manual, cek nilai write() dan await once(ws, 'drain')."

Checklist: apakah Anda menyebut…

  • backpressure = tujuan lebih lambat memberi sinyal ke sumber untuk berhenti?
  • highWaterMark sebagai ambang buffer internal (bukan batas keras)?
  • write() mengembalikan false saat buffer mencapai highWaterMark?
  • berhenti menulis dan lanjut setelah event 'drain'?
  • akibat diabaikan: memori membengkak, GC berat, bisa crash?
  • pipeline/pipe menangani backpressure otomatis?
