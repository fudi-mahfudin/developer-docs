worker_threads vs cluster vs child_process

Tiga cara keluar dari satu thread JavaScript: thread di proses yang sama, beberapa proses yang berbagi port, atau menjalankan program lain. Kapan memakai yang mana, dan kapan cukup menambah replika container

Di modul Runtime, Anda melihat bahwa JavaScript di Node berjalan di satu thread, dan pekerjaan CPU berat memblokir event loop untuk semua request (lesson 0004). Stream (lesson 0008–0009) menyelesaikan I/O besar, tapi tidak membantu pekerjaan CPU-bound, yaitu pekerjaan yang waktunya habis untuk menghitung, bukan menunggu disk atau jaringan. Pertanyaan interview yang sering muncul: "Node single-threaded, jadi bagaimana memakai 8 core?"

Target lesson ini: Anda bisa menjawab "Kapan memakai worker_threads, cluster, atau child_process?" tanpa catatan, dalam 60 detik: satu kasus untuk masing-masing, kenapa worker tidak membantu I/O, kenapa state tidak terbagi di cluster, dan kenapa di Kubernetes biasanya cukup menambah replika container.

2. worker_threads: CPU-bound di JavaScript

Dokumentasi Node v24 tegas: worker "are useful for performing CPU-intensive JavaScript operations. They do not help much with I/O-intensive work." I/O bawaan Node sudah asinkron dan lebih efisien daripada worker. [1] Berbeda dengan cluster dan child_process, worker bisa berbagi memori dengan mentransfer ArrayBuffer atau memakai SharedArrayBuffer. [1] 

// main.js
const { Worker } = require('node:worker_threads');

function hashInWorker(password) {
  return new Promise((resolve, reject) => {
    const w = new Worker('./hash-worker.js', { workerData: password });
    w.once('message', resolve);
    w.once('error', reject);
  });
}

// hash-worker.js
const { parentPort, workerData } = require('node:worker_threads');
parentPort.postMessage(slowHash(workerData)); // CPU berat, event loop utama tetap bebas

Contoh di atas membuat satu worker per panggilan supaya mudah dibaca. Di produksi, dokumentasi menyarankan "use a pool of Workers", karena biaya membuat worker bisa lebih besar daripada manfaatnya. [1] Library seperti piscina menyediakan pool siap pakai.

Jangan tertukar dengan libuv thread pool (lesson 0004). UV_THREADPOOL_SIZE hanya menambah thread untuk operasi bawaan seperti fs, crypto.pbkdf2, dan zlib. Kode JavaScript Anda sendiri tetap berjalan di thread utama, kecuali dipindah ke worker.

3. cluster: beberapa proses, satu port

cluster membuat beberapa proses Node (worker) yang "all share server ports". [2] Secara default (semua platform kecuali Windows), proses primary menerima koneksi dan membagikannya ke worker secara round-robin. [3]

Client→ Primary (port 3000)→ round-robin→ Worker 1 … Worker N (proses terpisah)

Dua konsekuensi yang sering ditanyakan:

  • State tidak terbagi. Setiap worker adalah proses dengan memori sendiri. Node "does not provide routing logic", jadi aplikasi sebaiknya tidak bergantung pada objek di memori untuk session dan login. [3] Simpan session di Redis (penyimpanan key-value di memori yang diakses lewat jaringan) atau pakai token.
  • Jumlah worker tidak dikelola otomatis. Worker yang mati tidak dihidupkan ulang sendiri; dokumentasi menyebut aplikasi bertanggung jawab mengelola pool worker. [3]

4. Cluster vs banyak replika container

Kalau aplikasi berjalan di Kubernetes atau platform container sejenis, orkestrator sudah melakukan hal yang dikerjakan cluster: membagi trafik ke banyak instance (Service/load balancer), menghidupkan ulang yang mati (health check), dan menambah instance saat beban naik (autoscaling). Karena itu, pola yang umum adalah satu proses Node per container, lalu menambah replika, bukan menjalankan cluster di dalam container.

  • Replika container: satu proses per container, limit CPU/memori dan metrik per pod jelas, restart ditangani orkestrator.
  • cluster tetap masuk akal di satu VM atau server tanpa orkestrator, misalnya dikelola PM2 (process manager untuk Node).

Ini keputusan arsitektur, bukan aturan Node. Jawaban yang baik di interview menyebut kedua opsi dan alasan memilih salah satunya.

5. child_process: menjalankan program lain

child_process menjalankan proses lain. spawn() adalah dasarnya; exec() menjalankan perintah di dalam shell; execFile() tanpa shell; fork() menjalankan modul Node dengan kanal IPC ke parent. [4] Setiap proses hasil fork() punya memori dan instance V8 sendiri, jadi membuat banyak proses anak tidak disarankan. [5] 

const { spawn } = require('node:child_process');

// Aman: argumen sebagai array, tanpa shell
const p = spawn('ffmpeg', ['-i', inputPath, '-vf', 'scale=640:-1', outPath]);
p.on('close', code => console.log('selesai dengan kode', code));

// Berbahaya: input user masuk ke string shell (command injection)
// exec(`ffmpeg -i ${req.query.file} out.mp4`);

Untuk exec(), dokumentasi memberi peringatan tebal: "Never pass unsanitized user input to this function." [6] Input seperti a.mp4; rm -rf / akan dijalankan shell sebagai dua perintah.

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Soal ini juga ada di bank soal dan bisa ditarik review 0020.

"Kapan Anda memakai worker_threads, cluster, atau child_process? Beri satu contoh kasus untuk masing-masing." (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Ketiganya untuk hal berbeda. worker_threads untuk pekerjaan CPU-bound di JavaScript, misalnya resize gambar atau parsing besar, supaya event loop tidak terblokir; worker satu proses dengan memori bisa dibagi lewat SharedArrayBuffer, dan saya pakai pool karena membuat worker mahal. Untuk I/O biasa worker tidak membantu karena I/O Node sudah asinkron. cluster menjalankan beberapa proses Node yang berbagi satu port, untuk memakai semua core di satu mesin; state seperti session harus di luar proses. Di Kubernetes saya lebih memilih beberapa replika container berproses tunggal karena orkestrator sudah menangani load balancing dan restart. child_process untuk menjalankan program lain seperti ffmpeg, dengan spawn dan argumen array, bukan exec dengan input user."

Checklist: apakah Anda menyebut…

  • worker_threads untuk CPU-bound JavaScript, tidak membantu I/O?
  • worker berbagi memori (SharedArrayBuffer/transfer), sebaiknya lewat pool?
  • cluster = beberapa proses berbagi port untuk memakai semua core?
  • state (session) tidak terbagi antar proses cluster?
  • di container/Kubernetes lebih suka replika ketimbang cluster?
  • child_process untuk program eksternal, hindari exec dengan input user?

Lulus jika minimal 4 dari 6.
