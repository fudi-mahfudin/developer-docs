Memory leak dan profiling

Bagaimana heap V8 dibagi, kenapa memori bisa naik terus walau ada garbage collector, dan alat bawaan Node untuk menemukan penyebabnya

Node punya garbage collector (GC), tapi aplikasi Node tetap bisa bocor memori. GC hanya membebaskan objek yang tidak lagi terjangkau dari kode; leak di JavaScript hampir selalu berarti objek yang tidak dipakai lagi tapi masih dirujuk dari suatu tempat. Pertanyaan interview: "Memori service Anda naik terus sampai crash. Apa yang Anda lakukan?"

Target lesson ini: Anda bisa menjawab "Bagaimana Anda mencari memory leak di Node?" tanpa catatan, dalam 90 detik: apa arti --max-old-space-size, tiga sumber leak yang umum (cache global, closure, listener), langkah membandingkan dua heap snapshot, dan kapan memakai --cpu-prof sebagai gantinya.

1. Heap V8 dan batasnya

V8 (mesin JavaScript di Node) membagi heap berdasarkan umur objek, karena "most objects die young". [1]

Objek baru: new space (young generation)→ GC minor (Scavenger), sering dan cepat→ Bertahan beberapa kali: dipindah ke old space→ GC major (Mark-Compact), jarang dan mahal

Objek yang bocor akhirnya menumpuk di old space, isinya objek berumur panjang seperti cache dan session. [2] Batasnya diatur --max-old-space-size (dalam MiB): "Sets the max memory size of V8's old memory section"; mendekati batas, V8 makin banyak menghabiskan waktu untuk GC. Dokumentasi memberi contoh: di mesin 2 GiB, pakai 1536 supaya ada sisa memori dan tidak swap. [3]

process.memoryUsage() memberi angka yang perlu dipantau: heapUsed/heapTotal untuk heap V8, external dan arrayBuffers untuk memori di luarnya (termasuk semua Buffer), dan rss untuk total memori proses. [4] Jadi Buffer besar tidak dibatasi --max-old-space-size, tapi tetap dihitung oleh limit memori container.

Menaikkan --max-old-space-size bukan perbaikan leak; itu hanya menunda crash. Tanda leak adalah heapUsed yang naik terus setelah GC walau trafik datar, bukan heap yang besar.

2. Sumber leak yang umum

// 1. Cache global tanpa batas: Map hidup selama proses hidup
const cache = new Map();
app.get('/report', async (req, res) => {
  if (!cache.has(req.url)) cache.set(req.url, await buildReport(req.query));
  res.json(cache.get(req.url));            // key unik per query string → tumbuh terus
});

// 2. Listener per request di emitter jangka panjang
app.get('/stream', (req, res) => {
  db.on('change', row => res.write(JSON.stringify(row)));  // tidak pernah dilepas
});

// 3. Closure yang menahan objek besar
function handler() {
  const bigRows = loadAllRows();           // ratusan MB
  setInterval(() => log(bigRows.length), 60_000); // timer menahan bigRows selamanya
}
  • Cache global: beri batas ukuran (LRU, buang yang paling lama tidak dipakai) dan TTL (umur maksimum entri), atau pindahkan cache ke luar proses.
  • Listener: lepas dengan removeListener/off saat request selesai (res.on('close', …)), atau pakai once. Node membantu mendeteksinya: secara default maksimal 10 listener per event; lebih dari itu, Node tetap menambahkannya tetapi mencetak peringatan "possible EventEmitter memory leak" (MaxListenersExceededWarning). [5]
  • Closure dan timer: fungsi yang masih bisa dipanggil (callback timer, listener) menahan semua variabel yang ia rujuk. clearInterval saat tidak dipakai, dan jangan merujuk objek besar dari callback yang berumur panjang.

3. Heap snapshot: menemukan apa yang menumpuk

Heap snapshot adalah foto semua objek di heap beserta siapa yang merujuknya (retainer). Cara mengambilnya: [6]

  • node --inspect app.js, lalu buka Chrome DevTools, tab Memory, "Take heap snapshot". Inspector mendengarkan di 127.0.0.1:9229 secara default; membukanya ke IP publik (--inspect=0.0.0.0) tanpa firewall memungkinkan remote code execution. [7]
  • node --heapsnapshot-signal=SIGUSR2 app.js, lalu kill -USR2 <pid> menulis file .heapsnapshot. [8]
  • require('node:v8').writeHeapSnapshot() dari dalam kode, mis. dipicu endpoint admin yang tidak terbuka ke publik.
  • --heapsnapshot-near-heap-limit=1: tulis snapshot otomatis saat heap mendekati batas, tepat sebelum crash (tidak lagi eksperimental sejak Node 24.13.1). [9]

Langkah menemukan leak dengan dua snapshot: [6]

  1. Biarkan aplikasi selesai startup, lalu pakai fitur yang dicurigai beberapa kali (alokasi awal bukan leak).
  2. Ambil snapshot pertama.
  3. Pakai fitur itu lagi beberapa saat, lalu ambil snapshot kedua.
  4. Di DevTools, pilih snapshot kedua dan ganti tampilan dari Summary ke Comparison. Cari delta positif terbesar, lalu telusuri retainer-nya sampai ketemu variabel yang menahannya.

Hati-hati di produksi: membuat snapshot "requires memory about twice the size of the heap" dan "is a synchronous operation which blocks the event loop". [10] Ambil dari satu instance yang boleh mati tanpa mengganggu availability, atau reproduksi di staging.

4. CPU profiling: kalau masalahnya lambat, bukan bocor

Kalau gejalanya latensi tinggi dan CPU 100%, heap snapshot tidak membantu. Pakai profil CPU: --cpu-prof menjalankan V8 CPU profiler sejak start dan menulis file .cpuprofile saat proses keluar (Node ≥ 22.4: flag ini stabil; sebelumnya eksperimental). [11] File itu dibuka di tab Performance Chrome DevTools untuk melihat fungsi mana yang paling lama. 

node --cpu-prof --cpu-prof-dir=./prof app.js   # jalankan beban, lalu hentikan proses
node --inspect app.js                          # atau rekam langsung dari DevTools
node --prof app.js && node --prof-process isolate-*.log  # profiler tick bawaan

--prof dan --prof-process adalah alternatif yang lebih lama: hasilnya ringkasan teks fungsi yang paling sering muncul di sampel. [12] Temuan yang sering muncul: JSON.parse/JSON.stringify payload besar, regex yang lambat, fungsi sync (*Sync), dan hashing password di thread utama. Solusinya kembali ke lesson 0004 dan 0010: pindahkan ke thread pool atau worker.

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Soal ini juga ada di bank soal dan bisa ditarik review 0020.

"Memori API Node Anda naik terus sampai container di-OOM-kill setiap dua hari. Bagaimana Anda mencari penyebabnya?" (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Pertama saya pastikan memang leak: grafik heapUsed yang naik terus walau trafik datar, bukan sekadar heap yang besar. Lalu saya reproduksi di staging. Saya jalankan dengan --inspect yang hanya terbuka di localhost, biarkan aplikasi selesai startup, pakai fitur yang dicurigai, ambil heap snapshot pertama, pakai lagi beberapa saat, ambil snapshot kedua, lalu bandingkan di mode Comparison di Chrome DevTools dan cari delta positif terbesar beserta retainer-nya. Di produksi bisa pakai --heapsnapshot-signal atau --heapsnapshot-near-heap-limit, tapi snapshot memblokir event loop dan butuh memori sekitar dua kali heap, jadi hanya di instance yang boleh mati. Tersangka umum: cache global tanpa batas, listener yang ditambah per request, closure yang menahan objek besar, timer yang tidak di-clear. --max-old-space-size hanya menunda crash, bukan solusi."

Checklist: apakah Anda menyebut…

  • membuktikan leak dengan tren memori (heapUsed naik walau trafik datar)?
  • --inspect (hanya localhost) + Chrome DevTools tab Memory?
  • dua heap snapshot lalu mode Comparison, cari delta dan retainer?
  • risiko snapshot di produksi: blok event loop, butuh ±2x memori heap?
  • tersangka umum: cache global, listener, closure, timer?
  • --max-old-space-size hanya menunda, bukan memperbaiki leak?

Lulus jika minimal 4 dari 6.
