CommonJS vs ESM

require vs import, cara Node memilih format sebuah file, dan apa yang terjadi saat kedua format saling memuat

Hampir setiap proyek Node yang Anda buka memakai salah satu dari dua sistem modul, kadang keduanya sekaligus. Error seperti "Cannot use import statement outside a module" atau "__dirname is not defined" muncul karena Node memperlakukan sebuah file dengan format yang tidak Anda kira. Interviewer biasanya bertanya: apa bedanya, bagaimana Node menentukan format, dan apakah CommonJS bisa memuat ESM.

Target lesson ini: Anda bisa menjawab "Apa beda CommonJS dan ES module di Node, dan bagaimana keduanya bisa saling memuat?" tanpa catatan, dalam 60 detik: sintaks dan sifat masing-masing, aturan .mjs/.cjs/field "type", dan batas require(esm).

1. Dua sistem modul

CommonJS adalah sistem modul asli Node: setiap file adalah modul, dimuat dengan require(), dan mengekspor lewat module.exports. [1] ES module (ESM) adalah standar JavaScript yang juga dipakai browser: import dan export. [2] 

// CommonJS: math.cjs
const { PI } = Math;
module.exports = { area: r => PI * r ** 2 };
// pemakai
const { area } = require('./math.cjs');

// ESM: math.mjs
export const area = r => Math.PI * r ** 2;
// pemakai
import { area } from './math.mjs';

Top-level await berarti await boleh ditulis langsung di badan modul ESM, di luar fungsi async; modul yang mengimpornya menunggu sampai selesai. Kalau Promise-nya tidak pernah selesai, proses keluar dengan kode 13. [2]

2. Cara Node memilih format sebuah file

Aturannya dari dokumentasi Node: [3]

  • .mjs selalu ESM, .cjs selalu CommonJS.
  • .js mengikuti field "type" di package.json terdekat: "module" berarti ESM, "commonjs" berarti CommonJS.
  • Tanpa field "type", file .js "ambigu": Node menjalankannya sebagai CommonJS, lalu mencoba ulang sebagai ESM kalau ada sintaks import/export (syntax detection, aktif default sejak Node ≥ 22.7). Cara ini ada biaya performanya, jadi dokumentasi menyarankan paket selalu menulis "type", bahkan kalau semua isinya CommonJS. [3]

3. Interop: ESM memuat CommonJS

Dari ESM, import bisa memuat file CommonJS. Objek module.exports menjadi default export. Named export kadang juga tersedia, tapi hanya dari analisis statis yang bersifat best-effort, jadi default import yang paling andal. [2] 

// legacy.cjs
module.exports = { a: 1 };

// app.mjs
import lib from './legacy.cjs';   // lib = { a: 1 }
import { a } from './legacy.cjs'; // hanya jalan kalau analisis statis menemukan 'a'

4. Interop: CommonJS memuat ESM, dan require(esm)

Dari CommonJS, cara yang selalu jalan adalah import() dinamis: ia mengembalikan Promise, jadi pemanggilnya harus asinkron. [2] Dulu require() pada file ESM selalu error. Sekarang tidak lagi:

  • require(esm) tidak lagi butuh flag sejak Node ≥ 22.12 (juga 23.0 dan 20.19), dan tidak lagi berstatus experimental sejak Node 24.15. [1]
  • Syaratnya: modul (dan seluruh graph yang ia impor) sepenuhnya sinkron, tanpa top-level await. Kalau ada, Node melempar ERR_REQUIRE_ASYNC_MODULE dan menyarankan import(). [1]
  • Hasilnya adalah namespace object modul itu. Default export ada di properti default, bukan nilai yang langsung dikembalikan.
// point.mjs
export default class Point { constructor(x, y) { this.x = x; this.y = y; } }

// app.cjs (Node ≥ 22.12)
const { default: Point } = require('./point.mjs');

// app.cjs, cara yang jalan di semua versi dan untuk modul dengan top-level await
const { default: Point2 } = await import('./point.mjs'); // di dalam fungsi async

Di interview, sebut versi: "require(esm) aktif tanpa flag sejak Node 22.12, asal tanpa top-level await." Jawaban "CommonJS tidak bisa me-require ESM" sudah usang untuk Node 24.

5. Memilih untuk proyek baru

Untuk aplikasi baru yang dijalankan langsung oleh Node, ESM dengan "type": "module" adalah pilihan standar. CommonJS masih wajar untuk codebase lama, atau ketika toolchain proyek mengompilasi ke CommonJS (Anda akan melihat require di folder dist/ hasil build banyak proyek TypeScript; konfigurasinya dibahas di lesson 0015). Yang penting adalah konsisten dan eksplisit: tulis "type", dan pakai .cjs/.mjs hanya untuk pengecualian.

Bandingkan dengan jawaban contoh dan checklist-nya

"CommonJS memakai require dan module.exports, dimuat sinkron; ES module memakai import/export, standar JavaScript, dan mendukung top-level await. Node menentukan formatnya dari ekstensi dan field type: .mjs selalu ESM, .cjs selalu CommonJS, .js mengikuti "type" di package.json terdekat. Di ESM, ekstensi file wajib ditulis di import relatif, dan __dirname diganti import.meta.dirname. Dari ESM, import file CommonJS memberi module.exports sebagai default export. Dari CommonJS, dulu hanya bisa pakai import() yang asinkron; sejak Node 22.12 require(esm) aktif tanpa flag dan di Node 24 sudah stabil, asal modulnya tidak memakai top-level await. Kalau memakai, Node melempar ERR_REQUIRE_ASYNC_MODULE dan saya pakai import(). Untuk paket baru saya tulis "type" secara eksplisit."

Checklist: apakah Anda menyebut…

  • require/module.exports vs import/export, CommonJS dimuat sinkron?
  • format ditentukan .mjs/.cjs dan field "type" di package.json terdekat?
  • ESM wajib ekstensi di import relatif, tanpa __dirname (pakai import.meta.dirname)?
  • import CommonJS dari ESM: module.exports menjadi default export?
  • require(esm) jalan tanpa flag sejak Node 22.12, kecuali modul dengan top-level await?
  • import() sebagai jalan dari CommonJS ke ESM asinkron?
