TypeScript di Node, env var, dan config per environment

Build dengan tsc vs type stripping bawaan Node, apa arti module: nodenext, dan cara membaca config dari environment tanpa kejutan

Anda sudah memakai TypeScript. Yang sering ditanyakan di interview adalah apa yang sebenarnya dijalankan Node: file .ts langsung, atau JavaScript hasil kompilasi? Bagian kedua lesson ini membahas config. Aplikasi yang sama berjalan di laptop, CI, staging, dan produksi dengan nilai berbeda, dan nilai itu datang dari environment variable.

Target lesson ini: Anda bisa menulis di kertas modul config.ts yang membaca, mengonversi, dan memvalidasi env var saat start, dan menjelaskan kenapa aplikasi NestJS tetap di-build dengan tsc/SWC walaupun Node 24 bisa menjalankan .ts langsung.

1. Dua cara menjalankan TypeScript

  • Build dengan tsc (atau SWC): kode dikompilasi ke JavaScript di dist/, lalu Node menjalankan hasilnya. tsc juga melakukan type-check. Semua fitur TypeScript didukung.
  • Type stripping: Node menjalankan file .ts yang hanya berisi sintaks TypeScript yang bisa dihapus (erasable). Anotasi tipe diganti spasi, dan tidak ada type-check. [1] Label versi: aktif default sejak Node ≥ 23.6, tanpa peringatan experimental sejak 24.3, dan berstatus stabil sejak Node 24.12. [1]

Batas type stripping yang perlu Anda sebut di interview: [1]

  • Fitur yang butuh pembuatan kode JavaScript error tanpa flag --experimental-transform-types: enum, namespace berisi kode runtime, parameter properties (constructor(private repo: Repo)), dan import alias.
  • Decorator tidak ditransformasi dan menghasilkan parser error.
  • Node tidak membaca tsconfig.json, jadi paths dan target lama tidak berlaku. Import tipe harus memakai import type. File .ts di node_modules ditolak.

Akibatnya untuk NestJS: decorator (@Module, @Injectable) dan parameter properties ada di setiap file, jadi aplikasi NestJS tetap di-build. Nest CLI (nest build) memakai tsc, dan bisa diganti SWC, yang menurut dokumentasi NestJS sekitar 20 kali lebih cepat tapi tidak melakukan type-check sendiri. [3] Type stripping cocok untuk script kecil dan tooling.

2. module: nodenext

Opsi module di tsconfig.json memberi tahu TypeScript sistem modul runtime target. Dengan nodenext, TypeScript meniru aturan Node dari lesson 0013: [2]

  • .mts selalu ESM, .cts selalu CommonJS, .ts mengikuti field "type" di package.json terdekat. Format output mengikuti format yang terdeteksi.
  • module: nodenext sekaligus memaksa moduleResolution: nodenext. [2]
  • Import relatif di file ESM wajib berekstensi, dan yang ditulis adalah ekstensi hasil build: './db.js', walaupun file sumbernya db.ts. TypeScript memetakannya ke file sumber. [2]
// tsconfig.json (potongan)
{ "compilerOptions": { "module": "nodenext", "outDir": "dist" } }

// src/app.ts, dengan "type": "module" di package.json
import { db } from './db.js';    // benar: db.ts dikompilasi menjadi db.js
// import { db } from './db';    // error di ESM: ekstensi wajib

3. Env var dan --env-file

Environment variable adalah pasangan nama=nilai yang diberikan sistem operasi ke sebuah proses. Di Node, semuanya ada di process.env. Nilainya selalu string: assignment non-string pun dikonversi menjadi string, dan perilaku konversi itu sudah deprecated. [5] Jadi FEATURE_X=false menghasilkan string "false", yang truthy.

File .env dulu dimuat dengan paket pihak ketiga. Sekarang Node bisa memuatnya sendiri dengan --env-file (Node ≥ 20.6, tidak lagi experimental sejak 24.10): [4] 

node --env-file=.env --env-file=.env.local dist/main.js
  • Kalau variabel yang sama ada di environment dan di file, environment menang.
  • Beberapa --env-file boleh dipakai; file berikutnya menimpa file sebelumnya.
  • File yang tidak ada membuat error; pakai --env-file-if-exists kalau file itu opsional. [4]
  • Dari kode, process.loadEnvFile() memuat ./.env secara default. [5]

4. Config per environment: satu modul, validasi saat start

Pola yang aman: kode aplikasi tidak membaca process.env di mana-mana. Satu modul config membaca semua variabel, mengonversi tipe, memvalidasi, dan throw saat start kalau ada yang salah (fail fast). Bedanya antar environment hanya isi env: .env untuk laptop (tidak di-commit), variabel CI untuk test, dan secret dari platform deploy untuk produksi. 

// config.ts
function required(name: string): string {
  const v = process.env[name];
  if (!v) throw new Error(`Env ${name} wajib diisi`);
  return v;
}
const port = Number(process.env.PORT ?? 3000);
if (!Number.isInteger(port)) throw new Error('PORT harus angka');

export const config = Object.freeze({
  port,
  databaseUrl: required('DATABASE_URL'),
  isProd: process.env.NODE_ENV === 'production',
});

Di NestJS, peran modul ini diambil @nestjs/config dengan validasi skema; itu dibahas di lesson 0032. Prinsipnya sama: baca sekali, validasi saat start.

Checklist: apakah Anda…

  • membaca dari process.env di satu modul config, bukan tersebar di kode?
  • mengubah PORT ke number dan memvalidasinya (nilai env selalu string)?
  • membuat DATABASE_URL wajib: throw kalau kosong?
  • memvalidasi saat start (fail fast), bukan saat request?
  • menyebut --env-file (atau process.loadEnvFile) untuk memuat .env?
  • menyebut environment mengalahkan file .env, dan secret produksi tidak di-commit?
