Kenapa NestJS; @Module dan feature module

Apa yang ditambahkan NestJS di atas Express, dan bagaimana aplikasi dipecah menjadi module yang saling meng-import

Modul ini pindah dari runtime Node ke framework. Anda sudah pernah membuat API Express: satu file app.js, router, dan service yang di-require langsung. Di interview NestJS, pertanyaan pembukanya hampir selalu "kenapa NestJS dan bukan Express saja?", lalu "jelaskan module di Nest". Lesson ini menjawab keduanya.

Target lesson ini: Anda bisa menjawab "Kenapa NestJS, dan apa isi sebuah @Module?" tanpa catatan, dalam 60 detik: struktur + DI di atas platform HTTP (Express default, Fastify opsional), empat properti @Module (imports, providers, controllers, exports), kenapa provider harus di-export supaya bisa dipakai module lain, dan kapan (jarang) memakai @Global.

1. Kenapa NestJS: struktur dan DI, bukan pengganti Express

Express hanya menyediakan routing dan middleware. Cara menyusun folder, cara service saling memanggil, dan cara mengganti dependency saat test diserahkan ke tim. NestJS menambahkan tiga hal di atasnya:

  • Struktur yang seragam: aplikasi dipecah menjadi module, controller (menerima request), dan provider (logika bisnis, akses data). Proyek Nest yang berbeda terlihat mirip, jadi orang baru cepat paham.
  • Dependency injection (DI): class tidak membuat dependency-nya sendiri dengan new; ia menyatakan kebutuhannya di constructor dan framework yang membuat serta menyuntikkan instance-nya. Dokumentasi Nest menyebut ini menyerahkan instansiasi ke "the IoC container" (Inversion of Control: framework, bukan kode Anda, yang memegang kendali pembuatan object). [1] Hasilnya: dependency mudah diganti mock saat test.
  • Pipeline request yang eksplisit: guard, pipe, interceptor, dan exception filter (modul berikutnya) punya tempat yang jelas, bukan middleware Express yang urutannya diatur manual.

Nest tidak membuang Express. "Nest is designed to be platform-agnostic"; secara bawaan ia memakai paket @nestjs/platform-express, dan bisa diganti Fastify (lebih cepat) tanpa mengubah controller. [2] Sejak NestJS 12, dokumentasi juga menyebut platform ketiga, @nestjs/platform-node, yang berjalan langsung di modul node:http. [2] 

// main.ts: titik masuk aplikasi
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule); // Express secara default
  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();

Jawaban "kenapa NestJS" yang baik juga menyebut biayanya: lebih banyak boilerplate (decorator, module), kurva belajar DI dan RxJS, dan overhead yang tidak perlu untuk script kecil atau satu-dua endpoint.

2. @Module: empat properti

Setiap aplikasi Nest punya minimal satu module, yaitu root module (AppModule). Decorator @Module() menerima object dengan empat properti: [3]

PropertiIsi
providersProvider yang dibuat oleh injector Nest dan bisa dipakai setidaknya di dalam module ini
controllersController milik module ini yang harus diinstansiasi
importsModule lain yang meng-export provider yang dibutuhkan module ini
exportsBagian dari providers yang boleh dipakai module lain yang meng-import module ini
 
@Module({
  imports: [PrismaModule],          // butuh PrismaService dari module lain
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService],          // module lain boleh meng-inject UsersService
})
export class UsersModule {}

Aturan yang paling sering menjebak: provider bersifat privat untuk module-nya. Kalau OrdersModule ingin meng-inject UsersService, UsersModule harus mencantumkannya di exports dan OrdersModule harus meng-import UsersModule. Kalau salah satunya lupa, Nest gagal start dengan error "Nest can't resolve dependencies of …".

3. Feature module, shared module, dan re-export

AppModule (root)imports → OrdersModule (feature)imports → UsersModule (exports UsersService)
  • Feature module: satu module per area bisnis (UsersModule, OrdersModule), berisi controller dan service-nya sendiri. Root module hanya meng-import feature module.
  • Shared module: module adalah singleton secara default, dan "every module is automatically a shared module". Kalau UsersService di-export dari satu module, semua module yang meng-import-nya mendapat instance yang sama. Kalau Anda malah mendaftarkan UsersService di providers dua module, Anda mendapat dua instance terpisah. [3]
  • Re-export: module boleh meng-export module yang ia import, mis. CoreModule meng-import dan meng-export CommonModule, sehingga siapa pun yang meng-import CoreModule ikut mendapat isi CommonModule. [3]

4. @Global: jalan pintas yang sebaiknya jarang dipakai

Untuk provider yang dipakai hampir di mana-mana (config, koneksi database), @Global() membuat module itu global: provider yang ia export bisa di-inject tanpa module lain meng-import-nya. Module global cukup didaftarkan sekali, biasanya oleh root module. Dokumentasi Nest memperingatkan bahwa membuat semuanya global "is not a recommended design practice": dependency jadi tidak terlihat di imports. [3] 

@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}

Banyak paket resmi memberi pilihan global lewat opsi, mis. ConfigModule.forRoot({ isGlobal: true }). Itu dynamic module, dibahas di lesson 0018.

"Kenapa tim Anda memilih NestJS dan bukan Express saja? Lalu jelaskan bagaimana module di Nest berbagi service." (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Express hanya memberi routing dan middleware; struktur dan cara service saling memanggil diserahkan ke tim. Nest menambahkan struktur seragam (module, controller, provider), dependency injection lewat IoC container sehingga dependency mudah diganti mock saat test, dan pipeline request yang jelas: guard, pipe, interceptor, filter. Di bawahnya tetap Express secara default, atau Fastify kalau butuh performa, tanpa mengubah controller. Biayanya boilerplate dan kurva belajar. Setiap module mendeklarasikan providers, controllers, imports, dan exports. Provider privat untuk module-nya; supaya module lain bisa memakai UsersService, UsersModule harus meng-export-nya dan module pemakai meng-import UsersModule. Module singleton, jadi semua pemakai mendapat instance yang sama. @Global hanya untuk hal seperti config atau database, karena dependency jadi tidak terlihat."

Checklist: apakah Anda menyebut…

  • struktur seragam (module, controller, provider) sebagai alasan utama?
  • dependency injection / IoC container dan manfaatnya untuk test?
  • Nest berjalan di atas Express (default) atau Fastify, bukan menggantikannya?
  • empat properti @Module: imports, providers, controllers, exports?
  • provider harus di-export dan module-nya di-import supaya bisa di-inject di module lain?
  • @Global hanya untuk sedikit hal (config, database), bukan default?

Lulus jika minimal 4 dari 6.
