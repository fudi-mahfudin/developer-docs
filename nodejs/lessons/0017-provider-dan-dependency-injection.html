Provider dan dependency injection

Bagaimana DI container Nest mencocokkan dependency lewat token, empat bentuk custom provider, dan apa yang terjadi kalau dua class saling bergantung

Di lesson 0016 module mendaftarkan provider dan meng-export-nya. Lesson ini masuk ke dalam: apa yang dilakukan container saat melihat constructor, dan bagaimana mendaftarkan sesuatu yang bukan class biasa (konstanta config, client hasil factory, mock untuk test). Pertanyaan "jelaskan useFactory" dan "bagaimana Nest menangani circular dependency" sering muncul di interview mid-level.

Target lesson ini: Anda bisa menjawab "Bagaimana DI di Nest bekerja?" tanpa catatan, dalam 60 detik: provider + token + container, kapan memakai useClass, useValue, useFactory, atau useExisting, kenapa interface tidak bisa jadi token, dan bagaimana forwardRef memecah circular dependency. Anda juga bisa menulis di kertas provider useFactory yang bergantung pada provider lain.

1. Provider, token, dan container

Menurut dokumentasi Nest, "the main idea behind a provider is that it can be injected as a dependency". Decorator @Injectable() menempelkan metadata yang menyatakan class itu dikelola Nest. Cara injeksi yang disarankan adalah lewat constructor, karena constructor "states explicitly which dependencies the class requires". Dengan scope default, Nest membuat instance sekali dan membagikannya ke setiap class yang membutuhkannya. [1] 

@Injectable()
export class UsersService {
  constructor(private readonly prisma: PrismaService) {} // token = class PrismaService
}

// di @Module: providers: [UsersService]
// sama dengan bentuk panjang:  { provide: UsersService, useClass: UsersService }

Saat container membuat UsersService, ia membaca tipe parameter constructor, mencari provider dengan token yang sama, membuatnya dulu kalau belum ada (rekursif), lalu menyuntikkannya. [2]

Baca constructor→ Cari provider per token→ Buat dependency dulu→ Simpan dan bagikan instance

Setiap injection token adalah kunci pencarian di container. Biasanya class itu sendiri, tapi boleh juga string, Symbol, atau enum TypeScript. Interface tidak bisa jadi token: "TypeScript types and interfaces are erased during compilation, so Nest can't reference them at runtime." Untuk token non-class, pakai @Inject(TOKEN) di parameter constructor. [2]

2. Empat bentuk custom provider

BentukArtinyaContoh pemakaian
useClassToken diselesaikan ke class tertentu, bisa dipilih saat runtimeImplementasi berbeda per environment
useValueToken diselesaikan ke nilai yang sudah jadiKonstanta config, mock object saat test
useFactoryToken diselesaikan ke hasil fungsi; argumen fungsi di-inject dari daftar injectClient yang butuh config dulu, inisialisasi async
useExistingAlias: token kedua menunjuk ke provider yang sudah adaNama lama tetap jalan setelah refactor

Detail dari dokumentasi: useValue berguna untuk "replacing a real implementation with a mock object"; useFactory menerima array inject berisi provider yang "Nest resolves and passes as arguments to the factory function", dan provider di daftar itu boleh ditandai opsional; dengan useExisting, kalau keduanya singleton, kedua token "resolve to the same instance". [2] 

export const REDIS = Symbol('REDIS');

@Module({
  imports: [ConfigModule],
  providers: [
    {
      provide: REDIS,
      useFactory: async (config: ConfigService) => {
        const client = createClient({ url: config.get('REDIS_URL') });
        await client.connect();             // factory boleh async
        return client;
      },
      inject: [ConfigService],              // urutan = urutan argumen factory
    },
  ],
  exports: [REDIS],                         // export pakai token
})
export class RedisModule {}

// pemakai:  constructor(@Inject(REDIS) private readonly redis: RedisClientType) {}

Custom provider tetap privat untuk module yang mendeklarasikannya. Untuk dipakai module lain, export dengan token-nya atau dengan object provider lengkapnya. [2]

3. Circular dependency dan forwardRef

"A circular dependency occurs when two classes depend on each other": UsersService butuh AuthService dan sebaliknya. Container tidak bisa membuat salah satunya lebih dulu, jadi start gagal. Nest menyediakan forwardRef(), yang dipasang di kedua sisi bersama @Inject(); untuk dua module yang saling meng-import, forwardRef() juga dipasang di kedua sisi imports. [3] 

@Injectable()
export class UsersService {
  constructor(
    @Inject(forwardRef(() => AuthService))
    private readonly auth: AuthService,
  ) {}
}
// AuthService melakukan hal yang sama untuk UsersService.
// Module: imports: [forwardRef(() => AuthModule)]

Dua peringatan dari dokumentasi: hindari circular dependency kalau bisa, dan "the order of instantiation is indeterminate", jadi jangan menulis kode yang bergantung pada constructor mana yang dipanggil lebih dulu. [3] Jawaban yang lebih baik di interview: forwardRef adalah jalan keluar darurat; perbaikan sebenarnya adalah memindahkan logika bersama ke service ketiga yang dipakai keduanya.

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Soal ini juga ada di bank soal dan bisa ditarik review 0029.

"Jelaskan bagaimana dependency injection di NestJS bekerja, dan kapan Anda memakai custom provider." (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Setiap provider didaftarkan di module dengan sebuah token, biasanya class-nya sendiri. Saat container membuat class, ia membaca parameter constructor, mencari provider dengan token yang sama, membuatnya dulu kalau perlu, lalu menyuntikkannya. Default-nya singleton: satu instance dibagi ke semua pemakai. Interface tidak bisa jadi token karena hilang saat kompilasi, jadi untuk hal non-class saya pakai string atau Symbol dengan @Inject. Custom provider: useValue untuk konstanta atau mock di test, useClass untuk memilih implementasi, useFactory kalau nilainya perlu dihitung dari provider lain lewat inject, misalnya client Redis dari ConfigService, dan useExisting untuk alias. Circular dependency bisa diakali forwardRef di kedua sisi, tapi saya lebih suka memecahnya dengan service ketiga."

Checklist: apakah Anda menyebut…

  • token sebagai kunci pencarian dan container yang membaca constructor?
  • singleton sebagai default (satu instance dibagi)?
  • interface tidak bisa jadi token; pakai string/Symbol + @Inject?
  • useValue dan useClass beserta contoh pemakaiannya?
  • useFactory dengan inject, dan useExisting sebagai alias?
  • forwardRef untuk circular dependency, dan lebih baik dipecah dengan service ketiga?

Lulus jika minimal 4 dari 6.

Latihan tulis kode — di kertas, tanpa IDE

Tulis jawabannya di kertas dulu, baru buka contoh. Soal ini juga ada di bank soal dan bisa ditarik review 0029.

"Tulis provider dengan token MAILER memakai useFactory: ia membaca SMTP_URL dari ConfigService dan mengembalikan new Mailer(url). Export provider itu, lalu tulis constructor service yang meng-inject-nya." (5 menit)
Bandingkan dengan jawaban contoh dan checklist-nya 
export const MAILER = 'MAILER';

@Module({
  imports: [ConfigModule],
  providers: [{
    provide: MAILER,
    useFactory: (config: ConfigService) => new Mailer(config.getOrThrow('SMTP_URL')),
    inject: [ConfigService],
  }],
  exports: [MAILER],
})
export class MailModule {}

@Injectable()
export class NotifyService {
  constructor(@Inject(MAILER) private readonly mailer: Mailer) {}
}

Checklist: apakah kode Anda…

  • memakai token non-class (string atau Symbol) yang diekspor sebagai konstanta?
  • menulis provide + useFactory yang mengembalikan instance?
  • mencantumkan inject: [ConfigService] sesuai urutan argumen factory?
  • meng-import module yang menyediakan ConfigService?
  • meng-export provider lewat token-nya?
  • meng-inject dengan @Inject(MAILER), bukan mengandalkan tipe saja?

Lulus jika minimal 4 dari 6.
