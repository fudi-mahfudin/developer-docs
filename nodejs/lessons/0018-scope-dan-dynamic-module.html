Scope provider dan dynamic module

Kapan provider dibuat ulang per request, kenapa scope itu merambat ke atas, dan bagaimana module menerima konfigurasi lewat forRoot, forFeature, atau register

Di lesson 0017 semua provider singleton: dibuat sekali saat start. Itu cocok untuk Node, karena satu proses melayani banyak request di satu thread. Lesson ini membahas pengecualiannya (scope REQUEST dan TRANSIENT) beserta biayanya, lalu pola yang dipakai hampir semua paket resmi Nest: dynamic module seperti ConfigModule.forRoot() dan TypeOrmModule.forFeature().

Target lesson ini: Anda bisa menjawab "Apa itu scope provider, dan apa itu dynamic module?" tanpa catatan, dalam 60 detik: tiga scope (DEFAULT, REQUEST, TRANSIENT), kenapa request scope merambat ke pemakainya dan apa biayanya, serta arti konvensi forRoot / forFeature / register. Anda juga bisa menulis di kertas dynamic module sederhana dengan forRoot(options).

1. Tiga scope

ScopeInstanceContoh pemakaian
DEFAULT (singleton)Satu instance dibagi ke seluruh aplikasiHampir semua service, repository, client database
REQUESTInstance baru untuk setiap request masuk, dibuang setelah request selesaiData per request: tenant, user, correlation id
TRANSIENTSetiap pemakai yang meng-inject mendapat instance sendiriLogger yang menyimpan nama konteks pemakainya

Definisi di tabel mengikuti dokumentasi Nest, yang juga menyatakan "Singleton scope is recommended for most use cases": instance di-cache dan hanya diinisialisasi sekali saat start. [1]

import { Injectable, Scope, Inject } from '@nestjs/common';
import { REQUEST } from '@nestjs/core';
import type { Request } from 'express';

@Injectable({ scope: Scope.REQUEST })
export class TenantContext {
  constructor(@Inject(REQUEST) private readonly req: Request) {}
  get tenantId() { return this.req.headers['x-tenant-id']; }
}

2. Scope merambat ke atas (bubbling) dan biayanya

Scope REQUEST tidak berhenti di provider yang Anda tandai. Dokumentasi memberi contoh rantai CatsController <- CatsService <- CatsRepository: kalau hanya CatsService yang request-scoped, CatsController yang meng-inject-nya ikut menjadi request-scoped, sedangkan CatsRepository di bawahnya tetap singleton. [1] Alasannya sederhana: singleton tidak bisa memegang referensi ke object yang berganti setiap request.

CatsController → ikut REQUEST← CatsService · REQUEST← CatsRepository · tetap singleton

Biayanya: setiap request, Nest membuat ulang seluruh rantai di atas provider itu. Menurut dokumentasi, aplikasi yang dirancang dengan baik dan memakai request-scoped provider seharusnya tidak melihat kenaikan latency lebih dari "~5%". [1] Dua akibat lain: lifecycle hook seperti onModuleInit tidak dipanggil untuk class request-scoped [2], dan satu provider request-scoped yang di-inject ke banyak tempat bisa membuat sebagian besar graf ikut dibuat per request.

Alternatif yang lebih murah untuk "data per request" adalah AsyncLocalStorage dari modul node:async_hooks, yang menyimpan konteks sepanjang rantai async satu request tanpa mengubah scope provider. Untuk aplikasi multi-tenant, dokumentasi Nest juga menyediakan durable providers: satu sub-graf dipakai ulang per tenant, bukan per request. [1]

3. Dynamic module: module yang dikonfigurasi saat dipakai

Module biasa (static) selalu berisi provider yang sama. Dynamic module menerima opsi dari pemakainya. "Dynamic modules let you create modules that are configured at runtime." [3] Secara teknis, dynamic module adalah method static yang mengembalikan object dengan properti yang sama seperti @Module, "plus the module property"; properti itu memperluas metadata @Module, bukan menimpanya. [4] 

@Module({})
export class MailModule {
  static forRoot(options: { from: string }): DynamicModule {
    return {
      module: MailModule,
      providers: [
        { provide: MAIL_OPTIONS, useValue: options },
        MailService,                  // MailService meng-inject MAIL_OPTIONS
      ],
      exports: [MailService],
      global: false,
    };
  }
}

// pemakai: imports: [MailModule.forRoot({ from: 'no-reply@app.id' })]

Nama method-nya bukan aturan keras, tapi paket @nestjs/* mengikuti konvensi berikut: [4]

MethodArtiContoh
forRootDikonfigurasi sekali, konfigurasinya dipakai ulang di banyak tempatConfigModule.forRoot(), koneksi database di root module
forFeatureMemakai konfigurasi forRoot, tapi menyesuaikan sebagian untuk satu feature moduleTypeOrmModule.forFeature([User]) di UsersModule
registerDikonfigurasi khusus untuk module pemanggil sajaHttpModule.register({ timeout: 5000 })

Masing-masing biasanya punya pasangan async, mis. forRootAsync, untuk opsi yang bergantung pada provider lain (bentuknya useFactory + inject seperti lesson 0017). Untuk menulis dynamic module sendiri dengan lebih sedikit kode, Nest menyediakan ConfigurableModuleBuilder. [4] 

TypeOrmModule.forRootAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({ url: config.get('DATABASE_URL') }),
})

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Soal ini juga ada di bank soal dan bisa ditarik review 0029.

"Rekan Anda ingin membuat semua service request-scoped supaya bisa membaca user dari request. Apa tanggapan Anda?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Nest punya tiga scope: DEFAULT atau singleton, REQUEST yang dibuat ulang per request, dan TRANSIENT yang memberi instance sendiri ke setiap pemakai. Singleton direkomendasikan karena dibuat sekali saat start. Request scope merambat ke atas: controller atau service yang meng-inject provider request-scoped ikut dibuat ulang setiap request, jadi kalau semuanya request-scoped, seluruh graf dibuat per request. Dokumentasi menyebut aplikasi yang dirancang baik sekitar 5% latency tambahan, tapi itu kalau dipakai hemat. Lifecycle hook seperti onModuleInit juga tidak jalan untuk class request-scoped. Untuk membaca user, saya ambil dari request di controller lewat parameter decorator lalu oper sebagai argumen, atau simpan di AsyncLocalStorage. Kalau memang butuh satu provider per request, cukup provider kecil itu, bukan semuanya."

Checklist: apakah Anda menyebut…

  • tiga scope: DEFAULT, REQUEST, TRANSIENT?
  • singleton sebagai rekomendasi default?
  • request scope merambat ke atas ke pemakainya (bubbling)?
  • biaya: graf dibuat ulang per request, latency bertambah?
  • lifecycle hook tidak dipanggil untuk class request-scoped?
  • alternatif: oper data sebagai argumen, AsyncLocalStorage, atau batasi ke satu provider kecil?

Lulus jika minimal 4 dari 6.

Latihan tulis kode — di kertas, tanpa IDE

Tulis jawabannya di kertas dulu, baru buka contoh. Soal ini juga ada di bank soal dan bisa ditarik review 0029.

"Tulis dynamic module StorageModule dengan static forRoot(options: { bucket: string }). Opsi disimpan dengan token STORAGE_OPTIONS, StorageService meng-inject opsi itu, dan module bisa dijadikan global lewat opsi isGlobal." (5 menit)
Bandingkan dengan jawaban contoh dan checklist-nya 
export const STORAGE_OPTIONS = Symbol('STORAGE_OPTIONS');

@Injectable()
export class StorageService {
  constructor(@Inject(STORAGE_OPTIONS) private readonly opts: { bucket: string }) {}
}

@Module({})
export class StorageModule {
  static forRoot(options: { bucket: string; isGlobal?: boolean }): DynamicModule {
    return {
      module: StorageModule,
      global: options.isGlobal ?? false,
      providers: [{ provide: STORAGE_OPTIONS, useValue: options }, StorageService],
      exports: [StorageService],
    };
  }
}

Checklist: apakah kode Anda…

  • memakai method static yang mengembalikan DynamicModule?
  • mengisi properti module dengan class module itu sendiri?
  • menyimpan opsi sebagai provider useValue dengan token sendiri?
  • meng-inject opsi di service dengan @Inject(TOKEN)?
  • meng-export StorageService supaya bisa dipakai pemanggil?
  • memetakan isGlobal ke properti global?

Lulus jika minimal 4 dari 6.
