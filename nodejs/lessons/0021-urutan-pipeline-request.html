Urutan pipeline request NestJS

Middleware, guard, interceptor, pipe, handler, exception filter: siapa jalan lebih dulu, dan di level mana masing-masing dipasang

Modul NestJS inti membahas bagaimana controller dan provider dirakit oleh DI container. Modul ini membahas apa yang terjadi pada satu request sebelum dan sesudah method controller dipanggil. Pertanyaan interview yang paling klasik di sini pendek: "Sebutkan urutan eksekusinya." Lesson ini memberi urutan itu, lalu tiga lesson berikutnya membedah tiap komponen.

Target lesson ini: Anda bisa menyebut urutan pipeline request NestJS tanpa catatan, memilih komponen yang tepat untuk satu kebutuhan (otorisasi, validasi, bentuk response, format error), dan menjelaskan beda memasang komponen secara global, per controller, dan per method, termasuk kenapa APP_GUARD berbeda dari useGlobalGuards().

1. Satu request, tujuh langkah

Dokumentasi NestJS merangkumnya dalam satu kalimat: "a request flows through middleware, then guards, then interceptors, then pipes, and finally back through interceptors on the return path." [1] Exception filter berada di luar jalur normal: ia hanya bekerja kalau ada exception yang tidak ditangkap di salah satu langkah.

Request→ Middleware→ Guard→ Interceptor (sebelum)→ Pipe→ Handler→ Interceptor (sesudah)→ Response

Exception yang lolos dari langkah mana pun (termasuk handler dan service) diteruskan ke exception filter, yang membentuk response error.

Satu kalimat per komponen, dengan pertanyaan yang ia jawab:

KomponenPertanyaan yang dijawabKebutuhan khas
Middleware"Apa yang harus terjadi pada setiap request mentah?"Logging akses, correlation id, CORS, body parser
Guard"Boleh request ini masuk ke handler ini?"Autentikasi, otorisasi role
Interceptor"Apa yang dibungkus di sekitar handler?"Durasi request, bentuk response, timeout, cache
Pipe"Apakah argumen handler valid, dan dalam tipe yang benar?"Validasi DTO, ubah "42" menjadi 42
Exception filter"Bagaimana exception diubah menjadi response?"Format error yang konsisten

Urutan ini masuk akal kalau dibaca dari biaya: middleware murah dan tidak tahu handler mana yang akan jalan; guard menolak request yang tidak berhak sebelum ada kerja lain; pipe baru memvalidasi body setelah jelas request boleh masuk. Guard dijalankan "after all middleware, but before any interceptor or pipe." [2]

Latihan 1 — Susun urutan pipeline

Susun langkah berikut dari yang pertama sampai yang terakhir menyentuh satu request. Pakai tombol ↑/↓, lalu "Periksa".

  1. Middleware
  2. Guard
  3. Interceptor (sebelum handler)
  4. Pipe
  5. Route handler (method controller)
  6. Interceptor (sesudah handler)
  7. Exception filter (kalau ada exception yang tidak ditangkap)

Middleware → guard → interceptor → pipe → handler → interceptor → filter. Interceptor muncul dua kali karena ia membungkus handler: bagian sebelum next.handle() jalan sebelum pipe, bagian di dalam operator RxJS jalan setelah handler selesai. Filter hanya dipanggil kalau ada exception yang lolos.

2. Tiga level binding: global, controller, method

Guard, interceptor, pipe, dan filter bisa dipasang di tiga level dengan decorator @UseGuards(), @UseInterceptors(), @UsePipes(), @UseFilters() (di atas class controller atau di atas satu method), atau secara global. Pipe punya level keempat: per parameter, mis. @Param('id', ParseIntPipe). 

// main.ts: global, tanpa DI
app.useGlobalPipes(new ValidationPipe({ whitelist: true }));

// app.module.ts: global, dengan DI (guard boleh meng-inject Reflector, service, dll.)
@Module({ providers: [{ provide: APP_GUARD, useClass: AuthGuard }] })
export class AppModule {}

// orders.controller.ts
@Controller('orders')
@UseInterceptors(LoggingInterceptor)     // level controller: semua method
export class OrdersController {
  @Post()
  @UseGuards(RolesGuard)                 // level method: hanya route ini
  create(@Body() dto: CreateOrderDto) { /* ... */ }
}

Beda dua cara global sering ditanyakan. useGlobalGuards(), useGlobalPipes(), dan kawan-kawannya dipanggil di main.ts, di luar module mana pun, jadi komponen itu tidak bisa meng-inject dependency. Token APP_GUARD, APP_PIPE, APP_INTERCEPTOR, dan APP_FILTER mendaftarkan komponen sebagai provider di sebuah module, sehingga DI berjalan, dan komponen itu tetap berlaku global dari module mana pun ia didaftarkan. [2] [3]

Middleware tidak ikut pola ini. Ia tidak dipasang lewat decorator, melainkan di method configure(consumer) sebuah module (consumer.apply(...).forRoutes(...)) atau secara global dengan app.use(). [4] Detailnya di lesson 0023.

Urutan di dalam satu jenis komponen

  • Guard, interceptor (sebelum), pipe: global → controller → method. Pipe parameter jalan paling akhir. [1]
  • Interceptor (sesudah): terbalik, method → controller → global. Observable-nya diselesaikan "in a first-in, last-out manner." [1]
  • Exception filter: satu-satunya yang tidak mulai dari global. Filter "resolve from the lowest level possible": filter method dicoba dulu, lalu controller, lalu global. Exception yang Anda tangkap sendiri dengan try/catch tidak sampai ke filter. [1]
  • Middleware: global (app.use()) dulu, lalu middleware yang dipasang di module, masing-masing sesuai urutan dipasang.

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Jelaskan apa saja yang dilewati satu request di NestJS sebelum dan sesudah method controller. Kalau saya butuh otorisasi role, validasi body, dan format error yang seragam, saya pasang di mana?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Request masuk ke middleware dulu, lalu guard, lalu bagian 'sebelum' dari interceptor, lalu pipe, baru handler. Hasil handler kembali lewat interceptor dengan urutan terbalik. Kalau ada exception yang tidak ditangkap di mana pun, exception filter yang membentuk response error. Otorisasi role saya taruh di guard, karena guard tahu handler mana yang akan jalan dan jalan sebelum pipe, jadi request yang tidak berhak ditolak sebelum body divalidasi. Validasi body saya taruh di ValidationPipe global. Format error yang seragam saya taruh di exception filter global. Untuk global yang butuh DI, misalnya guard yang meng-inject Reflector, saya daftarkan lewat APP_GUARD di module, bukan useGlobalGuards di main.ts."

Checklist: apakah Anda menyebut…

  • Urutan: middleware → guard → interceptor → pipe → handler
  • Interceptor juga jalan setelah handler (membungkus handler)
  • Exception filter hanya untuk exception yang tidak ditangkap
  • Otorisasi di guard, validasi di pipe, format error di filter
  • Alasan urutan: request ditolak sebelum kerja yang lebih mahal
  • Beda global lewat useGlobal*() (tanpa DI) dan APP_* (dengan DI)

Lulus jika minimal 4 dari 6.
