Guard vs middleware; latihan tulis guard

CanActivate, ExecutionContext, Reflector dengan custom decorator, dan kenapa otorisasi ditaruh di guard

Di lesson 0021, middleware dan guard sama-sama jalan sebelum handler. Pertanyaan interview yang muncul hampir selalu: "Kalau keduanya bisa menolak request, kenapa otorisasi ditaruh di guard?" Lesson ini menjawabnya, lalu Anda menulis guard berbasis role di kertas.

Target lesson ini: Anda bisa menulis guard yang membaca metadata role dari custom decorator lewat Reflector tanpa melihat dokumentasi, menjelaskan apa yang terjadi saat canActivate mengembalikan false, dan menjelaskan dalam 30 detik kenapa otorisasi adalah tugas guard, bukan middleware.

1. Middleware: Express-style, tidak tahu handler

Middleware Nest sama dengan middleware Express: fungsi (req, res, next) yang bisa menjalankan kode apa pun, mengubah req/res, mengakhiri request, atau memanggil next(). [1] Versi class mengimplementasikan NestMiddleware dan boleh meng-inject dependency. 

@Injectable()
export class CorrelationIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    req.headers['x-correlation-id'] ??= randomUUID();
    next();
  }
}

@Module({ /* ... */ })
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(CorrelationIdMiddleware).forRoutes('*splat');
  }
}

Middleware tidak dipasang di @Module(), melainkan di method configure(); exclude() mengecualikan route tertentu. Kalau middleware tidak butuh dependency, cukup tulis fungsi biasa (functional middleware). Middleware global lewat app.use() "cannot access the DI container". [1] Pola wildcard *splat di atas adalah wildcard bernama yang cocok dengan path apa pun.

Batasnya: middleware "is context-blind by nature: it doesn't know which handler will be executed after it calls next()." [2] Middleware hanya melihat URL dan header, tidak melihat method controller atau decorator yang menempel padanya.

2. Guard: satu tugas, dan tahu konteksnya

"Guards have a single responsibility: they determine whether a given request will be handled by the route handler." Guard adalah class yang mengimplementasikan CanActivate; method canActivate mengembalikan boolean, Promise<boolean>, atau Observable<boolean>. [2]

Argumennya adalah ExecutionContext, turunan ArgumentsHost yang menambahkan detail eksekusi saat ini: context.switchToHttp().getRequest() untuk objek request, context.getHandler() untuk method yang akan dipanggil, dan context.getClass() untuk class controller-nya. [2] Karena tahu handler-nya, guard bisa membaca metadata yang ditempel decorator di method itu. Inilah alasan otorisasi ditaruh di guard.

Saat canActivate mengembalikan false, Nest melempar ForbiddenException, dan client menerima { "statusCode": 403, "message": "Forbidden resource", "error": "Forbidden" }. Untuk respons lain (mis. 401 saat token tidak ada), lempar exception sendiri, mis. UnauthorizedException. [2]

3. Reflector dan custom decorator

Metadata di sini berarti data tambahan yang ditempel decorator ke sebuah class atau method saat aplikasi dimuat, lalu dibaca lagi saat request berjalan. Reflector.createDecorator() membuat decorator bertipe sekaligus kunci untuk membacanya; alternatif lamanya adalah @SetMetadata(). [2] 

// roles.decorator.ts
export const Roles = Reflector.createDecorator<string[]>();

// roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const roles = this.reflector.get(Roles, context.getHandler());
    if (!roles) return true;                         // route tanpa @Roles: bebas
    const { user } = context.switchToHttp().getRequest();
    return roles.some(r => user?.roles?.includes(r));
  }
}

// cats.controller.ts
@Post() @Roles(['admin']) create(@Body() dto: CreateCatDto) { /* ... */ }

request.user biasanya diisi guard autentikasi yang jalan lebih dulu (mis. guard JWT, dibahas di modul Data & auth). Karena RolesGuard meng-inject Reflector, pasang ia secara global lewat provider APP_GUARD, bukan useGlobalGuards(). [2]

Latihan tulis kode — Guard di kertas

Tutup editor. Tulis di kertas, lalu bacakan alasannya dengan suara keras seolah sedang live coding. Batas waktu 5 menit.

"Tulis guard yang hanya mengizinkan request kalau header x-api-key sama dengan nilai dari ConfigService, kecuali route ditandai decorator @Public(). Tunjukkan decorator-nya dan cara memasang guard secara global."
Bandingkan dengan jawaban contoh dan checklist-nya 
export const Public = Reflector.createDecorator<boolean>();

@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(private reflector: Reflector, private config: ConfigService) {}

  canActivate(context: ExecutionContext): boolean {
    const isPublic = this.reflector.getAllAndOverride(Public, [context.getHandler(), context.getClass()]);
    if (isPublic) return true;
    const req = context.switchToHttp().getRequest();
    if (req.headers['x-api-key'] !== this.config.get('API_KEY')) {
      throw new UnauthorizedException('API key tidak valid');
    }
    return true;
  }
}

// app.module.ts
providers: [{ provide: APP_GUARD, useClass: ApiKeyGuard }]

// pemakaian
@Public() @Get('health') health() { return 'ok'; }

Checklist: apakah Anda…

  • Menulis class @Injectable() yang mengimplementasikan CanActivate
  • Mengambil request lewat context.switchToHttp().getRequest()
  • Membuat decorator dengan Reflector.createDecorator() (atau SetMetadata) dan membacanya dengan Reflector
  • Membaca metadata dari handler (dan idealnya class) lewat context.getHandler()/getClass()
  • Melempar UnauthorizedException (401) alih-alih mengembalikan false (403) untuk kredensial yang salah
  • Memasang guard global lewat APP_GUARD agar DI (Reflector, ConfigService) berjalan

Lulus jika minimal 4 dari 6.
