Transaksi, migrasi, dan perbandingan TypeORM

$transaction bentuk array vs interactive, prisma migrate dev vs prisma migrate deploy, dan cara membaca codebase yang memakai TypeORM

Di lesson 0025 setiap method service menjalankan satu query. Begitu satu aksi bisnis butuh beberapa write (kurangi saldo A, tambah saldo B), muncul pertanyaan interview klasik: "bagaimana kalau server mati di tengah?" Jawabannya transaksi: sekumpulan query yang berhasil semua atau dibatalkan semua (rollback). Lesson ini memakai Prisma ORM 7, sama seperti 0025.

Target lesson ini: Anda bisa menulis di kertas transfer saldo dengan interactive transaction Prisma, menjelaskan kapan memakai prisma migrate dev dan kapan prisma migrate deploy, dan mengenali @Entity, Repository, dan @InjectRepository kalau codebase memakai TypeORM.

1. $transaction: array vs interactive

Bentuk array (sequential operations): berikan array query; query dijalankan sesuai urutan di array, dan kalau satu gagal, seluruh transaksi di-rollback. Keterbatasannya: hasil satu query tidak bisa dipakai sebagai input query berikutnya. [1] 

const [post, count] = await this.prisma.$transaction([
  this.prisma.post.create({ data: { title: 'Halo', authorId: 1 } }),
  this.prisma.post.count(),
]);

Interactive transaction: berikan fungsi async yang menerima tx (client yang terikat ke transaksi). Di dalamnya Anda boleh membaca, mengecek kondisi, lalu menulis. Kalau fungsi melempar error, transaksi otomatis di-rollback. [1] 

async transfer(from: number, to: number, amount: number) {
  return this.prisma.$transaction(async (tx) => {
    const sender = await tx.account.update({
      where: { id: from }, data: { balance: { decrement: amount } },
    });
    if (sender.balance < 0) throw new BadRequestException('Saldo tidak cukup');
    return tx.account.update({ where: { id: to }, data: { balance: { increment: amount } } });
  });
}

Aturan pakainya: semua query di dalam fungsi harus lewat tx, bukan this.prisma (yang di luar transaksi). Default-nya maxWait 2000 ms (menunggu mendapat transaksi) dan timeout 5000 ms (lama maksimal transaksi berjalan). Dokumentasi Prisma meminta transaksi dijaga singkat dan menghindari request jaringan atau query lambat di dalamnya, karena transaksi panjang menurunkan performa dan bisa memicu deadlock. [1] Isolation level (seberapa ketat transaksi terlindung dari transaksi lain yang berjalan bersamaan) bisa diatur lewat opsi isolationLevel di argumen kedua; tanpa itu dipakai default database.

Versi. Di Prisma ORM 8 tidak ada $transaction: kedua bentuk menjadi db.transaction(async (tx) => ...), dan bentuk array ditulis ulang sebagai query berurutan di dalam callback. [2]

2. Migrasi: migrate dev vs migrate deploy

Migrasi adalah file SQL berurutan yang mengubah schema database dari satu versi ke versi berikutnya, disimpan di git bersama kode. Prisma punya dua perintah untuk dua lingkungan berbeda. [3]

prisma migrate devprisma migrate deploy
Dipakai dilaptop developerCI/CD, staging, produksi, database test
Membuat file migrasi baruya, dari perubahan schema.prismatidak, hanya menerapkan yang pending
Shadow databaseya, untuk mendeteksi schema drifttidak
Bisa menawarkan reset databaseya (drift atau konflik history)tidak pernah
Generate Prisma Clientyatidak

Shadow database adalah database sementara tempat migrate dev memutar ulang seluruh history migrasi untuk mendeteksi drift (schema database yang berbeda dari yang dijelaskan history). Karena migrate dev bisa meminta reset, perintah itu hanya untuk development. migrate deploy dijalankan di pipeline CI/CD, dan dokumentasi Prisma tidak menyarankan menjalankannya dari laptop ke database produksi. [3]

ubah schema.prisma→ prisma migrate dev (lokal)→ commit folder migrations→ prisma migrate deploy (CI/CD)

3. Perbandingan singkat: TypeORM

TypeORM adalah ORM dengan entity berbasis decorator dan pola repository; tim Nest memelihara paket @nestjs/typeorm untuknya. [4] Bagian ini cukup supaya Anda tidak blank kalau codebase atau interviewer memakainya. 

@Entity()
export class User {
  @PrimaryGeneratedColumn() id: number;
  @Column() email: string;
}

@Module({ imports: [TypeOrmModule.forFeature([User])], providers: [UsersService] })
export class UsersModule {}

@Injectable()
export class UsersService {
  constructor(@InjectRepository(User) private usersRepository: Repository<User>) {}
  findAll() { return this.usersRepository.find(); }
}
PrismaTypeORM
Sumber kebenaran schemafile schema.prisma, client di-generateclass @Entity dengan decorator @Column
Akses data di serviceinject PrismaService, prisma.user.findMany()@InjectRepository(User) → Repository<User>
Registrasi di modulePrismaModule buatan sendiriTypeOrmModule.forRoot() + forFeature([User])
Transaksi$transactiondataSource.transaction() atau QueryRunner

Satu jebakan yang sering ditanyakan: opsi synchronize: true membuat TypeORM menyamakan schema database dengan entity setiap aplikasi start. Dokumentasi Nest: jangan pakai di produksi, karena data produksi bisa hilang. [4] Di produksi, pakai migrasi.

"Tulis OrdersService.checkout(userId, productId) dengan Prisma: kurangi stok produk satu, tolak kalau stok habis, lalu buat order. Keduanya harus berhasil bersama atau batal bersama."
Bandingkan dengan jawaban contoh dan checklist-nya 
checkout(userId: number, productId: number) {
  return this.prisma.$transaction(async (tx) => {
    const product = await tx.product.update({
      where: { id: productId }, data: { stock: { decrement: 1 } },
    });
    if (product.stock < 0) throw new ConflictException('Stok habis');
    return tx.order.create({ data: { userId, productId } });
  });
}

"Saya pakai interactive transaction karena query kedua bergantung pada hasil cek stok. Semua query lewat tx. Kalau stok negatif, saya lempar error dan Prisma me-rollback decrement-nya. Di dalam transaksi tidak ada panggilan jaringan supaya transaksinya singkat."

Checklist: apakah Anda…

  • memakai $transaction(async (tx) => ...) (interactive), bukan dua query terpisah?
  • menjalankan semua query lewat tx, bukan this.prisma?
  • mengecek stok dan melempar error kalau habis?
  • menyebut bahwa error di dalam fungsi membuat transaksi di-rollback?
  • menjelaskan kenapa bukan bentuk array (hasil cek dipakai untuk memutuskan langkah berikutnya)?
  • menjaga transaksi singkat (tanpa panggilan jaringan, mis. ke payment gateway, di dalamnya)?
