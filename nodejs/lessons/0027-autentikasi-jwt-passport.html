Autentikasi: hashing password, JWT, dan Passport

Menyimpan password dengan argon2/bcrypt, JWT access vs refresh token, @nestjs/jwt, strategi Passport (local, jwt), dan AuthGuard

Data user sudah tersimpan lewat PrismaService (0025). Sekarang dua pertanyaan interview yang hampir pasti muncul: "bagaimana Anda menyimpan password?" dan "bagaimana request berikutnya tahu siapa user-nya?". Autentikasi menjawab siapa Anda; otorisasi (lesson 0028) menjawab Anda boleh apa.

Target lesson ini: Anda bisa menjelaskan dalam 60 detik kenapa password di-hash dengan argon2id atau bcrypt (bukan SHA-256), apa isi JWT dan beda access token dengan refresh token, lalu menulis di kertas AuthService.signIn yang memverifikasi hash dan menerbitkan JWT.

1. Hashing password

Password disimpan sebagai hash, bukan dienkripsi: hashing adalah fungsi satu arah, jadi server tidak pernah bisa (dan tidak perlu) mengembalikan password asli. Saat login, password yang dikirim di-hash ulang lalu dibandingkan. Hash cepat seperti SHA-256 tidak cocok, karena penyerang yang mencuri database bisa mencoba miliaran tebakan per detik. [1]

AlgoritmaRekomendasi OWASP (minimum)Catatan
Argon2idmemori 19 MiB, iterasi 2, paralelisme 1pilihan pertama, memory-hard
scryptcost 217, block size 8kalau Argon2id tidak tersedia
bcryptwork factor 10 atau lebihsistem lama; input maksimal 72 byte

Angka di tabel dari OWASP Password Storage Cheat Sheet. [1] Salt (nilai acak unik per password, supaya dua password sama menghasilkan hash berbeda) wajib, tetapi library populer membuat dan menyimpannya otomatis di dalam string hash. Memory-hard artinya setiap tebakan butuh banyak memori, sehingga GPU tidak bisa menebak secara massal dengan murah. 

import * as argon2 from 'argon2';

const hash = await argon2.hash(dto.password);        // saat register
const ok = await argon2.verify(user.passwordHash, dto.password); // saat login

// bcrypt (codebase lama): await bcrypt.hash(pw, 10) dan await bcrypt.compare(pw, hash)

Hashing password sengaja lambat, jadi selalu pakai API async (await), bukan varian sync seperti bcrypt.hashSync yang memblokir event loop selama hashing berjalan.

2. JWT: access token dan refresh token

JWT (JSON Web Token) adalah "a compact, URL-safe means of representing claims to be transferred between two parties". Claim-nya berupa objek JSON yang menjadi payload JWS (ditandatangani) atau JWE (dienkripsi). [2] Hampir semua API memakai JWS: isi token bisa dibaca siapa pun (hanya base64url), tetapi tidak bisa diubah tanpa merusak tanda tangan. Jadi jangan menaruh data rahasia di payload. 

header.payload.signature
payload: { "sub": "42", "username": "ani", "iat": 1763100000, "exp": 1763100900 }
  • sub (subject): siapa principal token ini, biasanya ID user. [2]
  • iat (issued at): kapan token diterbitkan. exp (expiration time): pada atau setelah waktu ini token "MUST NOT be accepted for processing". [2]

Access token dikirim di setiap request (Authorization: Bearer <token>) dan dibuat berumur pendek (menit), karena JWT tidak bisa ditarik kembali sebelum exp. Refresh token adalah kredensial yang dipakai untuk mendapatkan access token baru saat access token kedaluwarsa. [3] Istilah ini berasal dari OAuth 2.0 (standar delegasi akses), tetapi polanya dipakai juga di login biasa: refresh token berumur panjang, disimpan di server (atau hash-nya) supaya bisa dicabut saat logout, dan diganti baru setiap kali dipakai (rotasi).

Di Nest, token diterbitkan dengan @nestjs/jwt. Dokumentasi Nest memakai claim sub untuk ID user "to be consistent with JWT standards", dan meminta secret tidak pernah dibocorkan (simpan di env var atau secret vault). [4] 

JwtModule.register({ secret: process.env.JWT_SECRET, signOptions: { expiresIn: '15m' } })

const payload = { sub: user.id, username: user.username };
return { access_token: this.jwtService.sign(payload) };

3. Passport: strategi local dan jwt, AuthGuard

Passport adalah library autentikasi Node.js yang paling populer, dan @nestjs/passport membungkusnya. [4] Setiap cara login adalah satu strategy. Anda menulis validate(); nilai yang dikembalikan dipasang Passport ke req.user.

  • Strategy local (paket passport-local): membaca username dan password dari body (bisa diganti, mis. usernameField: 'email'), dipakai di endpoint login.
  • Strategy jwt (paket passport-jwt): membaca token dari header Bearer, memverifikasi tanda tangan dan exp. Token kedaluwarsa ditolak dengan 401 Unauthorized. [4]
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: process.env.JWT_SECRET,
    });
  }
  validate(payload: { sub: number; username: string }) {
    return { userId: payload.sub, username: payload.username }; // → req.user
  }
}

@UseGuards(AuthGuard('local')) @Post('auth/login') login(@Req() req) { return this.auth.login(req.user); }
@UseGuards(AuthGuard('jwt'))   @Get('profile')     profile(@Req() req) { return req.user; }
POST /auth/login→ AuthGuard('local'): verifikasi hash→ terbitkan JWT→ GET /profile + Bearer→ AuthGuard('jwt'): req.user

Versi (NestJS 12). Bab Authentication di dokumentasi Nest kini memakai paket resmi baru @nestjs/authentication (guard global, @Public(), hashing scrypt bawaan dengan parameter OWASP), sementara Passport tetap ada sebagai recipe. [5] Banyak codebase dan soal interview masih memakai pola Passport + @nestjs/jwt di atas, dan konsepnya (hash, token, guard) sama.

"Tulis AuthService.signIn(email, password): cari user lewat Prisma, verifikasi password dengan argon2, lalu kembalikan access token JWT. Kalau gagal, respons harus sama untuk email salah maupun password salah."
Bandingkan dengan jawaban contoh dan checklist-nya 
@Injectable()
export class AuthService {
  constructor(private prisma: PrismaService, private jwt: JwtService) {}

  async signIn(email: string, password: string) {
    const user = await this.prisma.user.findUnique({ where: { email } });
    if (!user || !(await argon2.verify(user.passwordHash, password))) {
      throw new UnauthorizedException('Email atau password salah');
    }
    return { access_token: await this.jwt.signAsync({ sub: user.id }) };
  }
}

"Password dibandingkan lewat argon2.verify, bukan string compare. Email salah dan password salah memberi 401 dengan pesan yang sama supaya penyerang tidak bisa menebak email mana yang terdaftar. Payload hanya berisi sub, karena JWT bisa dibaca siapa pun; masa berlakunya pendek lewat expiresIn di JwtModule."

Checklist: apakah Anda…

  • meng-inject PrismaService dan JwtService lewat constructor?
  • memverifikasi dengan argon2.verify (atau bcrypt.compare), bukan membandingkan string atau hash cepat?
  • melempar UnauthorizedException (401) dengan pesan yang sama untuk email dan password salah?
  • memakai claim sub untuk ID user di payload?
  • tidak menaruh data rahasia (password, hash) di payload JWT?
  • menyebut access token berumur pendek (expiresIn) dan secret dari env var?

Lulus jika minimal 4 dari 6.
