Otorisasi role: @Roles, RolesGuard, dan 401 vs 403

RBAC dengan decorator + Reflector, guard global + @Public, cek kepemilikan resource, dan status code yang tepat

Di lesson 0027 guard autentikasi mengisi req.user. Lesson ini memakai informasi itu untuk memutuskan boleh atau tidak. Ini salah satu soal live coding NestJS yang paling sering diminta: "tulis guard yang mengecek role".

Target lesson ini: Anda bisa menulis di kertas decorator @Roles dan RolesGuard dalam 5 menit, menjelaskan kenapa cek kepemilikan resource tidak bisa diselesaikan oleh role saja, dan menjawab "kapan 401, kapan 403?" dengan merujuk RFC 9110.

1. RBAC dengan @Roles + RolesGuard

RBAC (role-based access control): izin ditempel ke role (admin, staff), dan user mendapat izin lewat role yang dimilikinya. Di Nest, polanya tiga bagian: decorator menempelkan metadata "role yang dibutuhkan" ke handler, guard membaca metadata itu lewat Reflector, lalu membandingkannya dengan req.user.roles. 

export enum Role { User = 'user', Admin = 'admin' }

export const Roles = Reflector.createDecorator<Role[]>();
// cara lama yang setara: export const Roles = (...roles: Role[]) => SetMetadata('roles', roles);

@Roles([Role.Admin])
@Delete(':id')
remove(@Param('id', ParseIntPipe) id: number) { return this.posts.remove(id); }

Reflector.createDecorator membuat decorator ber-type sekaligus kunci metadatanya; SetMetadata adalah cara tingkat rendah yang setara. [1] 

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride(Roles, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!required) return true;                 // route tanpa @Roles
    const { user } = context.switchToHttp().getRequest();
    return required.some((role) => user?.roles?.includes(role));
  }
}
  • getAllAndOverride mengembalikan nilai pertama yang terdefinisi sesuai urutan target, jadi @Roles di method mengalahkan @Roles di controller. getAllAndMerge menggabungkan keduanya. [1]
  • Saat guard mengembalikan false, Nest melempar ForbiddenException: {"statusCode": 403, "message": "Forbidden resource", "error": "Forbidden"}. Butuh status lain? Lempar exception sendiri dari guard. [2]
  • Guard berjalan setelah semua middleware dan sebelum interceptor atau pipe, sehingga request yang ditolak tidak pernah sampai ke validasi body. [2]

2. Guard global + @Public

Memasang @UseGuards(JwtAuthGuard) di setiap controller mudah terlupa. Pola yang lebih aman: daftarkan guard autentikasi secara global lewat token APP_GUARD (default tertutup), lalu buka route tertentu dengan decorator @Public(). Guard global membaca metadata itu dan langsung mengizinkan. [3] 

export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }
  canActivate(context: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(), context.getClass(),
    ]);
    return isPublic ? true : super.canActivate(context);
  }
}

// AppModule: providers: [{ provide: APP_GUARD, useClass: JwtAuthGuard },
//                        { provide: APP_GUARD, useClass: RolesGuard }]

APP_GUARD (bukan app.useGlobalGuards()) membuat guard global tetap bisa meng-inject dependency seperti Reflector; guard yang didaftarkan dengan useGlobalGuards() di luar module tidak bisa. [2] RolesGuard membutuhkan req.user, jadi guard autentikasi harus berjalan lebih dulu.

3. Cek kepemilikan resource

Role menjawab "user jenis apa", bukan "milik siapa data ini". Role user boleh mengedit post, tapi hanya post miliknya. Informasi kepemilikan ada di database, jadi ceknya dilakukan di service setelah data dibaca, bukan di guard yang hanya melihat metadata route. 

async update(id: number, dto: UpdatePostDto, user: { userId: number; roles: Role[] }) {
  const post = await this.prisma.post.findUnique({ where: { id } });
  if (!post) throw new NotFoundException();
  const isOwner = post.authorId === user.userId;
  if (!isOwner && !user.roles.includes(Role.Admin)) throw new ForbiddenException();
  return this.prisma.post.update({ where: { id }, data: dto });
}

Lupa cek ini adalah bug klasik IDOR (insecure direct object reference): user A cukup mengganti ID di URL untuk mengubah data user B.

4. 401 vs 403

RFC 9110 membedakan keduanya dengan jelas: [4]

  • 401 Unauthorized: request "lacks valid authentication credentials". Server yang mengirim 401 wajib menyertakan header WWW-Authenticate. Artinya: saya belum tahu Anda siapa (token tidak ada, kedaluwarsa, tanda tangan salah).
  • 403 Forbidden: server "understood the request but refuses to fulfill it"; kalau kredensial dikirim, server "considers them insufficient to grant access". Artinya: saya tahu Anda siapa, tapi Anda tidak boleh (role kurang, bukan pemilik).
  • Server yang ingin menyembunyikan keberadaan resource terlarang boleh menjawab 404 sebagai gantinya. [5]
token valid?→ tidak → 401 · ya → role/kepemilikan cukup?→ tidak → 403 (atau 404)

Bandingkan dengan jawaban contoh dan checklist-nya 
export const Roles = Reflector.createDecorator<string[]>();

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride(Roles, [
      context.getHandler(), context.getClass(),
    ]);
    if (!required) return true;
    const { user } = context.switchToHttp().getRequest();
    return required.some((r) => user?.roles?.includes(r));
  }
}

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(['admin'])
@Delete(':id')
remove(@Param('id', ParseIntPipe) id: number) { return this.posts.remove(id); }

"Decorator menempel metadata role; guard membacanya dengan Reflector, method dulu lalu class, jadi method menang. Tanpa metadata, guard mengizinkan. JwtAuthGuard jalan dulu supaya req.user terisi; kalau role tidak cocok, guard mengembalikan false dan Nest menjawab 403."

Checklist: apakah Anda…

  • membuat decorator @Roles (Reflector.createDecorator atau SetMetadata)?
  • menulis RolesGuard implements CanActivate yang meng-inject Reflector?
  • membaca metadata dari handler dan class dengan getAllAndOverride (method menang)?
  • mengizinkan (return true) route tanpa @Roles?
  • membandingkan dengan request.user.roles dan menyebut bahwa guard autentikasi harus jalan lebih dulu?
  • menyebut bahwa false menghasilkan 403, bukan 401?
