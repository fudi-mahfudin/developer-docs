Config dan logging

@nestjs/config dengan validasi env, Logger bawaan, structured logging, dan correlation id per request

Aplikasi yang sama berjalan di laptop, CI (lesson 0031), staging, dan production. Yang berbeda hanya konfigurasinya. Saat ada masalah di production, satu-satunya jendela ke dalam aplikasi adalah log-nya. Lesson ini membahas keduanya dari sisi NestJS.

Target lesson ini: Anda bisa menjelaskan dalam 60 detik cara aplikasi NestJS membaca dan memvalidasi konfigurasi per environment, dan cara membuat log-nya terstruktur serta bisa ditelusuri per request dengan correlation id.

1. @nestjs/config: env dibaca sekali, divalidasi saat start

ConfigModule.forRoot() memuat file .env (lokasinya bisa diganti dengan envFilePath) dan variabel environment proses, lalu menyediakannya lewat ConfigService. isGlobal: true membuat module lain tidak perlu meng-import ConfigModule lagi. Secara default variabel environment runtime menang atas isi .env; override: true membalik urutan itu. [1]

Dengan validationSchema, variabel yang wajib tapi hilang membuat aplikasi gagal bootstrap. Itu disengaja: lebih baik deploy gagal di detik pertama daripada request pertama gagal karena DATABASE_URL kosong. ConfigService menyajikan nilai hasil skema, jadi z.coerce.number() mengubah string "3000" menjadi angka. [1]

Label versi NestJS 12: @nestjs/config pindah dari validasi khusus Joi ke Standard Schema (antarmuka bersama yang diimplementasikan Zod, Valibot, ArkType). Joi tetap jalan asalkan v18 ke atas. [2] 

// app.module.ts
const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string(),            // tanpa default = wajib
});

@Module({
  imports: [ConfigModule.forRoot({ isGlobal: true, validationSchema: envSchema })],
})
export class AppModule {}

// di service
const url = this.config.getOrThrow<string>('DATABASE_URL');

get(key, default) mengembalikan nilai atau default; getOrThrow(key) melempar error kalau nilainya undefined. [1] Aturan praktis: baca konfigurasi lewat ConfigService, jangan process.env.X yang tersebar di seluruh kode, dan jangan commit .env berisi secret.

2. Logger bawaan dan structured logging

Praktik yang dianjurkan dokumentasi NestJS: buat Logger dari @nestjs/common di setiap class dengan nama class sebagai context: private readonly logger = new Logger(OrdersService.name). Level yang tersedia: fatal, error, warn, log, debug, verbose. [3]

Structured logging berarti setiap entri log adalah objek dengan field tetap (level, waktu, context, pesan, data), biasanya JSON satu baris. Sistem log bisa memfilter level=error AND requestId=abc tanpa regex. ConsoleLogger bawaan punya mode JSON (json: true). Label versi NestJS 12: objek biasa yang dikirim setelah pesan dilampirkan ke entri yang sama sebagai structured params. [3] 

// main.ts
const app = await NestFactory.create(AppModule, {
  logger: new ConsoleLogger({ json: true }),
});

// orders.service.ts
this.logger.log('Order dibuat', { orderId: order.id, total: order.total });
// satu baris JSON: level, context, pesan, dan objek di bawah key "params"

Untuk kebutuhan lebih (kirim ke file atau HTTP, redaksi field sensitif, performa tinggi), dokumentasi NestJS menyarankan library khusus seperti pino atau Winston dan memasangnya lewat app.useLogger(); panggilan Logger di seluruh aplikasi otomatis diteruskan ke sana. bufferLogs: true menahan log awal sampai logger itu terpasang. [3] Pino menulis JSON per baris secara default.

3. Correlation id dengan AsyncLocalStorage

Correlation id adalah satu id unik per request (biasanya dari header X-Request-Id yang dikirim gateway, atau UUID baru) yang ditempel di setiap baris log selama request itu diproses. Saat 500 request berjalan bersamaan, log mereka bercampur; id inilah yang memisahkannya.

Masalahnya: bagaimana logger di kedalaman service tahu id request yang sedang berjalan, tanpa meneruskan parameter ke setiap fungsi? Variabel global salah, karena satu proses Node melayani banyak request bersamaan. AsyncLocalStorage dari node:async_hooks menyimpan sebuah store yang ikut sepanjang rantai operasi async yang dimulai di dalam als.run(store, fn). [4]

Request masuk→ Middleware: ambil X-Request-Id atau buat UUID→ als.run({ requestId }, next)→ Controller → service → logger.log()→ Logger membaca als.getStore().requestId 
export const als = new AsyncLocalStorage<{ requestId: string }>();

@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: () => void) {
    const requestId = req.header('x-request-id') ?? randomUUID();
    res.setHeader('x-request-id', requestId);
    als.run({ requestId }, next);
  }
}

Alternatif membuat logger REQUEST-scoped memang bisa, tapi scope itu merambat ke setiap provider yang bergantung padanya dan membuat instance baru per request. AsyncLocalStorage tidak punya biaya itu.

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai. Soal ini juga ada di bank soal dan bisa ditarik review 0035.

"Aplikasi NestJS Anda akan jalan di staging dan production. Bagaimana Anda mengelola konfigurasinya, dan bagaimana log-nya supaya satu request bisa ditelusuri?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Konfigurasi dari environment variable, dibaca lewat @nestjs/config: ConfigModule.forRoot dengan isGlobal dan validationSchema, misalnya skema Zod. Kalau variabel wajib seperti DATABASE_URL tidak ada atau salah format, aplikasi gagal saat bootstrap, bukan saat request pertama. Env runtime menang atas .env, jadi .env hanya untuk lokal, dan secret tidak di-commit. Di kode saya pakai ConfigService.getOrThrow, bukan process.env tersebar. Untuk log, setiap class punya new Logger(NamaClass.name), di production keluarannya JSON, lewat ConsoleLogger json: true atau Pino. Setiap request diberi correlation id: middleware mengambil header X-Request-Id atau membuat UUID, menyimpannya di AsyncLocalStorage, dan logger menambahkannya ke setiap entri, lalu id itu juga dikirim balik di response header. Dengan begitu satu request bisa difilter dari ribuan baris log."

Checklist: apakah Anda menyebut…

  • ConfigModule.forRoot dengan validationSchema (mis. Zod), isGlobal?
  • gagal cepat saat bootstrap kalau env wajib hilang atau salah?
  • env runtime menang atas .env; secret tidak di-commit; ConfigService bukan process.env tersebar?
  • Logger per class dengan context (new Logger(X.name))?
  • structured logging JSON di production (ConsoleLogger json atau Pino)?
  • correlation id dari header/UUID, disimpan di AsyncLocalStorage, ikut di setiap log?

Lulus jika minimal 4 dari 6.
