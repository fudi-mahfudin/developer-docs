Graceful shutdown, health check, throttle, cache

SIGTERM dan enableShutdownHooks, @nestjs/terminus, @nestjs/throttler, dan CacheModule secara singkat

Empat fitur kecil yang membedakan aplikasi "jalan di laptop" dari aplikasi yang aman di-deploy berkali-kali sehari. Fokusnya pada API Node dan NestJS; konsep di baliknya cukup satu-dua kalimat.

Target lesson ini: Anda bisa menjelaskan dalam 60 detik apa yang terjadi saat container NestJS menerima SIGTERM dan bagaimana orchestrator tahu aplikasi sehat, lalu menyebut cara memasang rate limit dan cache di NestJS beserta jebakannya.

1. Graceful shutdown: SIGTERM dan enableShutdownHooks

Saat deploy atau scale down, orchestrator (Docker, Kubernetes) mengirim SIGTERM ke proses, menunggu masa tenggang (grace period), lalu mengirim SIGKILL. Di Node, SIGTERM dan SIGINT punya handler default yang langsung keluar dengan kode 128 + nomor sinyal; memasang listener menghapus perilaku default itu. SIGKILL tidak bisa ditangkap sama sekali. [1]

Di NestJS, listener sinyal mati secara default karena memakan resource. Panggil app.enableShutdownHooks(); tanpa itu, hook shutdown hanya jalan kalau Anda memanggil app.close() sendiri. Urutannya: onModuleDestroy → beforeApplicationShutdown → koneksi ditutup → onApplicationShutdown(signal), dan Nest menunggu Promise dari setiap hook. Di Windows, SIGTERM tidak pernah bekerja. [2]

SIGTERM→ onModuleDestroy→ beforeApplicationShutdown→ server HTTP ditutup→ onApplicationShutdown(signal)→ proses keluar (atau SIGKILL setelah grace period) 
// main.ts
const app = await NestFactory.create(AppModule);
app.enableShutdownHooks();
await app.listen(3000);

// prisma.service.ts
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() { await this.$connect(); }
  async onModuleDestroy() { await this.$disconnect(); }
}

Label versi NestJS 12: adapter Express kini menguras (drain) request yang sedang berjalan saat shutdown, dan lifecycle hook dipanggil per level hierarki komponen, sehingga urutan antar provider yang saling bergantung bisa berbeda dari v11. [3]

2. Health check dengan @nestjs/terminus

Health check adalah endpoint yang dipanggil orchestrator atau load balancer secara berkala untuk memutuskan apakah instance boleh menerima traffic. @nestjs/terminus menyediakan HealthCheckService, decorator @HealthCheck(), dan indicator siap pakai (HTTP, memori, disk, Prisma, TypeORM). Respons berisi status (ok, error, degraded, shutting_down) serta info, error, dan details per indicator; instance yang tidak sehat dijawab 503. [4] 

@Controller('health')
export class HealthController {
  constructor(private health: HealthCheckService, private memory: MemoryHealthIndicator) {}

  @Get()
  @HealthCheck()
  check() {
    return this.health.check([
      () => this.memory.checkHeap('memory_heap', 150 * 1024 * 1024),
    ]);
  }
}

TerminusModule.forRoot({ gracefulShutdownTimeoutMs: 1000 }) memberi jeda sebelum shutdown setelah SIGTERM (default 0), sehingga load balancer sempat melihat instance ini sedang berhenti. Shutdown hooks harus aktif. [4] Label versi NestJS 12: API indicator lama (extend HealthIndicator, lempar error) dihapus; custom indicator memakai HealthIndicatorService dengan check(key) lalu up()/down() atau attempt(). [3]

3. Rate limiting dengan @nestjs/throttler

Rate limiting membatasi jumlah request satu client dalam rentang waktu, supaya satu client (bug, scraper, brute force login) tidak menghabiskan kapasitas yang dibagi. Status HTTP untuk itu adalah 429 Too Many Requests. [5]

ThrottlerModule.forRoot menerima satu atau beberapa set { ttl, limit }; sejak v5, ttl dalam milidetik. Pasang ThrottlerGuard sebagai guard global lewat APP_GUARD, lalu atur per route dengan @SkipThrottle() dan @Throttle({ default: { limit, ttl } }). [6] Saat limit terlewati, guard melempar ThrottlerException berstatus 429. [7] 

@Module({
  imports: [ThrottlerModule.forRoot({ throttlers: [{ ttl: 60_000, limit: 10 }] })],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
export class AppModule {}

@Throttle({ default: { limit: 3, ttl: 60_000 } })   // login lebih ketat
@Post('login')
login(@Body() dto: LoginDto) { /* ... */ }

Dua jebakan yang sering ditanyakan: [6]

  • Banyak instance: storage default ada di memori proses. Empat instance dengan limit 10/menit berarti client bisa lolos sampai 40/menit. Pakai storage bersama (Redis).
  • Di belakang proxy: tanpa app.set('trust proxy', ...), semua request terlihat datang dari IP proxy, sehingga semua user berbagi satu limit.

4. CacheModule secara singkat

Cache menyimpan hasil yang mahal dihitung (query berat, panggilan API luar) untuk sementara, supaya request berikutnya dijawab dari memori; harganya, data bisa basi sampai entri kedaluwarsa. Di NestJS: npm install @nestjs/cache-manager cache-manager, CacheModule.register(), lalu inject CACHE_MANAGER untuk get/set/del. ttl dalam milidetik, dan tanpa ttl entri tidak kedaluwarsa. CacheInterceptor meng-cache response otomatis, tapi secara default hanya endpoint GET. Store bisa dipindah ke Redis lewat Keyv. [8] 

constructor(@Inject(CACHE_MANAGER) private cache: Cache, private prisma: PrismaService) {}

async getProduct(id: number) {
  const key = `product:${id}`;
  const hit = await this.cache.get<Product>(key);
  if (hit) return hit;
  const product = await this.prisma.product.findUniqueOrThrow({ where: { id } });
  await this.cache.set(key, product, 30_000);           // 30 detik
  return product;
}

Saat produk di-update, panggil this.cache.del(key) supaya pembaca berikutnya tidak menerima data lama.

"Saat deploy, orchestrator mengirim SIGTERM ke container NestJS Anda. Apa yang harus terjadi supaya tidak ada request atau koneksi yang terputus kasar, dan bagaimana orchestrator tahu aplikasi sehat?" (60 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Di main.ts saya panggil app.enableShutdownHooks(), karena secara default Nest tidak mendengarkan sinyal. Saat SIGTERM datang, Nest menjalankan onModuleDestroy, lalu beforeApplicationShutdown, menutup server HTTP, lalu onApplicationShutdown dengan nama sinyalnya. Di hook itu saya menutup koneksi: PrismaService memanggil $disconnect, worker queue berhenti mengambil job baru. Di NestJS 12 adapter Express juga menunggu request yang sedang jalan selesai. Kalau proses tidak berhenti dalam grace period, orchestrator mengirim SIGKILL yang tidak bisa ditangkap, jadi hook harus cepat. Untuk kesehatan, saya pasang endpoint /health dengan @nestjs/terminus: HealthCheckService.check berisi indicator database dan memori. Kalau ada yang down, responsnya 503 dan orchestrator berhenti mengirim traffic. Terminus juga punya gracefulShutdownTimeoutMs untuk memberi jeda sebelum shutdown."

Checklist: apakah Anda menyebut…

  • app.enableShutdownHooks() karena listener sinyal mati secara default?
  • urutan onModuleDestroy → beforeApplicationShutdown → onApplicationShutdown(signal)?
  • menutup koneksi di hook (Prisma $disconnect, worker berhenti ambil job)?
  • SIGKILL setelah grace period tidak bisa ditangkap, jadi shutdown harus cepat?
  • endpoint /health dengan @nestjs/terminus: HealthCheckService + indicator?
  • unhealthy → 503 sehingga orchestrator berhenti mengirim traffic?

Lulus jika minimal 4 dari 6.
