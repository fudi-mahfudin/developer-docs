Babak 1 · Konsep Node (±15 menit)

"Jelaskan event loop Node. Di mana process.nextTick dan Promise dijalankan relatif terhadap setTimeout dan setImmediate? Lalu jelaskan backpressure pada stream: apa yang terjadi kalau Anda mengabaikannya?"

Lalu interviewer menunjukkan kode berikut (CommonJS, Node 24): "Tulis urutan outputnya dan jelaskan setiap baris."

console.log('1');
setImmediate(() => console.log('2'));
Promise.resolve().then(() => {
  console.log('3');
  process.nextTick(() => console.log('4'));
});
process.nextTick(() => console.log('5'));
(async () => {
  console.log('6');
  await null;
  console.log('7');
})();
console.log('8');
Lihat urutan output
  1. 1
  2. 6
  3. 8
  4. 5
  5. 3
  6. 7
  7. 4
  8. 2

Kode sinkron jalan sampai habis: 1, badan async function sampai await (6), lalu 8. Next tick queue dikosongkan (5), baru microtask queue: 3 lalu lanjutan setelah await (7), sesuai urutan masuk antrean. nextTick yang dijadwalkan dari dalam microtask (4) jalan setelah microtask queue habis. [1] setImmediate (2) menunggu fase check. Kunci ini diverifikasi dengan menjalankan kodenya di Node v24.

Lihat jawaban contoh babak 1

"Node menjalankan JavaScript di satu thread; I/O diserahkan ke libuv, dan callback-nya dijalankan event loop. Satu putaran punya fase timers untuk setTimeout/setInterval, pending callbacks, poll untuk callback I/O, check untuk setImmediate, dan close callbacks. [2] Di luar fase itu ada dua antrean yang dikosongkan setiap kali satu callback selesai: next tick queue dulu, lalu microtask queue untuk Promise. Jadi nextTick dan then selalu mendahului timer dan immediate berikutnya. setTimeout 0 vs setImmediate di main module tidak deterministik, tetapi di dalam callback I/O setImmediate selalu duluan. Backpressure: write() mengembalikan false kalau buffer Writable melewati highWaterMark; produsen harus berhenti dan menunggu event 'drain'. [3] Kalau diabaikan, data menumpuk di memori sampai proses membengkak. Paling aman memakai stream.pipeline, yang menangani backpressure dan error sekaligus."

Checklist: apakah Anda menyebut…

  • satu thread JavaScript, I/O diserahkan ke libuv?
  • fase utama berurutan: timers → poll → check (setImmediate) → close?
  • next tick queue dikosongkan sebelum microtask queue, keduanya setelah setiap callback?
  • setTimeout 0 vs setImmediate: tidak deterministik di main module, immediate duluan di callback I/O?
  • write() mengembalikan false di atas highWaterMark, lalu tunggu event 'drain'?
  • mengabaikan backpressure membuat memori membengkak; solusinya stream.pipeline()?

Lulus jika minimal 4 dari 6. Soal urutan output dinilai terpisah: benar semua atau tidak.

Babak 2 · Konsep NestJS (±15 menit)

"Bagaimana dependency injection bekerja di NestJS, dan apa beda scope DEFAULT, REQUEST, dan TRANSIENT? Sebutkan urutan pipeline request. Kenapa otorisasi role ditaruh di guard, bukan di middleware?"

Pertanyaan lanjutan yang sering muncul: "Kalau OrdersService meng-inject provider request-scoped, apa yang terjadi?" dan "User bukan admin mengirim body tidak valid: dapat 400 atau 403?"

Lihat jawaban contoh babak 2

"Class bertanda @Injectable didaftarkan sebagai provider di sebuah module; IoC container Nest membaca tipe parameter constructor dan menyuntikkan instance-nya. Provider bisa dipakai module lain kalau di-export. Scope DEFAULT berarti singleton, satu instance untuk seluruh aplikasi, dan itu yang direkomendasikan. REQUEST dibuat per request, dan scope itu naik ke atas rantai: siapa pun yang meng-inject-nya ikut request-scoped. [4] TRANSIENT memberi instance baru untuk setiap consumer. Pipeline-nya: middleware, guard, interceptor bagian sebelum, pipe, handler, lalu interceptor bagian sesudah dengan urutan terbalik; exception yang lolos ditangani exception filter. [5] Otorisasi di guard karena guard menerima ExecutionContext, jadi tahu handler mana yang akan jalan dan bisa membaca metadata @Roles lewat Reflector, sedangkan middleware tidak tahu handler berikutnya. Guard juga jalan sebelum pipe, jadi user bukan admin dengan body tidak valid mendapat 403, bukan 400." Dokumentasi Nest: guard dijalankan "after all middleware, but before any interceptor or pipe." [6]

Middleware→ Guard→ Interceptor (sebelum)→ Pipe→ Handler→ Interceptor (sesudah)

Checklist: apakah Anda menyebut…

  • provider @Injectable didaftarkan di module dan disuntik lewat constructor oleh IoC container?
  • DEFAULT = singleton dan direkomendasikan; REQUEST per request; TRANSIENT per consumer?
  • scope REQUEST naik ke class yang meng-inject-nya?
  • urutan: middleware → guard → interceptor → pipe → handler → interceptor; exception filter untuk error?
  • guard tahu handler lewat ExecutionContext dan membaca metadata dengan Reflector; middleware tidak?
  • guard jalan sebelum pipe, jadi request tak berhak ditolak (403) sebelum validasi?

Lulus jika minimal 4 dari 6.

Babak 3 · Live coding di kertas (±15 menit)

"Kita punya tabel Product di Prisma. Tulis endpoint POST /products yang hanya boleh dipanggil admin, dan GET /products/:id. Saya ingin melihat DTO dengan validasi, guard berbasis role, service yang memakai PrismaService, controller, dan satu unit test untuk service."

Anggap req.user sudah diisi auth guard (JWT) sebelumnya dan PrismaService sudah ada. Fokus pada empat potongan: DTO, guard, service + controller, test.

Lihat jawaban contoh babak 3 
// create-product.dto.ts
import { IsString, IsInt, Min } from 'class-validator';
export class CreateProductDto {
  @IsString() name: string;
  @IsInt() @Min(0) price: number;
}

// roles.guard.ts (req.user sudah diisi auth guard sebelumnya)
export const Roles = Reflector.createDecorator<string[]>();
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const roles = this.reflector.get(Roles, ctx.getHandler());
    if (!roles) return true;
    const { user } = ctx.switchToHttp().getRequest();
    return roles.some(r => user?.roles?.includes(r));
  }
}

// products.service.ts
@Injectable()
export class ProductsService {
  constructor(private prisma: PrismaService) {}
  create(dto: CreateProductDto) { return this.prisma.product.create({ data: dto }); }
  async findOne(id: number) {
    const p = await this.prisma.product.findUnique({ where: { id } });
    if (!p) throw new NotFoundException();
    return p;
  }
}

// products.controller.ts (main.ts: app.useGlobalPipes(new ValidationPipe({ whitelist: true })))
@Controller('products')
@UseGuards(RolesGuard)
export class ProductsController {
  constructor(private products: ProductsService) {}
  @Post() @Roles(['admin'])
  create(@Body() dto: CreateProductDto) { return this.products.create(dto); }
  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) { return this.products.findOne(id); }
}

// products.service.spec.ts
it('findOne melempar NotFoundException kalau produk tidak ada', async () => {
  const prisma = { product: { findUnique: jest.fn().mockResolvedValue(null) } };
  const mod = await Test.createTestingModule({
    providers: [ProductsService, { provide: PrismaService, useValue: prisma }],
  }).compile();
  await expect(mod.get(ProductsService).findOne(1)).rejects.toThrow(NotFoundException);
});

DTO harus class, bukan interface, karena ValidationPipe membaca decorator class-validator saat runtime; whitelist membuang properti tanpa decorator. [7] Di unit test, PrismaService diganti objek berisi jest.fn() lewat useValue sehingga tidak ada database yang disentuh. [8] Kalau waktu tersisa, sebut apa yang akan Anda tambah: test untuk create, e2e test dengan supertest untuk 403 dan 400.

Checklist: apakah kode Anda…

  • punya DTO berupa class dengan decorator class-validator (@IsString, @IsInt) dan ValidationPipe aktif?
  • punya RolesGuard yang mengimplementasikan CanActivate dan membaca @Roles lewat Reflector dari context.getHandler()?
  • memasang guard di controller atau method (@UseGuards) dan @Roles(['admin']) hanya di POST?
  • meng-inject PrismaService di service lewat constructor dan memanggil create/findUnique?
  • menghasilkan NotFoundException (404) kalau data tidak ada, dengan id diubah lewat ParseIntPipe?
  • memakai Test.createTestingModule dengan PrismaService di-mock (useValue + jest.fn) dan expect pada hasilnya?

Lulus jika minimal 4 dari 6.
