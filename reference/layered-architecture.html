Tiga aturan

  1. Layer hanya memanggil layer di bawahnya. Controller tidak memakai DbContext langsung, dan tidak berisi aturan bisnis. [1] [3]
  2. Bergantung pada interface (IProductService, IProductRepository), bukan kelas konkret dan tanpa new. [2]
  3. Hanya composition root (Program.cs) yang tahu implementasi konkret. [1]
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(cfg.GetConnectionString("Default")));
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.Configure<JwtSettings>(cfg.GetSection("Jwt"));

Jawaban 60 detik

Layered dalam satu project. Controller = HTTP, Service = aturan bisnis, Repository = akses data via EF Core. DTO memisahkan kontrak API dari skema DB. Semua bergantung pada interface dan disambungkan di Program.cs (composition root), sehingga Service bisa di-unit-test dengan mock. Config lewat appsettings + Options Pattern. Kalau domain bertambah kompleks, pindah ke Clean Architecture.

Pertanyaan lanjutan yang mungkin muncul

  • "Kenapa DTO?" → mencegah over-posting, menyembunyikan property, payload lebih kecil, object graph lebih datar; skema DB tidak bocor. [4]
  • "Kenapa Service tidak memakai new?" → dependensi langsung sulit diganti dan sulit di-unit-test; DI memakai interface + registrasi di container + injeksi lewat constructor. [2]
  • "Kenapa Options Pattern?" → akses konfigurasi bertipe per kelompok setting (encapsulation, separation of concerns). [5] Detail: lesson 0005.
  • "Repository di atas EF Core perlu?" → pro/kontra di lesson 0011.
  • "Layer vs tier?" → layer = pemisahan logis, tier = pemisahan fisik (server/proses berbeda). [1]
