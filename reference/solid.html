DIP dalam satu gambar

ProductService→IProductRepository←ProductRepository

Panah = dependency compile-time. Alur runtime tidak berubah: Service tetap memanggil Repository. [1] DIP = prinsip; Dependency Injection = teknik yang dimungkinkannya (container + constructor injection di Program.cs).

public class ProductService(IProductRepository repo) : IProductService { /* … */ }
builder.Services.AddScoped<IProductRepository, ProductRepository>();   // composition root
var sut = new ProductService(new Mock<IProductRepository>().Object);   // unit test

Jawaban 60 detik: "SOLID mana yang paling sering Anda terapkan?"

SRP dan DIP, karena keduanya membuat kode bisa di-unit-test. SRP: Controller hanya HTTP, Service aturan bisnis, Repository akses data; fitur baru seperti export CSV jadi class baru. DIP: Service bergantung pada IProductRepository, didaftarkan di Program.cs dan diinjeksi lewat constructor, sehingga di test saya memberi mock Moq (seperti jest.fn()). Gejala SRP dilanggar: constructor dengan terlalu banyak dependency.

Pertanyaan lanjutan yang mungkin muncul

  • "SRP vs separation of concerns?" → SRP berlaku di level class, tapi bisa dipakai sebagai prinsip arsitektur yang mirip separation of concerns (pembagian layer). [1]
  • "Bagaimana tahu class melanggar SRP?" → banyak dependency yang diinjeksi adalah tandanya. [3]
  • "Kenapa tidak new saja?" → dependency langsung sulit diganti dan sulit di-unit-test. [3]
  • "Explicit dependencies?" → class meminta semua kolaboratornya lewat constructor, supaya jujur pada pemakainya. [1]
  • "Repository di atas EF Core perlu?" → lesson 0011.
