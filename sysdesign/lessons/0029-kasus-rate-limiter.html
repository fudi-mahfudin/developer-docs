Studi kasus: rate limiter terdistribusi

Di mana limiter dipasang (gateway atau middleware), counter bersama di Redis, race condition, dan respons 429

Sebelumnya, lesson 0028 menjalankan kerangka 5 langkah untuk sistem read-heavy. Kali ini soalnya berbeda: komponen kecil yang dipanggil di setiap request, sehingga latency tambahan dan kebenaran counter di banyak server menjadi inti diskusinya. Algoritmanya (token bucket, leaky bucket, fixed/sliding window) sudah dibahas di modul Reliabilitas & API; di sini fokusnya pada penerapan terdistribusi.

Target lesson ini: Anda bisa menjawab "Rancang rate limiter untuk API yang berjalan di 10 server" tanpa catatan, dalam 90 detik: posisi limiter, kenapa counter harus bersama (Redis), race condition pada counter dan cara menutupnya, respons 429 + Retry-After, dan trade-off fixed window vs token bucket.

Langkah 1 — Klarifikasi requirement

  • Functional: batasi setiap API key ke 100 request per menit; request yang melewati batas ditolak dengan pesan jelas; batas bisa berbeda per paket (gratis vs berbayar).
  • Skala (asumsi): 1 juta API key aktif per hari; API berjalan di 10 server di belakang load balancer round robin; total ±5.000 QPS rata-rata.
  • Non-functional: limiter menambah latency sesedikit mungkin (satu round trip jaringan per request); kalau limiter rusak, API tetap jalan; sedikit lebih longgar dari 100 sesekali masih bisa diterima.

Baris terakhir adalah angka yang membenarkan komponen pertama: counter harus bersama untuk semua server. ±100 MB dan ±15.000 operasi/detik adalah beban kecil untuk satu instance Redis (tetap ukur dengan benchmark sebelum memutuskan apa pun). Kalau API hanya berjalan di satu server, counter in-memory atau modul nginx sudah cukup dan Redis tidak perlu.

Respons penolakan mengikuti RFC 6585: 429 berarti "the user has sent too many requests in a given amount of time ("rate limiting")", dan respons itu "MAY include a Retry-After header indicating how long to wait". [1] Nilai Retry-After boleh berupa jumlah detik atau HTTP-date. [2]

Langkah 4 — High-level design (v1)

Desain v1 paling sederhana yang memenuhi angka: middleware di setiap API server dan satu Redis sebagai counter bersama, dengan fixed window per menit. Redis docs memberi pola ini langsung: INCR + EXPIRE dibungkus MULTI/EXEC "in order to make sure that we'll both increment and set the expire at every API call". [5]

Alur: middleware membentuk key rl:{apiKey}:{menit}, menjalankan INCR (+ EXPIRE 60 detik), lalu membandingkan nilai setelah increment dengan batas. Lebih dari 100 → 429; selain itu → handler.

Langkah 5 — Deep dive, bottleneck, trade-off

1. Race condition pada counter. Dua bentuk yang perlu Anda sebut:

  • Check-then-act: v = GET(key); if v < 100 then INCR(key). Dua server membaca 99 pada saat yang sama, keduanya lolos, counter menjadi 101. Perbaikan: jangan membaca dulu. INCR adalah operasi atomic yang mengembalikan nilai baru, jadi bandingkan hasil INCR itu dengan batas.
  • Key bocor: Redis docs mencatat varian single counter (INCR, lalu EXPIRE kalau nilainya 1) punya race condition: "If for some reason the client performs the INCR command but does not perform the EXPIRE the key will be leaked". Perbaikannya: jadikan keduanya satu Lua script yang dikirim dengan EVAL. [5] Redis "guarantees the script's atomic execution", jadi tidak ada server lain yang menyisip di tengah. [6]
-- Lua script (dijalankan atomic di Redis)
local current = redis.call("incr", KEYS[1])
if current == 1 then redis.call("expire", KEYS[1], 60) end
return current

2. Burst di batas window. Fixed window membolehkan 100 request pukul 10:00:59 dan 100 lagi pukul 10:01:00: 200 request dalam dua detik. Kalau requirement melarang burst seperti itu, evolusi ke sliding window counter atau token bucket (keduanya bisa ditulis sebagai Lua script, tetap satu round trip). Kalau requirement "sedikit longgar masih bisa diterima" seperti di langkah 1, fixed window cukup dan lebih murah dipahami.

3. Redis gagal. Requirement bilang API harus tetap jalan, jadi limiter fail-open: pakai timeout pendek ke Redis; kalau gagal, loloskan request dan catat metrik. Untuk availability counter, tambah replica Redis. Trade-off: Redis "uses by default asynchronous replication" [7], jadi saat failover sebagian counter bisa hilang dan beberapa API key sesaat mendapat jatah lebih.

4. Bottleneck berikutnya (belum sekarang). Kalau CPU Redis mendekati batas pada puncak, langkah berikutnya memecah key ke beberapa node (shard berdasarkan API key). Pada ±15.000 operasi/detik ini belum dibenarkan; sebut sinyalnya saja.

Latihan 3 — Counter dan race condition

Latihan lisan — Ucapkan dengan suara keras

Pasang timer dan jawab dengan suara keras, seolah sedang interview. Jangan buka jawaban contoh sebelum selesai.

"Rancang rate limiter: 100 request per menit per API key, untuk API yang berjalan di 10 server." (90 detik)
Bandingkan dengan jawaban contoh dan checklist-nya

"Limiter saya pasang di server, sebagai middleware atau di API gateway, bukan di client karena client tidak bisa dipercaya. Karena ada 10 server di belakang round robin, counter per server membuat limit efektif sekitar 1.000 per menit, jadi counter harus bersama: satu Redis. Estimasinya sekitar 15.000 operasi per detik dan 100 MB untuk 1 juta key, masih muat di satu node. v1-nya fixed window: key berisi API key dan menit, INCR lalu EXPIRE 60 detik, dan saya bandingkan nilai hasil INCR, bukan GET dulu, supaya tidak ada race check-then-act. INCR dan EXPIRE saya gabung dalam Lua script supaya atomic dan key tidak bocor tanpa TTL. Request yang ditolak mendapat 429 dengan Retry-After. Fixed window membolehkan burst dua kali lipat di batas menit; kalau itu tidak boleh, saya ganti sliding window atau token bucket. Kalau Redis down, limiter fail-open dengan timeout pendek."

Checklist: apakah Anda menyebut…

  • posisi di server (middleware atau gateway), bukan client, beserta alasannya?
  • counter bersama di Redis karena counter per server membuat limit efektif 10×?
  • race condition: bandingkan hasil INCR, dan INCR + EXPIRE atomic lewat MULTI atau Lua script?
  • respons 429 dengan Retry-After?
  • trade-off fixed window (burst di batas window) vs sliding window atau token bucket?
  • membenarkan komponen dengan angka (Redis karena 10 server; ±15.000 operasi/detik dan ±100 MB muat di satu node; sharding belum perlu)?

Lulus jika minimal 4 dari 6.

Bacaan lanjutan (opsional, tidak dihitung dalam durasi) Redis docs: INCR, bagian "Pattern: Rate limiter", ±10 menit. Tiga varian rate limiter dan race condition masing-masing.
